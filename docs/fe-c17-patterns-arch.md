# fe-c17-s1 | 设计模式总览与选型
> 模式不是银弹，是"在特定场景已被验证的组织代码方式"。

## 心智模型
设计模式像**装修的成熟户型方案**：你不必每次从零想"厨房该在哪"，直接套经过验证的格局，再按自家需求微调。关键是"知道有哪些方案、各自适合什么房型"，而不是硬套。

## 核心知识点（锚定官方）
- **经典分类（GoF/Addy Osmani《JavaScript Design Patterns》）**：创建型（工厂/单例）、结构型（模块/组合/适配器）、行为型（观察者/策略/命令）。
- **前端语境**：多数模式已被框架内化——React/Vue 组件即组合模式，状态管理即观察者，DI 由框架提供。
- **反模式**：过度抽象（三层继承只为复用一行）、为用模式而用模式。

## 为什么重要
随着应用变大，代码组织方式直接决定可维护性与团队协作效率。懂模式能让你在 Code Review 里"一眼看出更好的结构"，也能在面试中讲清"为什么这么拆"。

## 常见坑
- 把简单问题复杂化：一个工具函数非要套工厂+策略。
- 套错场景：用单例存请求级状态导致并发串号（参考 fe-c16-s6）。
- 忽视框架已有能力，重复造轮子（自己写发布订阅而框架已有响应式）。

## 动手自测
1. 列出现有项目里用到的"隐式模式"（组件=组合、store=观察者），写一段注释说明。
2. 把一个 if/else 分支链重构成策略模式，对比可读性。

## 面试视角
"你用过哪些设计模式？为什么用观察者？单例的坑？"——讲清模式解决的问题而非名词背诵。

# fe-c17-s2 | 观察者模式与发布订阅
> UI 变化驱动视图更新，底层就是观察者；跨模块通信靠事件总线。

## 心智模型
观察者像**订阅公众号**：你（观察者）关注（subscribe）后，号主（被观察者）一发文章（notify）你就收到推送。发布订阅（Pub/Sub）多了一个"邮局"（中间代理），发布者和订阅者互不相识，只认频道。

## 核心知识点（锚定官方）
- **观察者（Observer）**：主体维护观察者列表，状态变时逐个通知；JS 里 `EventTarget.addEventListener` 即原生观察者。
- **Node `events` 模块**：`EventEmitter` 是服务端 Pub/Sub 实现（前端 BFF 常用）。
- **与响应式区分**：Vue 的 `ref`/React 的 `useState` 是把"状态→视图"的观察者关系由框架自动管理。

## 为什么重要
前端状态驱动 UI 的本质是观察者；事件总线解耦模块。理解它才能看懂 Redux/Vuex/Pinia 的底层，也才能在自定义控件里正确暴露事件。

## 常见坑
- 忘记 `unsubscribe`/`removeEventListener`，组件销毁后回调仍触发（内存泄漏）。
- 一个事件被多个订阅者改同一状态，顺序依赖导致 bug。
- 滥用全局事件总线，调用链不可追踪（"谁发了这个事件？"）。

## 动手自测
1. 用 `EventTarget` 手写一个迷你发布订阅，支持 on/off/emit。
2. 在组件卸载时正确注销监听，用 DevTools 内存面板验证无泄漏。

## 面试视角
"观察者和发布订阅区别？为什么要及时解绑？框架响应式底层是什么？"——讲清耦合度、内存泄漏、框架封装。

# fe-c17-s3 | 模块模式与命名空间
> 在 ES 模块之前，靠 IIFE 制造私有作用域曾是主流隔离手段。

## 心智模型
模块模式像**带锁的储物柜**：IIFE（立即执行函数）造出一个外人进不去的私密空间，只通过返回的"取物口"（公开 API）对外暴露你想给的东西，其余实现细节藏起来。

## 核心知识点（锚定官方）
- **IIFE + 闭包**：`(function(){ const private=...; return { public }; })()` 实现私有状态。
- **命名空间模式**：早期用全局对象 `App.util = ...` 避免污染，但仍有全局耦合。
- **现代替代**：ES Modules（fe-c16-s2）用 `import/export` 原生达成隔离，已淘汰手写 IIFE 模块。

## 为什么重要
理解历史模块模式，能读懂老代码库（jQuery 插件、`window.xxx` 挂载），也更能体会 ESM 解决了什么痛点。

## 常见坑
- 在 ESM 时代还手写 IIFE 模块，徒增样板。
- 命名空间挂在全局对象上，仍可能被覆盖或冲突。
- 闭包引用大对象不及时释放，造成内存泄漏。

## 动手自测
1. 用 IIFE 写一个带私有计数器的计数器模块，验证外部无法直接改内部值。
2. 把同一逻辑改写为 ESM，对比代码量与可读性。

## 面试视角
"模块模式解决什么？ESM 如何替代它？闭包为什么能造私有？"——讲清作用域隔离、闭包、现代替代。

# fe-c17-s4 | 组合模式与组件组合
> React/Vue 的一切皆组件，组合模式是 UI 框架的天生范式。

## 心智模型
组合模式像**俄罗斯套娃的乐高化**：树里每个节点（组件）都长一样（有 render/children），你可以把小组件拼成大组件、再把大组件拼成页面，调用方无需区分"单个"还是"一群"——统一对待。

## 核心知识点（锚定官方）
- **组合（Composite）**：叶子与容器实现同一接口，递归组合成树；React 的 `children`/`props`、Vue 的 `<slot>` 即此思想。
- **HOC / 组合 API**：React 用 `children` 组合、Vue 用 `slots` 做布局插槽。
- **headless 组件**：把逻辑与 UI 分离，通过组合复用（如 Radix/VueUse）。

## 为什么重要
组件化是前端工程化的核心。懂组合模式才能写出"可拼装、可复用、易测试"的 UI，避免巨石组件与 prop 透传地狱。

## 常见坑
- "prop  drilling"：层层透传属性，中间组件沦为搬运工——可用 Context/provide-inject 或组合。
- 过度拆分导致组件碎成几十个、阅读困难。
- 用继承扩展组件（React 不推荐），应优先组合。

## 动手自测
1. 写一个 `Card` 容器组件，用 `slot`/`children` 组合任意内容，对比不用组合的写法。
2. 把一段"逻辑+UI"拆成 headless hook + 纯展示组件。

## 面试视角
"组合模式在前端哪体现？为什么 React 不推荐继承？slot/children 的作用？"——讲清组件树、组合优于继承。

# fe-c17-s5 | 单例与服务定位
> 全局只一份的实例（如 store、router），但要小心并发与测试。

## 心智模型
单例像**公司唯一的公章**：全公司盖章都走它，保证"章"只有一份、状态一致。服务定位器（Service Locator）则是"前台登记簿"——谁要什么服务去查就行。

## 核心知识点（锚定官方）
- **单例（Singleton）**：保证类只有一个实例并全局可访问；前端 `store`、`router`、`i18n` 实例多为单例。
- **依赖注入（DI）**：Vue 的 `provide/inject`、Angular 的 DI 容器、NestJS 的 `@Injectable` 把依赖"由外部注入"而非内部 `new`。
- **测试隐患**：单例共享状态会让测试用例互相污染，需用 DI 注入 mock。

## 为什么重要
状态管理、路由、配置中心都依赖单例/服务定位。懂它才能在 Nuxt（本项目）里正确使用 `useState`（注意它是请求级而非全局单例）、`pinia` store。

## 常见坑
- 把请求级数据放进全局单例（如用户会话），多用户串号（见 fe-c16-s6）。
- 单例带可变状态导致测试不纯。
- 过度依赖全局单例，模块耦合变高。

## 动手自测
1. 用 `provide/inject` 把配置注入深层组件，对比逐层 props 透传。
2. 在单测里用 mock 替换单例依赖，验证测试隔离。

## 面试视角
"单例适用场景？为什么测试要小心？DI 和直接 new 的区别？"——讲清全局状态、测试污染、解耦。

# fe-c17-s6 | 状态管理范式
> 当组件间共享状态变复杂，需要统一的状态管理（Flux/Redux/Pinia）。

## 心智模型
状态管理像**公司的中央公告板**：所有部门（组件）都从同一块板读最新通知、要改也只能通过规定流程（action/dispatch）改，避免"张三口头说改了、李四不知道"的信息不一致。

## 核心知识点（锚定官方）
- **Flux 单向流（Meta Flux 文档）**：action → dispatcher → store → view，数据单向、可预测。
- **Redux（redux.js.org）**：纯函数 reducer `(state, action) => newState`，不可变更新、时间旅行调试。
- **Pinia（pinia.vuejs.org，Vue 官方推荐）**：`state/getters/actions`，组合式 API 风格，比 Vuex 更轻。

## 为什么重要
Nuxt（本项目）官方状态库即 Pinia。组件多了之后，prop 透传和事件冒泡会失控，集中式状态管理能显著降低复杂度、便于调试。

## 常见坑
- 在 store 里存请求级/用户级状态导致串号（Nuxt 要用 `useState`/插件隔离）。
- 直接 mutation 改 state 而非走 action，破坏可追踪性（老 Vuex 模式）。
- 把本属组件私有的 UI 状态也塞进全局 store，过度设计。

## 动手自测
1. 用 Pinia 写一个购物车 store，体会 action 改 state、getter 派生。
2. 故意在 reducer 里直接改原 state，观察为什么 Redux 要求返回新对象。

## 面试视角
"Redux 和 Pinia 区别？为什么单向数据流？不可变更新为何重要？"——讲清可预测性、纯函数、调试优势。

# fe-c17-s7 | 微前端架构
> 当多个团队要独立开发部署同一大应用，把应用拆成可组合的"应用碎片"。

## 心智模型
微前端像**商场里的独立门店**：每家店（子应用）自己装修、自己进货、独立开业/倒闭，但都挂在同一商场（主框架）里，顾客（用户）感觉是逛一家大商场。

## 核心知识点（锚定官方）
- **核心问题**：独立开发/部署、技术栈无关、运行时集成、样式与 JS 隔离。
- **集成方式**：iframe（最强隔离）、Web Components、JS 入口挂载（qiankun 等）。
- **基座（Shell）**：负责路由分发、共享依赖、通信（自定义事件/全局 store）。

## 为什么重要
大型组织中多个前端团队协作同一产品时，微前端能解耦发布节奏、降低耦合。理解它才能在中大型架构评审中提出合理方案。

## 常见坑
- 共享依赖（React/Vue）重复加载，包体翻倍——需 externals 或模块共享。
- 样式/全局变量互相污染（iframe 外需做隔离）。
- 拆得太碎，通信与运维成本反超收益。

## 动手自测
1. 用 qiankun 或原生 Web Components 把两个独立打包的子应用挂到同一基座。
2. 验证子应用卸载后其全局样式/事件被清理。

## 面试视角
"微前端解决什么？和 iframe 比优劣？依赖如何共享？"——讲清独立部署、隔离成本、适用边界。

# fe-c17-s8 | 模块联邦 Module Federation
> Webpack 5 / Rspack 的 Module Federation 让多个构建产物在运行时共享模块。

## 心智模型
模块联邦像**多家餐厅共用同一个冷链供应链**：A 店（应用 A）产出的"预制菜"（模块）直接被 B 店按需取用，不用各自备货、也不用重新打包，运行时实时拉取。

## 核心知识点（锚定官方）
- **Module Federation（webpack.js.org/plugins/module-federation）**：`exposes` 暴露模块、`remotes` 远程消费，构建时声明、运行时加载。
- **共享依赖（shared）**：声明 react 等共享，避免重复实例化（singleton:true）。
- **Rspack/Vite 实现**：社区有 `@module-federation/enhanced` 等跨构建工具方案。

## 为什么重要
它是微前端"运行时集成"的高性能实现，支持独立部署的团队共享组件/工具而不重新打包。理解它能落地真正的按需集成架构。

## 常见坑
- shared 没设 `singleton:true`，导致 React 双实例、hooks 报错。
- 远程模块版本不兼容，运行时找不到导出。
- 把大模块都远程化，首屏反而变慢（额外网络往返）。

## 动手自测
1. 用 Module Federation 让 appB 消费 appA 暴露的一个按钮组件，验证独立部署可热更。
2. 故意设两次 React 实例，观察报错并加 `singleton` 修复。

## 面试视角
"Module Federation 是什么？和 npm 包共享区别？shared singleton 为何重要？"——讲清运行时共享、独立部署、实例唯一。

# fe-c17-s9 | Monorepo 工程化
> 多包/多应用放在一个仓库，统一构建、测试、发布。

## 心智模型
Monorepo 像**一栋写字楼里多家关联公司**：代码各占一层（packages），但共用大堂（依赖安装）、电梯（构建管道）、物业（CI）。改一处接口，所有依赖方立刻能跑测试发现影响。

## 核心知识点（锚定官方）
- **pnpm workspace（pnpm.io/workspaces）**：基于硬链接的内容寻址存储，省空间、严格依赖隔离（不允诺扁平化幽灵依赖）。
- **Turborepo（turbo.build）**：基于任务依赖图的增量构建与远程缓存，`turbo run build --filter`。
- **对比 Polyrepo**：Monorepo 利于跨包重构与统一规范，但需更好 CI/权限治理。

## 为什么重要
中大型前端团队普遍采用 Monorepo 管理组件库、应用、工具。理解 pnpm workspace + Turborepo 能显著提升多包项目的构建与协作效率。

## 常见坑
- 用 npm/yarn 扁平化导致"幽灵依赖"（没声明却能用），换 pnpm 后报错。
- 没有任务缓存，CI 全量重构建越来越慢。
- 仓库过大、权限难控——需配合 CODEOWNERS 与 CI 过滤。

## 动手自测
1. 用 pnpm workspace 建 `packages/ui` 与 `apps/web`，web 直接依赖本地 ui 包。
2. 用 Turborepo 串起 build/test，观察二次运行命中缓存变快。

## 面试视角
"Monorepo 利弊？pnpm 如何避免幽灵依赖？Turborepo 缓存原理？"——讲清统一重构、内容寻址、增量缓存。
