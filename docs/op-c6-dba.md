# op-c6-s1 | MySQL 备份与恢复
> 备份不是"有就行"，是"能恢复且验证过"才算数。

## 心智模型
数据库备份像**保险柜里的现金+流水账**：全量备份是某天清点的一整箱钱（mysqldump/xtrabackup），增量/binlog 是之后每天的流水，恢复时先搬箱子、再按流水补到指定时刻（PITR）。没演练过的备份等于没备份。

## 核心知识点（锚定官方）
- **逻辑备份 `mysqldump`**：导出 SQL，慢但可读；`--single-transaction` 得一致性快照。
- **物理备份 `xtrabackup`（Percona）**：热备 InnoDB 文件，快、支持流式/压缩，适合大库。
- **PITR（时间点恢复）**：全量 + binlog（`mysqlbinlog --start-position`）回放到故障前时刻。

## 为什么重要
数据是企业的命根子。丢失或未验证的备份会在宕机/误删时造成不可逆损失。DBA 第一职责就是"备份可恢复"。

## 常见坑
- 只备份从不恢复演练，真出事发现备份损坏。
- 逻辑备份锁表导致线上长事务（应用 `--single-transaction` 注意一致性）。
- binlog 被清，无法做 PITR。

## 动手自测
1. 用 xtrabackup 热备一个实例，再恢复到另一台，验证数据一致。
2. 模拟误删表，用全量+binlog 做 PITR 恢复到删前时刻。

## 面试视角
"备份方式区别？PITR 怎么做？为什么备份要演练？"——讲清逻辑/物理、binlog 回放、演练必要性。

# op-c6-s2 | MySQL 主从复制运维
> 复制是读写分离与高可用的地基，但延迟与断点是常态。

## 心智模型
主从复制像**总店把每天的交易流水（binlog）寄给分店**，分店照着重做一遍保持账本一致。网络一抖，分店就"慢半拍"（复制延迟）；流水寄丢了（断点），分店就得从正确位置接着重做。

## 核心知识点（锚定官方）
- **复制原理（MySQL 官方）**：主库写 binlog → dump 线程发从库 → IO 线程写 relay log → SQL 线程重放。
- **GTID 复制**：用全局事务 ID 取代文件+位置，自动找同步点，故障切换更稳。
- **延迟监控**：`Seconds_Behind_Master` / `performance_schema`；大事务、从库慢查询都会放大延迟。

## 为什么重要
读写分离、备份、高可用都建立在复制上。不懂延迟成因与断点修复，会在大促从库落后、切主混乱时束手无策。

## 常见坑
- 主库一个超大事务，从库重放卡很久（延迟飙升）。
- 从库开写导致主从不一致（应 `read_only`）。
- 非 GTID 切换，找 binlog 位置易错。

## 动手自测
1. 搭一主一从（GTID），在主库插数据验证从库同步。
2. 故意在主库跑大事务，观察从库 `Seconds_Behind_Master` 变化。

## 面试视角
"复制流程？GTID 好处？复制延迟怎么排查？"——讲清 binlog 链路、自动位点、延迟根因。

# op-c6-s3 | Redis 持久化与高可用
> Redis 快是因为内存，但"内存"意味着重启就丢，必须配持久化与高可用。

## 心智模型
Redis 像**放在桌上的现金抽屉（内存，快但一关灯就没）**：RDB 是定时拍照存档、AOF 是每笔记账。高可用则是"再摆一个同样的抽屉+一个监工（Sentinel）"，主抽屉出问题监工立刻把备抽屉扶正。

## 核心知识点（锚定官方）
- **持久化（redis.io）**：RDB 快照（快、省空间、可能丢最后一段）、AOF 追加（每写都记，可配 everysec，更稳但文件大）。
- **Sentinel**：监控+自动故障转移+配置中心，解决主从切换。
- **Cluster**：分片+副本，数据按 slot 分布，支持水平扩展与故障转移。

## 为什么重要
Redis 常做缓存/会话/排行榜，一旦丢了且没持久化，缓存击穿打爆后端。理解持久化与 Sentinel/Cluster 才能设计并守住高可用。

## 常见坑
- 纯内存无持久化当存储，重启全丢。
- AOF everysec 下宕机丢 1 秒，业务误当不丢。
- Cluster 大 key 迁移阻塞、跨 slot 事务不支持。

## 动手自测
1. 配置 RDB+AOF，重启验证数据恢复；对比只 RDB 时的丢数据窗口。
2. 用 Sentinel 模拟主节点宕机，验证自动选主与客户端重连。

## 面试视角
"RDB vs AOF？Sentinel 干嘛？Cluster 分片原理？"——讲清快照/日志、故障转移、slot 分片。

# op-c6-s4 | 慢查询治理与索引优化
> 慢查询是数据库性能的头号杀手，治理靠慢日志+执行计划。

## 心智模型
慢查询治理像**给拥堵路口装监控+改红绿灯**：先开慢日志（slow query log）抓出"哪些车开得慢"，再用 `EXPLAIN` 看它走的"路线"（是否全表扫、是否用索引），最后建对索引或改写 SQL 让车走高速。

## 核心知识点（锚定官方）
- **慢日志（MySQL）**：`slow_query_log`、`long_query_time`、`log_queries_not_using_indexes`；用 `mysqldumpslow`/`pt-query-digest` 聚合。
- **EXPLAIN**：看 `type`（ALL=全表扫最差）、`key`（用到哪个索引）、`rows`（估算扫描行）、`Extra`（Using filesort/index）。
- **索引策略**：复合索引最左前缀、覆盖索引避免回表、避免对列函数导致索引失效。

## 为什么重要
一条慢 SQL 能拖垮整个实例（连接占满、CPU 打满）。DBA 的日常就是持续治理慢查询、守住响应时间。

## 常见坑
- 对索引列套函数/`隐式转换`，索引失效全表扫。
- 建一堆重复/低区分度索引，写变慢、空间涨。
- 只看 `EXPLAIN` 不看实际数据分布，误判。

## 动手自测
1. 开慢日志跑压测，用 pt-query-digest 找出 Top 慢 SQL。
2. 对一条全表扫 SQL 建复合索引，EXPLAIN 验证 type 从 ALL 变 ref/range。

## 面试视角
"怎么定位慢 SQL？EXPLAIN 看什么？索引为什么失效？"——讲清慢日志、执行计划、最左前缀。

# op-c6-s5 | 参数调优
> 默认参数面向通用，生产必须按硬件与负载调。

## 心智模型
参数调优像**按发动机改装车**：`innodb_buffer_pool_size` 是把多少内存当"数据缓存车库"——越大命中率越高、少读盘；`max_connections` 是同时能进几辆车，设太小堵车、设太大内存炸。

## 核心知识点（锚定官方）
- **InnoDB 缓冲池（MySQL）**：`innodb_buffer_pool_size` 通常设物理内存 60-80%，让热数据驻内存。
- **连接与线程**：`max_connections`、`thread_cache_size`；配合连接池而非每请求新建。
- **落盘策略**：`innodb_flush_log_at_trx_commit`（1=不丢、2/0=性能换风险）；`sync_binlog`。

## 为什么重要
不合理参数要么浪费昂贵硬件，要么在高峰雪崩。DBA 需结合监控（命中率、连接数、IO 等待）持续调优。

## 常见坑
- buffer pool 设太小，命中率低、磁盘 IO 打满。
- `trx_commit=0` 追求性能，宕机丢事务。
- `max_connections` 过大被慢查询拖垮全实例。

## 动手自测
1. 调大 buffer pool，用 sysbench 压测对比 QPS 与磁盘读。
2. 故意设 `trx_commit=0`，kill -9 后验证事务丢失。

## 面试视角
"buffer pool 设多大？trx_commit 各值含义？连接数怎么定？"——讲清缓存命中、持久化取舍、连接池。

# op-c6-s6 | 高可用架构
> 单实例必挂，高可用靠"冗余+自动切换+流量调度"。

## 心智模型
高可用架构像**重要桥梁的备用桥+交警**：主库是主桥，副本是备用桥，交警（ Orchestrator/MHA/ProxySQL）在主桥塌时把车流切到备用桥，应用无感。冗余不是为了用，是为了"挂了也能活"。

## 核心知识点（锚定官方）
- **MGR（MySQL Group Replication）**：基于 Paxos 的多主/单主复制，自动选主、防脑裂。
- **Orchestrator（GitHub）**：拓扑管理与自动故障转移，可视化复制树。
- **ProxySQL**：读写分离+连接池+故障节点剔除，屏蔽后端变化。

## 为什么重要
数据库可用性直接决定业务可用性。没有自动切换，主库宕机就要人工救火、RTO 以小时计。高可用架构是 SLA 的底座。

## 常见坑
- 有副本但无自动切换，主挂仍要人工干预。
- 读写分离把写流量误路由到从库（只读）。
- 脑裂：双主同时可接受写，数据冲突。

## 动手自测
1. 用 MGR 起三节点，kill 主节点验证自动选主。
2. 用 ProxySQL 把读流量按权重分到从库。

## 面试视角
"高可用怎么实现？MGR/Orchestrator 作用？脑裂怎么防？"——讲清冗余、自动切换、quorum。

# op-c6-s7 | 在线 schema 变更
> 直接 ALTER 大表会锁表把业务卡死，必须无锁变更工具。

## 心智模型
在线改表像**给飞行中的飞机换引擎**：不能停飞（锁表），所以用 gh-ost/pt-osc 这种"影子表"方案——先建一张新表悄悄改好结构、边跑边把老表增量同步过去，最后瞬间切换，业务几乎无感。

## 核心知识点（锚定官方）
- **pt-online-schema-change（Percona）**：建影子表+触发器同步增量，完成后 rename 切换。
- **gh-ost（GitHub）**：基于 binlog 异步同步，无触发器、可控暂停/限流，对主库更友好。
- **风险点**：磁盘空间（影子表）、主从延迟、切换瞬间锁。

## 为什么重要
大表 `ALTER` 原生锁表会导致长时间不可写，是"改个字段搞挂业务"的经典事故。无锁变更是 DBA 必备技能。

## 常见坑
- 小表也用重工具，流程复杂化。
- 变更期间主从延迟飙升，从库读脏。
- 磁盘不够建影子表，变更中途失败。

## 动手自测
1. 用 gh-ost 给一张百万行表加索引，观察业务写入不被长期阻塞。
2. 对比原生 ALTER 与 gh-ost 对线上写入的影响。

## 面试视角
"大表改结构怎么做？pt-osc 和 gh-ost 区别？为什么不能直接 ALTER？"——讲清影子表、binlog 同步、锁表代价。

# op-c6-s8 | 容量规划与监控
> 不知道数据库"还能撑多久"，就等于蒙眼开车。

## 心智模型
容量监控像**油表+转速表**：QPS、连接数、缓冲命中率、磁盘余量是油表；慢查询比例、复制延迟是转速异常。DBA 要设阈值告警，在"油尽前"扩容或优化，而不是等抛锚。

## 核心知识点（锚定官方）
- **指标采集**：`mysqld_exporter`/`redis_exporter` + Prometheus；关键指标 QPS、Connections、Innodb_buffer_pool_hit、Replication lag、慢查询数。
- **监控项**：磁盘空间/增长趋势、连接数水位、锁等待、临时表落盘。
- **告警**：基于 SLO 设阈值（如延迟>5s、命中率<95%）。

## 为什么重要
被动救火成本高。前瞻的容量与监控能在性能拐点前行动，保障 SLA、避免突发雪崩。

## 常见坑
- 只监控"进程活着"，不监控"慢/满/延迟"。
- 磁盘 100% 才告警，已无法写入。
- 指标无长期趋势，无法做容量预测。

## 动手自测
1. 部署 mysqld_exporter + Prometheus + Grafana，看关键面板。
2. 设一条"复制延迟>10s"告警规则并验证触发。

## 面试视角
"DB 监控看哪些指标？如何做容量规划？为什么只看进程存活不够？"——讲清核心指标、趋势预测、SLO 告警。

# op-c6-s9 | 容灾与恢复演练
> 容灾不是文档里写了，是真正演练过、RTO/RPO 可达成。

## 心智模型
容灾演练像**消防演习**：你不能等火灾当天才第一次找灭火器。定期把备份恢复到隔离环境、模拟主库宕机切到异地，验证"真出事时能在承诺时间内（RTO）只丢这么点（RPO）恢复业务"。

## 核心知识点（锚定官方）
- **RTO/RPO**：恢复时间目标、恢复点目标（最多丢多少数据）；二者决定备份频率与高可用等级。
- **演练类型**：备份恢复演练（定期恢复校验）、故障注入（chaos 杀主库看切换）、异地容灾切换。
- **等级**：同城双活/异地多活，成本与可用性递增。

## 为什么重要
没有演练的容灾是心理安慰。真实故障中，未验证的恢复流程往往失败，造成超长停机与数据丢失。

## 常见坑
- 只写容灾文档从不演练，出事手忙脚乱。
- RTO 目标定得漂亮但恢复实际要几小时。
- 恢复演练用和线上不同版本/配置，结论失真。

## 动手自测
1. 季度性把最新备份恢复到沙箱，校验数据完整性与耗时（对标 RTO）。
2. 用 chaos 工具杀主库，验证 Sentinel/MGR 切换时间与数据丢失量（对标 RPO）。

## 面试视角
"RTO/RPO 是什么？为什么必须演练？容灾等级怎么选？"——讲清恢复目标、演练价值、成本权衡。
