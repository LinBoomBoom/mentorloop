# be-test-s1 | 测试金字塔与分层
> 测试不是越多越好，是按"成本-价值"分层投入。

## 心智模型
测试金字塔像**一个三角形的防线**：底层是大量廉价快速的单元测试（地基，占 70%），中层是少量集成测试（验证模块协作），顶层是更少但更贵的端到端测试（验证完整链路）。倒过来（冰激凌筒）则慢且脆。

## 核心知识点（锚定官方）
- **测试金字塔（Martin Fowler / Google 测试博客）**：单元 > 集成 > E2E，数量与成本反相关。
- **三层职责**：Unit 测函数/类逻辑；Integration 测"代码+真实依赖（DB/HTTP）"；E2E 测用户旅程。
- **测试替身分层**：越靠上越用真实依赖，越靠下越用 mock。

## 为什么重要
没有分层策略，团队要么不写测试（不敢改），要么堆满 E2E（CI 跑一小时）。金字塔让"改代码有安全感"且 CI 快。

## 常见坑
- 倒金字塔：全是 E2E，CI 慢、flaky 多、维护贵。
- 单元测试里连真实数据库，慢且不稳定。
- 测试只断言"没抛异常"，等于没测。

## 动手自测
1. 给一个现有服务画测试金字塔，标出哪层缺、哪层过量。
2. 把一个连库的"单测"改成正经单测（mock 依赖）+ 一个独立集成测试。

## 面试视角
"测试金字塔是什么？为什么 E2E 不能多？单测和集成测区别？"——讲清成本收益、分层职责。

# be-test-s2 | JUnit 5 单元测试
> Java 后端单测事实标准，注解驱动、生命周期清晰。

## 心智模型
JUnit 就像**给方法请的"考官"**：你用 `@Test` 圈出要考的方法，`@BeforeEach` 考前准备、`@AfterEach` 考后收尾，考官按你写的断言（`assertEquals` 等）判定对错，全公司（构建）统一阅卷。

## 核心知识点（锚定官方）
- **JUnit 5（junit.org）**：`@Test`、`@BeforeEach`/`@AfterEach`、`@DisplayName`、断言 `Assertions.*`、假定 `Assumptions`。
- **生命周期**：每个测试方法独立实例化，状态不串；`@Nested` 组织分组。
- **参数化**：`@ParameterizedTest` + `@ValueSource` 一套逻辑多组数据。

## 为什么重要
JUnit 是 Java 生态单测基石，Spring/Kotlin/Android 全用它。懂生命周期与断言才能写出可靠、可读、可维护的测试。

## 常见坑
- 测试间共享可变静态/实例字段，执行顺序导致偶发失败。
- 一个测试方法里断言太多，失败难定位（应小且聚焦）。
- 用 `System.out` 代替断言"肉眼看"，CI 不报错等于没测。

## 动手自测
1. 用 JUnit 5 给一个纯函数写单测，覆盖正常值、边界、异常（`assertThrows`）。
2. 用 `@ParameterizedTest` 用 5 组数据测同一个校验逻辑。

## 面试视角
"JUnit 5 生命周期？@BeforeEach 作用？参数化测试怎么写？"——讲清实例化隔离、断言、数据驱动。

# be-test-s3 | Mockito 模拟与隔离
> 单测要"只测目标、替身依赖"，Mockito 帮你造替身。

## 心智模型
Mockito 像**剧组的替身演员**：你要测的主角（被测类）身边那些配角（依赖）不必请真人，用替身顶上、按剧本给回应（`when(...).thenReturn(...)`），这样你只验证主角演得对不对，不被配角拖慢或带偏。

## 核心知识点（锚定官方）
- **Mockito（site.mockito.org）**：`mock()`、`@Mock` + `@ExtendWith(MockitoExtension.class)`、`when().thenReturn()`、`verify()` 校验交互。
- **注入**：`@InjectMocks` 把 mock 自动注入被测对象（或手动构造）。
- **行为校验**：`verify(mock).method()` 验证"是否被正确调用"，不只校验返回值。

## 为什么重要
真实依赖（DB、第三方 HTTP）在单测里又慢又不可控。Mock 让单测快、确定、专注逻辑。它是 Java 单测的标配。

## 常见坑
- 过度 mock：连简单值对象都 mock，测试变"验证框架调用"失去意义。
- `when` 条件与真实调用不匹配，返回默认值（null）导致诡异 NPE。
- 用 mock 验证"实现细节"而非"行为契约"，重构就碎。

## 动手自测
1. 用 Mockito 测一个 Service：mock 其 Repository，验证 Service 在异常依赖下正确抛业务异常。
2. 用 `verify` 确认依赖被恰好调用一次、参数正确。

## 面试视角
"Mockito 干嘛用？verify 和 when 区别？什么时候不该 mock？"——讲清替身隔离、行为校验、适度原则。

# be-test-s4 | 测试替身：stub/mock/spy/fake
> 替身有四种，分不清会误用。

## 心智模型
测试替身像**不同性质的替补队员**：stub 是"背好答案的替补"（只回固定值）；mock 是"被盯梢的替补"（还要查它有没有被按剧本叫）；spy 是"真队员带记录仪"（真身干活但记录调用）；fake 是"轻量真替身"（如内存版 DB，逻辑真但不接生产）。

## 核心知识点（锚定官方）
- **Martin Fowler《Test Double》**：Dummy / Stub / Spy / Mock / Fake 五类。
- **stub vs mock**：stub 提供间接输入，mock 额外验证交互；现代框架常统称 mock。
- **fake vs mock**：fake 有可工作的简化实现（内存 Map 当 DB），适合集成轻测；mock 是纯模拟。

## 为什么重要
选错替身会让测试要么过松（没测到）、要么过紧（绑死实现）。理解差异才能写出"测契约而非实现"的健康测试。

## 常见坑
- 用 mock 验证私有调用，重构即碎。
- 把 fake 当生产实现误提交（fake 不保证全部语义）。
- 混淆 stub（不校验调用）与 mock（校验调用），断言预期落空。

## 动手自测
1. 手写一个 `FakeUserRepository`（内存 List），跑通 Service 集成轻测。
2. 对比同一用例用 mock 与用 fake 写的测试，体会断言点差异。

## 面试视角：能清晰区分五类替身并举例，是测试成熟度信号。

# be-test-s5 | 集成测试与测试容器
> 验证"代码 + 真实依赖"协作，用 Testcontainers 拉真实 DB。

## 心智模型
集成测试像**带真乐器的小合奏**：不再用替身，而是真把数据库/消息队列搬上来的小规模联排，确认你的代码和真实依赖"对得上拍子"。Testcontainers 就是"用 Docker 临时借一件真乐器来排练"。

## 核心知识点（锚定官方）
- **Testcontainers（testcontainers.com）**：JUnit 扩展，在测试生命周期启停 Docker 容器（Postgres/Redis/Kafka），`@Container` 声明。
- **Spring `@SpringBootTest`**：加载上下文做集成测试；可用 `testcontainers` 替换数据源。
- **数据库迁移测试**：跑 Flyway/Liquibase 迁移确认 schema 正确。

## 为什么重要
单测过了、一接真库就炸，是高频事故源。集成测试在 CI 里用真实依赖抓"SQL 错、类型错、事务错"，性价比极高。

## 常见坑
- 没 Docker 环境时 Testcontainers 起不来（CI 需装 Docker 或改用 Testcontainers Cloud）。
- 集成测试不清理数据，互相污染（用事务回滚或独立 schema）。
- 集成测试太慢被关掉，失去防护网。

## 动手自测
1. 用 Testcontainers 起 Postgres，跑一个 Repository 的真实 CRUD 测试。
2. 配置测试后自动回滚，验证多次运行结果一致。

## 面试视角
"集成测试为何用真依赖？Testcontainers 解决什么？如何保证测试隔离？"——讲清真实协作、Docker 化、数据清理。

# be-test-s6 | 契约测试
> 微服务间接口，用契约测试代替昂贵的跨服务 E2E。

## 心智模型
契约测试像**甲乙双方的盖章合同**：消费者（调用方）写下"我期望你返回这样的字段"，提供者（服务端）按合同自检"我确实满足"。双方各自 CI 验证合同，不必每次真把两个服务全链路跑起来。

## 核心知识点（锚定官方）
- **消费者驱动契约（CDC，Pact 文档）**：消费者生成契约文件，提供者用 `pact verify` 校验。
- **Spring Cloud Contract**：以 Groovy/YAML 写契约，自动生成提供者测试桩与文档。
- **价值**：把"跨服务集成"的验证成本从 E2E 下沉到双方单仓库内，早期发现问题。

## 为什么重要
微服务多了之后，靠全链路 E2E 验证接口变更既慢又易碎。契约测试在"改接口"时立刻知道谁会受影响，是微服务测试的核心实践。

## 常见坑
- 契约只测 happy path，忽略错误码/边界，生产照样炸。
- 消费者更新契约但没同步让提供者 verify，合同形同虚设。
- 把契约当 E2E 用，写满业务逻辑断言。

## 动手自测
1. 用 Pact 写一个消费者测试生成契约，再让提供者端 `verify` 通过。
2. 故意改提供者返回字段，验证契约校验失败报警。

## 面试视角
"什么是契约测试？比 E2E 好在哪？消费者驱动是什么意思？"——讲清接口契约、降本、双方自检。

# be-test-s7 | TDD 与测试驱动开发
> 先写失败的测试，再写刚好让它通过的实现。

## 心智模型
TDD 像**先立验收标准再施工**：红（写测试、必然失败）→ 绿（写最小实现让它过）→ 重构（在测试保护下整理代码）。测试不是事后补的"保险"，而是设计接口的第一道草图。

## 核心知识点（锚定官方）
- **三步循环（Kent Beck / 经典 TDD）**：Red → Green → Refactor。
- **好处**：逼出可测、低耦合的设计；测试即规格；重构有安全网。
- **适用边界**：探索性/UI 密集场景不一定先 TDD，可后补测试。

## 为什么重要
TDD 产出的代码天然可测、接口清晰，且改代码有即时反馈。即使不全流程 TDD，"测试保护下的重构"也是必备能力。

## 常见坑
- 写出永远红的测试或不写断言的测试，循环无法推进。
- 在 TDD 里过度设计（提前抽象），违背"最小实现"。
- 把 TDD 当银弹，强行用于需求极不明确的探索阶段。

## 动手自测
1. 用 TDD 实现一个字符串计算器（含负数/多分隔符规则），体会红绿重构。
2. 在已有无测试代码上，先补测试再重构，对比心理安全感。

## 面试视角
"TDD 三步？它提升什么？何时不适合？"——讲清红绿重构、设计收益、适用边界。

# be-test-s8 | 覆盖率与质量门禁
> 覆盖率不是目标，是"哪里还没被照到"的探针。

## 心智模型
覆盖率像**仓库的监控死角地图**：它告诉你哪些代码从没被测试"照"到。100% 覆盖率不等于没 bug，但 0% 覆盖率的模块一定是高危区。门禁则是"覆盖率低于阈值就不让合并"。

## 核心知识点（锚定官方）
- **JaCoCo（eclemma.github.io/jacoco）**：字节码插桩统计行/分支覆盖率，`jacoco:report`。
- **分支 vs 行覆盖**：行覆盖高不代表分支都测了（if/else 只走一边仍算覆盖）。
- **SonarQube**：聚合覆盖率+重复率+坏味道，设质量门（Quality Gate）。

## 为什么重要
覆盖率指标能防止"测试被偷偷删光"。但务必记住：它衡量"被执行的量"而非"断言的质量"。门禁应结合分支覆盖与关键路径。

## 常见坑
- 为刷覆盖率写无断言测试，数字好看实则没防护。
- 只看行覆盖忽略分支，漏掉 else 错误分支。
- 门禁设 100% 逼出大量垃圾测试，团队反弹。

## 动手自测
1. 跑 JaCoCo 看某模块行/分支覆盖率，挑一个 0 分支覆盖的方法补测试。
2. 在 CI 配质量门：分支覆盖 < 60% 则失败。

## 面试视角
"覆盖率 100% 代表无 bug 吗？行覆盖和分支覆盖区别？门禁怎么设？"——讲清度量意义、分支、务实阈值。

# be-test-s9 | 测试数据与夹具
> 可重复的测试，靠可控的测试数据。

## 心智模型
测试数据像**做菜的标准配料包**：每次下锅都得是同一份、已知结果的料（fixture），否则今天咸明天淡，测试就不稳定。复杂的料用"工厂/建造者"按需组装，而不是到处复制粘贴大段 JSON。

## 核心知识点（锚定官方）
- **Fixture**：固定输入/预期输出，放在 `@BeforeEach` 或独立 fixture 文件，保证可重复。
- **Test Data Builder / Object Mother**：用建造者模式按需构造领域对象，避免构造函数膨胀导致的测试噪音。
- **数据隔离**：每个测试用独立数据集或事务回滚，避免相互污染（见 s5）。

## 为什么重要
测试不稳定（flaky）的头号原因是共享可变数据。良好的 fixture/建造者让测试"自给自足、可重复、可读"。

## 常见坑
- 测试直接连生产库或共享库，数据被别人改导致偶失败。
- 复制大段实体构造代码，一改字段全崩。
- fixture 含多余字段，掩盖了"到底哪些输入影响结果"。

## 动手自测
1. 用建造者模式重构一段重复的用户对象构造，让测试只写明关心的字段。
2. 把共享测试数据改为每测试独立 setup，验证可重复运行。

## 面试视角
"测试不稳定常见原因？Fixture/Builder 解决什么？如何隔离数据？"——讲清数据污染、构造噪音、独立 setup。
