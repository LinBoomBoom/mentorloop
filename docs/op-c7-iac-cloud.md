# op-c7-s1 | IaC 理念与价值
> 基础设施不该靠"登录控制台点点点"，该像代码一样可版本化、可评审、可回滚。

## 心智模型
IaC 像**用施工图代替口头指挥盖楼**：过去靠工程师爬上控制台手动点按钮（容易漏、不可复现、离职即失传）；现在把"要几台机器、什么网络、什么存储"写成代码，谁改了哪一行有 git 记录、能评审、能一键重建一模一样的环境。

## 核心知识点（锚定官方）
- **IaC 定义（HashiCorp / CNCF 共识）**：用声明式/命令式代码管理基础设施，核心收益是**可复现、版本化、自动化**。
- **声明式 vs 命令式**：Terraform/Pulumi 声明"终态"，系统算出差异并执行；Ansible 偏过程式。
- **与配置管理区别**：IaC 管"资源存在与否"（VM/网络），配置管理（Ansible）管"资源内部状态"（装什么软件）。

## 为什么重要
手工运维在规模化后必然失控（环境漂移、雪崩式误操作）。IaC 是云原生运维的基石，也是 SRE"消除重复手工"的核心实践（见 op-c5）。

## 常见坑
- 控制台手动改了资源，Terraform 状态与实际漂移，下次 apply 冲突。
- 把密钥写进 IaC 代码提交（应走变量/密钥管理）。
- 认为 IaC 只是"便利"，忽视它带来的评审与回滚安全网。

## 动手自测
1. 用 Terraform 写一个安全组+一台 VM 的声明，apply 后 destroy，验证环境可重建。
2. 故意在控制台改资源，再 `terraform plan` 观察检测到的漂移。

## 面试视角
"IaC 解决什么？声明式与命令式区别？状态和实际漂移怎么处理？"——讲清可复现、终态声明、漂移检测。

# op-c7-s2 | Terraform 核心：HCL 与生命周期
> Terraform 用 HCL 声明终态，plan 预览差异、apply 落地。

## 心智模型
Terraform 像**一个会做"差异对比"的施工队**：你提交一张终态图纸（.tf），它先 `plan` 告诉你"会新建什么、改什么、删什么"（预览，不操作），你点头后 `apply` 才真去施工。每一步都可预期、可撤销（destroy）。

## 核心知识点（锚定官方）
- **HCL 基础（Terraform 文档）**：`provider`（云厂商插件）、`resource`（资源）、`variable`（入参）、`output`（出参）、`data`（查询已有资源）。
- **工作流**：`init`（装 provider）→ `plan`（预览差异）→ `apply`（执行）→ `destroy`（销毁）。
- **provider 版本锁定**：`required_providers` 固定版本，避免意外升级破坏。

## 为什么重要
Terraform 是事实标准 IaC 工具，跨 AWS/Azure/GCP/阿里云通用。懂其生命周期才能安全地管理大规模云资源。

## 常见坑
- 不先 `plan` 直接 `apply`，误删生产资源。
- provider 版本未锁，CI 拉到新版本行为变化。
- `apply` 中途失败，部分资源已建，需理解"部分状态"再补救。

## 动手自测
1. 写一份含 variable 的 tf，用 `terraform plan -var` 预览不同参数下的差异。
2. `apply` 中途 Ctrl-C，观察状态并安全继续/回滚。

## 面试视角
"Terraform 工作流？plan 作用？为什么锁 provider 版本？"——讲清 init/plan/apply、差异预览、可复现。

# op-c7-s3 | Terraform 状态与后端
> 状态文件是 Terraform 的"记忆"，必须安全存放与加锁。

## 心智模型
state 文件像**施工队的工程进度本**：记着"哪些资源已建、云上 ID 是什么、当前实际参数"。这本子若只放本地，多人协作会互相覆盖；必须锁进"公共保险柜"（remote backend）并加锁，防止两人同时施工打架。

## 核心知识点（锚定官方）
- **state 文件（Terraform）**：`terraform.tfstate` 映射资源到云 ID；`terraform state` 命令可查看/迁移。
- **remote backend**：如 `s3`+`dynamodb` 锁、`terraform cloud`、Consul，实现共享与并发锁。
- **敏感数据**：state 默认明文存资源属性（可能含密码），需加密后端 + 最小权限。

## 为什么重要
state 损坏或并发写会导致资源"失联"或重复创建。生产必须用远程后端+锁+加密，否则协作即灾难。

## 常见坑
- state 存本地随开发者离职丢失，资源变"孤儿"。
- 无锁时两人同时 apply，资源被双重创建或冲突。
- state 含明文密钥提交到 git。

## 动手自测
1. 配置 s3+dynamodb 后端，两人（或两次会话）同时 plan/apply 验证锁生效。
2. 用 `terraform state list/mv` 修复一个被误改名导致漂移的资源。

## 面试视角
"state 是什么？为什么用 remote backend？并发锁怎么实现？"——讲清映射记忆、共享安全、DynamoDB 锁。

# op-c7-s4 | 模块化与可复用
> 把常用架构打成"模块"，像调函数一样复用，避免复制粘贴。

## 心智模型
Terraform 模块像**乐高说明书套装**：把"一套标准 VPC+子网+安全组"打包成一个模块，以后谁要建环境，只要传几个参数（区域、CIDR）就能复用，而不是每次从零写几十行、还容易写错。

## 核心知识点（锚定官方）
- **module（Terraform）**：`module "network" { source="..." }`，source 可为本地路径、Git、Registry；输入 `variables`、输出 `outputs`。
- **版本化模块**：Registry/私有源打 version，团队复用并受控升级。
- **封装原则**：对内暴露必要参数，隐藏实现细节，单一职责。

## 为什么重要
没有模块化，IaC 代码会膨胀成难以维护的"意大利面"，且各环境配置不一致。模块是规模化 IaC 的关键。

## 常见坑
- 把模块写成"万能大杂烩"，参数爆炸难用。
- 模块不版本化，一处改全局受影响。
- 在模块里硬编码环境差异，丧失复用性。

## 动手自测
1. 把"VPC+子网"抽成 module，用不同 variables 建 dev/prod 两套网络。
2. 把模块推到私有 Git，用 `source = git::...` 引用并指定 ref 版本。

## 面试视角
"Terraform 模块干嘛用？怎么版本化？封装原则？"——讲清复用、Registry、单一职责。

# op-c7-s5 | 公有云计算与网络
> 云上"机器+网络"是 IaC 最高频的资源，VPC 是隔离边界。

## 心智模型
云网络像**在云厂商大楼里租一层并自己隔房间**：VPC 是你租下的私有楼层（逻辑隔离），子网是房间（分公网/私网），安全组是门禁规则（谁能进哪扇门），路由表是走廊指向。计算实例放进对应房间。

## 核心知识点（锚定官方）
- **VPC/子网（AWS VPC / 阿里云 VPC）**：CIDR 划分、公有/私有子网、路由表、NAT 网关（私网出公网）。
- **安全组 vs NACL**：安全组是实例级有状态防火墙，NACL 是子网级无状态。
- **计算实例**：EC2 / ECS（阿里云）/ CVM，配合弹性伸缩（ASG）按负载扩缩。

## 为什么重要
几乎所有云上系统都建立在"计算+网络"之上。理解 VPC 模型才能设计安全、可扩展、成本合理的云架构，也是排障（连不通）的基础。

## 常见坑
- 私网实例无 NAT 却要访问公网，出不去。
- 安全组放 `0.0.0.0/0` 全开，暴露风险。
- CIDR 规划混乱，子网无法互通或地址耗尽。

## 动手自测
1. 用 Terraform 建一个 VPC：1 公网子网（放 NAT）+1 私网子网（放应用）。
2. 配安全组只允许 80/443 入、应用仅经 NAT 出公网，验证连通性。

## 面试视角
"VPC 是什么？安全组和 NACL 区别？NAT 干嘛用？"——讲清隔离、有状态防火墙、私网出网。

# op-c7-s6 | 对象存储与 CDN
> 海量非结构化文件（图片/视频/备份）不该放块存储，用对象存储+CDN。

## 心智模型
对象存储像**无限大的自助仓储柜（S3/OSS）**：你按 key 存任意文件，按量付费、自动多副本。CDN 则是**在各地前置的快递代收点**，把热门文件缓存到离用户近的地方，访问秒开、回源少。

## 核心知识点（锚定官方）
- **对象存储（AWS S3 / 阿里云 OSS）**：bucket + object key；存储类别（标准/低频/归档）、生命周期规则自动转储/过期。
- **访问安全**：IAM 策略、预签名 URL（临时下载）、阻断公读。
- **CDN（CloudFront / CDN）**：边缘节点缓存，回源策略、缓存刷新、HTTPS 加速。

## 为什么重要
静态资源、用户上传、日志归档、备份全都走对象存储。配好 CDN 与生命周期能大幅降成本、提体验，是云成本治理重点（联动 op-c5 FinOps）。

## 常见坑
- bucket 公读导致数据泄露（应最小权限+预签名）。
- 不做生命周期规则，冷数据长期占标准存储烧钱。
- CDN 缓存策略错，用户总拿到旧文件（缓存击穿/未刷新）。

## 动手自测
1. 建 OSS bucket 上传图片，用预签名 URL 临时分享，验证无公读权限。
2. 配 CDN 加速并设缓存 TTL，观察回源流量下降。

## 面试视角
"对象存储适合什么？预签名 URL 干嘛？CDN 怎么降成本？"——讲清非结构化、临时授权、边缘缓存。

# op-c7-s7 | Serverless 与函数计算
> 不想管服务器？函数计算按调用付费、自动伸缩。

## 心智模型
Serverless 函数像**随叫随到的临时工**：你只交一段代码（如"处理一次上传"），云厂商在有事件触发时拉起运行、跑完即回收，你只为"实际运行的毫秒"付费，无需养着一台 24 小时开机的机器。

## 核心知识点（锚定官方）
- **函数计算（AWS Lambda / 阿里云 FC）**：事件驱动（HTTP/对象存储/队列触发）、按量计费、冷启动（首次拉起慢）。
- **适用边界**：短任务、突发/低频、事件驱动；长驻服务/有状态仍适合容器/VM。
- **配套**：API Gateway 暴露 HTTP、Step Functions 编排多函数。

## 为什么重要
对低频/峰值明显的任务（图片处理、Webhook、定时任务），Serverless 大幅降本并免运维。理解它才能在现代云架构里做对"何时用函数"。

## 常见坑
- 把长耗时/有状态服务塞进函数，受 15 分钟上限与冷启动拖累。
- 函数里建数据库连接不回收，并发起来连接数爆。
- 忽视冷启动，同步链路首请求明显变慢。

## 动手自测
1. 写一个 Lambda/FC 函数，由对象存储"上传事件"触发做图片压缩。
2. 压测观察冷启动延迟，并用预留并发缓解。

## 面试视角
"Serverless 适合什么？冷启动是什么？和容器怎么选？"——讲清事件驱动、按量、边界。

# op-c7-s8 | GitOps 与 IaC 的 CI/CD
> 把 IaC 也接进流水线，变更经 PR 评审、自动 plan/apply。

## 心智模型
GitOps 像**把"施工图纸的修改"也走公司审批流**：改基础设施不再私自执行，而是提一个 PR，CI 自动 `plan` 把差异贴到 PR 上供评审，合并后机器人（如 Atlantis）自动 `apply`。git 成为环境的事实真相源。

## 核心知识点（锚定官方）
- **GitOps 理念（CNCF / Weaveworks）**：git 为唯一事实源，声明式系统自动向 git 状态收敛；`kubectl`/手动改会被自动纠正。
- **Atlantis / Terraform Cloud**：PR 评论触发 plan/apply，锁环境、留审计。
- **安全**：最小权限的 CI 凭据、plan 输出人工 review 后才 apply。

## 为什么重要
IaC 若仍靠个人本地 `apply`，就失去了评审与审计价值。GitOps 把基础设施变更纳入和代码同级的工程纪律（联动 op-c4 CI/CD）。

## 常见坑
- plan 输出不评审直接 auto-apply，误删资源进生产。
- CI 凭据权限过大，PR 被篡改即获云管理员。
- git 状态与实际漂移后，自动化"纠正"误删人工合法改动。

## 动手自测
1. 配置 Atlantis，对 IaC 仓库提 PR，验证自动 plan 评论与合并后 apply。
2. 故意在 PR 里加 `destroy`，验证需人工审批才放行。

## 面试视角
"GitOps 是什么？和一般 CI/CD 区别？Atlantis 干嘛？"——讲清 git 真相源、PR 驱动、自动收敛。

# op-c7-s9 | 多环境与状态隔离
> dev/staging/prod 必须隔离，绝不让测试碰生产状态。

## 心智模型
多环境隔离像**给开发、预发、生产三套完全独立的施工队与图纸柜**：每套有自己的 state 保险柜（backend）、自己的云账号/项目、自己的变量。这样在开发环境随便拆改，绝不会误触生产的"工程进度本"。

## 核心知识点（锚定官方）
- **workspace（Terraform）**：`terraform workspace` 在同一配置下切换 dev/prod 状态（同一 backend 内隔离）。
- **backend per env**：更彻底——不同环境用不同 backend/云账号，物理隔离，防串。
- **变量分层**：`*.tfvars` 按环境注入，代码复用、配置分离。

## 为什么重要
环境与环境的事故隔离是运维安全底线。混用状态/账号，一次测试误操作就能干掉生产。清晰的隔离策略是合规与稳定的前提。

## 常见坑
- dev/prod 共用一个 state backend，误 apply 到生产。
- 用 workspace 但变量未分离，环境配置串味。
- 测试账号有生产网络连通，越权风险。

## 动手自测
1. 用 workspace 或独立 backend 建立 dev/prod 两套隔离环境。
2. 验证在 dev workspace apply 不会影响 prod 的 state 与资源。

## 面试视角
"多环境怎么隔离？workspace vs 独立 backend？为什么不能共用 state？"——讲清状态隔离、账号隔离、防误触。
