# MentorLoop 内容地基补全方案（第 0 阶段）

> 状态：Draft v1 · 作者：产品协同（前端/后端/运维/内容质量专家联合）· 日期：2026-08-01
> 配套文档：`docs/vip-implementation-plan.md`（开发实现计划）
> 定位：**本阶段必须优先于 T1–T12 的价值线（T3/T4/T5）完成**，是付费权益能"言之有物"的前置地基。

---

## 0. 核心原则（不可妥协）

1. **信源权威、可溯源**：所有知识点、答案、判定标准，必须来自官方文档/规范/手册，标注来源 URL。禁止 AI 凭空编造、禁止"大概如此"的模糊表述。
2. **不批量 AI 生成**：AI 仅用于「采集编排、错别字修正、结构化排版、互链建议」，**不负责产出事实性内容**。事实内容由专家/编辑基于官方信源撰写并签名。
3. **按领域完整覆盖，数量由内容决定**：前端 15 章/84 点只是它"恰好需要的量"，**不是配额**。后端、运维该写多少就写多少——可多于或少于 15 章，以"官方信源覆盖完整、无重大遗漏"为唯一验收标准，绝不为凑数对等而注水或削足适履。参照前端的是**单点深度**（每章/每点该讲透的程度），而非章节总数。
4. **入库即合规**：内容写入 `data/seed-content.json` 时，严格复用现有 schema（`chapters → sections[content]`、`interview.{hot,special}`、`examSets.{choices,written}`），不另起字段。

### 内容价值原则（为何"引用官方"≠"抄官方"）

官方文档是 **reference（参考层）**：权威、精确、全面，但按"维护者视角"组织——默认读者已懂上下文、先抛形式定义、不教学习顺序、不 foreground 常见坑、少有"和邻居怎么区分""何时该用"的对比，更没有自测与面试视角。用户直接看官方，常陷入"每个字都认识连起来不懂""看完不知从哪学起""记不住、分不清、用不上"。

我们的内容必须是 **learning layer（学习层）**，架在官方事实之上、价值由我们自研：

- **事实锚定官方（真相底座）**：定义、机制、API 边界、版本差异，一律以官方信源为准、标注 URL、不改写不臆造。
- **价值由我们撰写（学习层）**：每个知识点至少包含——①一句话心智模型 / 人话类比；②为什么重要、什么时候会用到；③常见坑 / 踩雷警示（官方不 foreground 但实战必踩）；④与"邻居"的对比 / 决策表；⑤动手自测（预测输出、合上想 10 秒）；⑥面试 / 实战视角。
- **两套语言并存**：官方引用做"权威背书"，人话解释做"理解入口"——用户先懂、再溯源，二者不矛盾。

> 验收从"格式对不对"升级为"有没有学习价值"：用户能否 30 秒建立心智模型、能否分清易混概念、能否动手验证、能否关联到面试 / 实战。

**模板 v1 状态**：已于 2026-08-01 经用户评审定稿，完整示范见 `docs/pilot-sample.md`（三方向各 2 知识点）。后续逐章按此模板落笔、入库。

**可选 v2 增强（产品视角建议，待定）**：v1 模板六维度全开，对"边缘点"可能偏重。建议补充：
- **分级深度**：核心点六维度全开、深写；边缘点只保留「心智模型 + 官方定义 + 1 个坑」，并给每点打「难度 / 优先级」标签，便于 T5 学习路径排序，避免模板变八股、信息过载。
- **连接性（知识图谱）**：每点增「前置知识 / 关联点 / 下一步」互链，让知识树从平铺列表变成有向学习图，直接喂给 T5 学习路径定制。
- **版本边界 + 图示触发**：官方常跨版本，需显式版本标签（Vue2/3、MySQL 5.7/8、JDK 差异）；并规定"何时用图代替字"（B-tree 结构、事件循环、K8s 拓扑等——图比字省数倍理解成本）。

## 2. 目标规模（以知识树为母本，量由覆盖派生，非配额）

| 资产 | 后端 | 运维 | 前端 |
|---|---|---|---|
| 知识树 | 按官方信源**完整重建/补全** | 按官方信源**完整重建/补全** | 按官方信源**重新做过内容基建、完善体系**（非"已 15 章即完成"） |
| 知识点深度 | 单点讲透、含官方定义+示例+来源 | 同左 | 同左 |
| 面试题 | **由知识树规模派生**：每个核心知识点/主题域派生若干题（概念+场景+必要时手写/设计），不做固定条数配额 | 同左 | 同左 |
| 考卷 | **由知识树覆盖派生**：按主题域抽样组卷，套数与题量以"覆盖主要知识点+典型场景"为准，不预设 3–5 套 | 同左 | 同左 |

> 三方向均参与内容基建，前端亦需重建完善，不存在"前端已达标"的例外。

## 4. 任务拆解（C1/C2/C3）

### C1 · 知识树补全（P0 头部）
- **C1-B**：后端当前 5 章/11 点/0.8 万字 → 按官方信源**完整覆盖后端领域**，章数由内容决定（可多于或少于 15），单点深度对齐前端。下列为"主题域清单"而非"必须恰好 15 章"的配额：
  - 主题域：编程语言与并发 → JVM 与性能调优 → MySQL → Redis → Spring 生态 → 微服务/分布式 → 消息队列 → 系统设计/高并发 → 计算机网络 → Web 安全 → 算法与数据结构 → 设计模式 → 测试 → 工程实践。覆盖齐全即可，**不强制章数=15**。
- **C1-D**：运维当前 5 章/11 点/0.7 万字 → 按官方信源**完整覆盖运维/DevOps 领域**，章数同样由内容决定。主题域清单：
  - 主题域：Linux 内核与 Shell → 网络与 DNS → Nginx → 数据库运维 → Docker → Kubernetes → CI/CD → 监控告警 → 日志与链路追踪 → SRE/稳定性 → 安全加固 → 成本治理 → 故障演练 → 多云/混合云 → 工程实践。覆盖齐全即可。
- **C1-F**：前端**重新做过内容基建、完善知识树体系**——不因为"已有 15 章/84 点"就视为完成，须按官方信源逐项复核覆盖完整度与单点深度，补全遗漏主题域（如前端工程化、Web 安全纵深、现代框架原理等），达到与后端/运维同等的"完整重建"标准。
- **验收（双图层）**：每知识点 `content` 须同时具备——
  - **真相底座**：官方定义（可引用原文）/ 机制 / 可运行代码示例 / 来源 URL，事实不改写、不臆造；
  - **学习层（价值所在）**：至少含「一句话心智模型 / 人话类比」「为什么重要 / 何时用」「常见坑 / 踩雷警示」「与邻居对比 / 决策表」「动手自测」「面试 / 实战视角」中的多数维度。
  - 覆盖完整无重大遗漏；专家双签。**验收看"覆盖完整度 + 学习价值"，不看章数是否等于 15，也不看"格式像不像官方"**。

### C2 · 面试题库（由知识树派生，非固定配额）
- **派生规则**：面试题是知识树的"提问侧映射"——对每个核心知识点/主题域，派生若干题，类型随知识点性质而定：
  - 概念题（是什么/为什么）→ 锚定官方定义；
  - 场景题（线上问题如何排查）→ 锚定官方机制/最佳实践；
  - 手写/设计题（适用处）→ 给出"考察点+官方依据+参考实现思路"。
  - 不预设"每方向 100 条"的 KPI，题库规模 = 知识树广度 × 单点可考维度，**有多少知识点就派生多少题**，无上限、不注水。
- 三方向（含前端）均按此规则构建；答案须附官方来源 URL，标注版本边界（如 Vue2/3 响应式差异）。
- **验收**：随机抽查 10% 题目，答案事实与官方信源一致、无臆测、无过期 API；题目与知识树知识点可追溯对应。

### C3 · 考卷扩充（由知识树覆盖派生，与 T3 衔接）
- **派生规则**：考卷是知识树的"抽样组卷"——按主题域在知识树上均匀抽样，套数与题量以"覆盖主要知识点 + 典型场景"为准，**不预设 3–5 套配额**：
  - 免费层：依据知识树规模组若干套综合/专项卷；
  - VIP 层：本阶段产出内容并预置 `vipOnly:true` 草案，由 T3 负责标记与门禁（深度/专项卷可作为 VIP 差异化内容）。
- 出题从 C1/C2 真实内容抽取，答案键(answer key)锚定官方信源。
- **验收**：套卷知识点覆盖率合理（随知识树规模浮动）；判分标准明确；VIP 与免费卷难度/专项梯度合理。

## 5. 工作流程（采集 → 结构化 → 校验 → 入库）

### 5.1 单模块标准工序（每个章节/主题域都走一遍）
```
① 采集   脚本从官方信源批量抓取正文（仅抓取、不生成）；专家按信源摘录，记录来源URL（严禁改写事实）
② 落笔   该方向专家基于官方信源撰写知识点：事实层（定义/机制/代码/来源）锚定官方，学习层（心智模型/为何重要/常见坑/对比/自测/面试视角）由专家自研，两套语言并存
③ 结构化 按现有 schema 排版：知识树→chapters.sections.content；面试题→interview.{hot,special}；考卷→examSets
④ 校验   内容质量专家 + 方向专家双签：事实一致性、版本边界、代码示例可运行、来源齐全
⑤ 入库   写入 data/seed-content.json；跑 reset.mjs 校验可加载、无 schema 漂移
```

### 5.2 分批执行节奏（按模块，非一次性补全）
> 用户明确要求**按模块分批、逐模块可审**，避免一次性大批量产出导致质量失控/糊弄。

- **Step 0 试点**：每个方向各挑 **1 个代表性章节** 作为样本（前端"JavaScript 语言核心"、后端"MySQL"、运维"Linux 与 Shell"），完整走 5.1 工序，重点验证**「学习层」是否成立**——用户能否 30 秒建立心智模型、能否分清易混概念、能否动手验证、是否比直接看官方更有用。**评审焦点从"格式对不对"转为"值不值得看"**。
- **Step 1 评审通过后再批量**：试点获用户认可后，按"主题域清单"**逐章推进**，每完成若干章即同步一次进度、保留抽查权利。
- **Step 2 题/卷派生后置**：面试题(C2)、考卷(C3) 在对应方向知识树达到一定覆盖后再派生，不抢跑。
- 任何模块发现"官方信源无明确答案"的争议点，**先探讨或回到权威官方找答案，不臆测、不占位**。

### 5.3 AI 辅助边界（明确禁止越界）
- ✅ 允许：脚本从官网批量抓取正文、Markdown 排版、错别字修正、知识点互链建议、进度看板生成。
- ❌ 禁止：生成事实性答案、补全"不确定"的内容、用训练记忆替代官方信源、一次性铺量绕过逐模块评审。

- T4 的 LLM 提示词应以 C2 真实题库为语料锚，提升出题/评分可信度。
