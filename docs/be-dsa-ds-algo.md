## 1. 复杂度分析与大 O 记号

> 引导：先建立复杂度的直觉：它衡量的是数据量增长时耗时/内存的膨胀趋势，而非单次绝对速度。

## 心智模型
复杂度分析不是"这段代码跑多快"，而是"当数据量 n 翻 10 倍、翻 100 倍时，耗时/内存按什么比例膨胀"。把算法想成一台机器：大 O 记的是这台机器的"弹性"——n 增大时它是纹丝不动(O(1))、匀速变慢(O(n))，还是爆炸式增长(O(2ⁿ))。面试官考它，是因为真实系统数据量会涨，选错复杂度就是选错架构。

## 核心知识点（锚定官方）
渐近记号采用《算法导论》(Cormen 等, CLRS)的标准定义：
- **O (大 O / 渐近上界)**：f(n)=O(g(n)) 表示存在常数 c、n₀，使对所有 n≥n₀ 有 0≤f(n)≤c·g(n)。描述"最坏不会比这更慢"。
- **Ω (大 Omega / 下界)**：描述"至少要多快"。
- **Θ (大 Theta / 紧界)**：上下界一致，精确刻画增长阶。
常见量级（由快到慢）：O(1) < O(log n) < O(n) < O(n log n) < O(n²) < O(n³) < O(2ⁿ) < O(n!)。
- **均摊复杂度**：一系列操作中单次的平均代价（如动态数组扩容，虽偶尔 O(n) 但均摊 O(1)）。
- **主定理(Master Theorem)**：用于分治递归 T(n)=aT(n/b)+f(n) 的快速求解，是分析归并/快排/树操作复杂度的标准工具。

## 为什么重要
1. 系统设计时，选 O(n²) 的接口在数据量 10 万时就崩，O(n log n) 才能扛住。
2. 排查慢查询、慢接口，第一步就是定位复杂度瓶颈，而不是盲目加机器。
3. 面试中"这个解法能优化吗"的本质，就是寻找更低的复杂度边界。

## 常见坑
- **把常数项当小事**：O(n) 和 O(1000n) 同阶，但常数差 1000 倍时在小数据量下后者更慢——复杂度看趋势，工程看实测。
- **混淆最坏/均摊**：HashMap get 是 O(1) 均摊，但极端哈希冲突时退化；不能当成"永远 O(1)"。
- **递归不看栈深**：O(log n) 的递归若每层开销大，仍可能栈溢出（如深递归未尾优化）。
- **忘记空间复杂度**：时间优化了，却开了 O(n²) 的二维数组把内存打爆。

## 动手自测
1. 写出二分查找、归并排序、两层嵌套循环、递归斐波那契的复杂度，并指出哪几个含隐藏的 O(n) 空间。
2. 主定理练手：T(n)=2T(n/2)+O(n)（归并）、T(n)=2T(n/2)+O(1)（二分查找树高）、T(n)=T(n-1)+O(1)（线性递归）各是什么阶？
3. 用 JMH 或简单计时，验证"在 n=10⁵ 时 O(n²) 比 O(n log n) 慢几个数量级"。

## 面试视角
高频问法："这个算法复杂度多少？能优化到多少？""为什么快排平均 O(n log n) 而最坏 O(n²)？""master theorem 怎么用？"准备一句万能收尾："复杂度分析要同时看时间和空间、最坏和均摊，真实选型还要结合数据规模和常数因子实测。"

## 2. 数组与动态数组(ArrayList)

> 引导：理解连续内存带来的 O(1) 随机访问，以及扩容的均摊成本与工程取舍。

## 心智模型
数组是一排连号的储物柜：柜子紧挨着，凭编号（下标）一秒取到(O(1))；但要在中间插一个新柜，得把后面所有柜子往后挪(O(n))。动态数组(Java 的 ArrayList)就是"柜子不够了就换一排更大的"，所以它能自动扩容，但扩容瞬间有成本。

## 核心知识点（锚定官方）
依据 OpenJDK Java 17 `ArrayList` 官方文档：
- 实现：`Resizable-array implementation of the List interface`，底层是可变长的内部数组。
- 随机访问：实现 `RandomAccess` 接口；文档明确 `size`、`isEmpty`、`get`、`set`、`iterator`、`listIterator` 均为 **constant time (O(1))**。
- 默认容量：无参构造 `ArrayList()` 为 **initial capacity of ten**。
- 线程安全：文档警示 `this implementation is not synchronized`，并发修改需外部同步（如 `Collections.synchronizedList`）。
- 扩容：Javadoc 仅说"capacity grows automatically"，未规定倍数；但 OpenJDK 源码 `grow()` 实现为 `oldCapacity + (oldCapacity >> 1)`，即**约 1.5 倍**增长，均摊插入为 O(1)。
- 与 `LinkedList` 区别：后者非 `RandomAccess`，随机访问 O(n)。

## 为什么重要
1. 90% 的业务集合用 ArrayList，理解扩容能避免频繁扩容导致的性能抖动（预分配 `new ArrayList<>(expectedSize)`）。
2. 随机访问 vs 插入删除的权衡，直接决定选 ArrayList 还是 LinkedList。
3. 非线程安全是并发 Bug 高发点（详见常见坑）。

## 常见坑
- **在循环里频繁 add 到未预分配的小 ArrayList**：反复扩容拷贝，复杂度从均摊 O(1) 退化成接近 O(n²)。
- **用 ArrayList 做队列/栈**：头部插入删除 O(n)，应改用 `ArrayDeque`。
- **多线程共享未同步**：一个线程 add、另一个遍历会抛 `ConcurrentModificationException` 或数据错乱。
- **下标越界**：`get(index)` 越界抛 `IndexOutOfBoundsException`。

## 动手自测
1. 对比 `new ArrayList<>()` 与 `new ArrayList<>(10000)` 插入 1 万条的时间差。
2. 读 OpenJDK `ArrayList.grow()` 源码，确认扩容倍数，并解释"为什么是 1.5 而非 2 倍"（空间浪费 vs 拷贝频率的折中）。
3. 用 `Collections.synchronizedList` 包装后，在多线程下验证不再抛异常。

## 面试视角
高频："ArrayList 和 LinkedList 区别？""扩容机制？为什么默认 10？""线程安全吗？"收尾点："默认容量是历史约定+经验值；扩容倍数 1.5 是空间与拷贝成本的权衡；高并发场景应换 `CopyOnWriteArrayList` 或并发容器。"

## 3. 链表(单向/双向/循环)

> 引导：掌握指针操作的命脉，看清链表与数组的取舍，以及 LRU 这类经典落点。

## 心智模型
链表像 treasure hunt 的线索链：每个节点只存"我是谁 + 下一个线索在哪"。好处是插入/删除只改指针(O(1))；坏处是"找第 100 个"得从头数(O(n))。双向链表还额外记"上一个是谁"，能往前走。

## 核心知识点（锚定官方）
- 结构：节点(Node)含数据域与指针域(单向指 next，双向额外含 prev)。
- Java 视角：`LinkedList` 实现 `List` 与 `Deque`，是**双向链表**；注意它**没有实现 `RandomAccess`**，随机访问 `get(i)` 为 O(n)（需从头/尾遍历到 i）。
- 环形链表：尾节点 next 指向头，常用于轮询/令牌环。
- 经典应用：**LRU 缓存**用"哈希表 + 双向链表"，使查找 O(1)、淘汰最久未用 O(1)。
- 与数组对比：链表插入删除 O(1)（已知前驱）、内存不连续、无随机访问；数组反之。

## 为什么重要
1. LRU 缓存、邻接表、内存池都依赖链表，是底层数据结构基石。
2. 链表题是面试手撕重灾区，考察指针操作与边界思维。
3. 理解它能避免"该用链表却用数组导致 O(n) 插入"的反模式。

## 常见坑
- **指针丢失/内存泄漏**：删除节点时先断后链还是先存后继，顺序错就丢引用（如 `node.next = node.next.next` 前要先留 `next`）。
- **双向链表忘改 prev**：导致链表断裂、遍历错位。
- **误以为 LinkedList 随机访问快**：它非 RandomAccess，`get(i)` 是 O(n)，大量随机访问场景应换 ArrayList。
- **环检测**：面试常考"判断链表是否有环"(快慢指针 Floyd)，手写易错。

## 动手自测
1. 纯手写单向链表：头插、尾插、按值删除、反转（迭代+递归两种）。
2. 实现 LRU Cache（HashMap + 双向链表，或 LinkedHashMap 子类）。
3. 用快慢指针写"链表求中点"和"检测环并返回入环点"。

## 面试视角
高频："反转链表""合并两个有序链表""删除倒数第 k 个""检测环"。收尾："链表题的命脉是画图、先存后继再改指针、处理头尾空指针边界；工程上 LRU 是最经典落点。"

## 4. 栈与队列(含 Deque 与阻塞队列)

> 引导：用 LIFO/FIFO 模型理解函数栈、BFS、缓冲与并发生产者-消费者。

## 心智模型
栈像一摞盘子：只能从最上面拿/放（后进先出 LIFO）——函数调用、Undo、括号匹配都靠它。队列像排队买票：先来先服务（先进先出 FIFO）——BFS、消息缓冲、限流都靠它。双端队列(Deque)两边都能进出，最灵活。

## 核心知识点（锚定官方）
- 栈(LIFO)：典型操作 push/pop/peek。Java 中 **`Stack` 类已过时**（被 `Vector` 同步、设计陈旧），官方推荐用 **`ArrayDeque`** 当栈用（`Deque` 接口）。
- 队列(FIFO)：`Queue` 接口，常用 `LinkedList`/`ArrayDeque` 实现。
- 双端队列：`Deque` 接口，`ArrayDeque` 基于可增长循环数组，无容量限制、非线程安全、禁止 null。
- 并发队列：`java.util.concurrent.BlockingQueue`（如 `ArrayBlockingQueue`、`LinkedBlockingQueue`、`PriorityBlockingQueue`）提供阻塞的 `put/take`，是生产者-消费者模型的核心。
- 优先级队列：`PriorityQueue` 基于堆，出队按优先级（默认最小堆）。
- 衍生算法：**单调栈**（找下一个更大/更小元素）、**单调队列**（滑动窗口最大值）。

## 为什么重要
1. 函数调用栈、表达式求值、DFS 本质都是栈；BFS、缓冲、限流本质都是队列。
2. 并发场景下 BlockingQueue 是解耦生产者与消费者的标准件。
3. 单调栈/队列是中等算法题的"降维"利器。

## 常见坑
- **继续用 `Stack` 类**：同步开销且无必要，官方建议 `ArrayDeque`。
- **`PriorityQueue` 不是有序集合**：只有堆顶是极值，整体遍历不保证有序，需 `poll` 依次取出。
- **阻塞队列在单线程用错**：`put` 在无界队列不阻塞，但有界队列会阻塞线程，需配合线程池。
- **`ArrayDeque` 存 null 抛异常**：它明确禁止 null 元素。

## 动手自测
1. 用 ArrayDeque 实现括号匹配校验、用两个栈模拟队列。
2. 用 BlockingQueue 写生产者-消费者（一个线程生产、一个消费）。
3. 单调栈练手：LeetCode 739 每日温度（下一个更暖的一天）；单调队列：滑动窗口最大值。

## 面试视角
高频："用栈实现队列""括号匹配""最小栈""阻塞队列怎么用？"收尾："现代 Java 用 ArrayDeque 替代 Stack；并发用 BlockingQueue；单调栈/队列是把 O(n²) 降到 O(n) 的关键技巧。"

## 5. 哈希表(HashMap 原理)

> 引导：吃透 O(1) 背后的哈希+桶+冲突处理，以及 JDK8 链表转红黑树与并发安全。

## 心智模型
哈希表像快递柜：你存东西时系统用"名字"算出一个柜子编号（哈希），取的时候同样算编号直奔那个柜子，所以理想情况下拿取都是一瞬间(O(1))。冲突就像两个包裹被算到同一个柜子——得有规则处理（拉链挂一串，或换柜子）。

## 核心知识点（锚定官方）
依据 OpenJDK Java 17 `HashMap` 官方文档与 JDK8 源码：
- 性能：文档明确 `get`/`put` 提供 **constant-time performance (O(1))**，前提是哈希函数把元素充分分散到桶(buckets)中。
- 两个参数：初始容量(default **16**) 与 负载因子(default **0.75**)；"0.75 在时间和空间成本间提供了好的权衡"。
- 允许：permit `null` 键和 `null` 值。
- 线程安全：文档警示 `not synchronized`，并发需 `ConcurrentHashMap` 或 `Collections.synchronizedMap`。
- JDK8 源码级实现（Javadoc 未写，属源码常量）：桶是**链表**，当单个桶节点数 ≥ **TREEIFY_THRESHOLD = 8** 且表容量 ≥ 64 时转为**红黑树**；当节点数 ≤ **UNTREEIFY_THRESHOLD = 6** 时退化为链表；容量始终为 **2 的幂**（位运算取模提速）。
- 扩容：元素数超 `capacity × loadFactor` 时容量翻倍、rehash。

## 为什么重要
1. HashMap 是 Java 最常用的数据结构，缓存、索引、计数、分组全靠它。
2. 面试必考：哈希冲突、扩容、树化、并发安全，是区分"会用"和"懂原理"的分水岭。
3. 理解负载因子能调优（空间换时间 or 时间换空间）。

## 常见坑
- **不当作线程安全用**：多线程 put 可能死循环/数据丢失，必须换 `ConcurrentHashMap`。
- **可变对象做 key**：key 的 hashCode 若变化，就再也找不到原来的值（如用 ArrayList 当 key 还改了内容）。
- **hashCode 写烂导致退化**：所有对象哈希相同 → 全挤一个桶 → O(1) 退化 O(n)/O(log n)。
- **忽略初始容量导致频繁扩容**：已知数据量大时应 `new HashMap<>(expectedSize)`，避免多次翻倍 rehash。

## 动手自测
1. 实现一个简易哈希表：用拉链法处理冲突，写 put/get，观察冲突时链表增长。
2. 读 OpenJDK `HashMap.putVal` / `resize` 源码，画出"链表转红黑树"的触发条件。
3. 对比 `HashMap`(非同步)、`Hashtable`(古老同步)、`ConcurrentHashMap`(分段/Node 级锁) 的线程安全差异。

## 面试视角
高频："HashMap 原理？""为什么负载因子 0.75、容量 2 的幂？""链表何时转红黑树？""HashMap 线程安全吗？ConcurrentHashMap 怎么做的？"收尾："核心是'哈希+数组桶+冲突处理'，JDK8 用链表+红黑树平衡了冲突时的查询成本，并发场景无脑上 ConcurrentHashMap。"

## 6. 树、堆与平衡树

> 引导：用层次化家谱模型理解遍历、有序容器与动态取极值(堆)。

## 心智模型
树是一张有层次的家谱：每个节点有父有子。最实用的是"每个节点最多俩孩子"的二叉树。堆是"父节点永远比孩子大/小"的特殊完全二叉树，用来快速取最大/最小值；平衡树（红黑树、AVL）保证树别歪成一条链表，让查找稳定在 O(log n)。

## 核心知识点（锚定官方）
- 遍历：前序/中序/后序(深度优先,DFS) 与 层序(广度优先,BFS)。二叉搜索树(BST)中序遍历得到有序序列。
- 平衡树：AVL（严格平衡，查快改慢）、红黑树（近似平衡，增删查都 O(log n)）。Java 中 **`TreeMap`/`TreeSet` 基于红黑树**，是有序集合。
- 堆：完全二叉树，大顶堆(父≥子)/小顶堆(父≤子)。Java **`PriorityQueue` 默认小顶堆**，基于堆实现，插入/取堆顶 O(log n)。
- 完全二叉树可用数组紧凑存储（下标 i 的左孩子 2i+1、右孩子 2i+2）。
- 经典应用：堆排序、Top-K（小顶堆）、Dijkstra 优先队列、中位数(双堆)。

## 为什么重要
1. 数据库索引(B+树)、文件系统、有序容器底层都是树。
2. 堆是"动态取极值"和 Top-K 问题的最优解。
3. 树的递归性质天然对应分治与回溯思维。

## 常见坑
- **把 TreeMap 当 HashMap 用**：TreeMap 多一次比较开销、按 key 有序但非 O(1)，不需要排序时应选 HashMap。
- **混淆堆顶语义**：默认小顶堆，想取最大要先取负或自定义比较器。
- **递归遍历栈溢出**：极深树用递归会 StackOverflow，应改迭代+显式栈。
- **平衡树旋转写错**：AVL/红黑树旋转是手写难点，易丢指针。

## 动手自测
1. 递归+迭代两种实现二叉树前/中/后序遍历。
2. 用数组实现小顶堆，写 `push`/`pop`，并解决 Top-K 问题。
3. 用两个堆（一个大顶、一个小顶）实时维护数据流的中位数。

## 面试视角
高频："二叉树遍历（手写三种）""堆排 vs 快排""Top-K 怎么解？""TreeMap 和 HashMap 区别？"收尾："树的核心是递归与平衡；工程上 HashMap 取快、TreeMap 取有序、PriorityQueue 取动态极值，三者各司其职。"

## 7. 图与常见算法(BFS/DFS/拓扑/最短路/并查集)

> 引导：把关系网问题抽象成点边，选对遍历与最短路工具。

## 心智模型
图是"关系网"：城市是点(顶点)，公路是线(边)。怎么找两城最短路径？怎么安排任务不打架（拓扑）？怎么把点分成互不连通的群（并查集）？图算法就是给这张网找规律的一套工具箱。

## 核心知识点（锚定官方）
- 表示：邻接矩阵(适合稠密图，O(V²) 空间)、邻接表(适合稀疏图，O(V+E))。
- 遍历：**DFS**（栈/递归，探到底再回）、**BFS**（队列，逐层扩散，求无权图最短路径）。
- 拓扑排序：对有向无环图(DAG)排线性序，用于任务依赖、编译顺序；检测环即发现依赖死锁。
- 最短路径：**Dijkstra**(非负权，贪心+优先队列 O(E log V))、**Bellman-Ford**(可负权、检测负环)、**Floyd**(多源)。
- 最小生成树：**Prim**、**Kruskal**(配并查集)。
- **并查集(Union-Find)**：路径压缩+按秩合并后近乎 O(1)，用于连通性、Kruskal、岛屿数量。

## 为什么重要
1. 社交网络、推荐系统、依赖编排、网络路由底层都是图。
2. BFS/DFS/拓扑/并查集是面试手撕高频，且能解大量中等题。
3. 最短路径与最小生成树是运筹与网络优化的基础。

## 常见坑
- **Dijkstra 遇负权失效**：负权必须用 Bellman-Ford。
- **DFS 忘标记 visited**：会死循环（有环图）。
- **拓扑排序前不查环**：有环则无拓扑序，需先判 DAG。
- **并查集不路径压缩**：退化为链，复杂度爆炸。

## 动手自测
1. 用邻接表+BFS 求无权图最短路径；用 DFS 判断有环。
2. 实现拓扑排序（Kahn 算法，入度表）。
3. 用并查集解"岛屿数量"或"朋友圈"问题。

## 面试视角
高频："图的两种表示区别？""BFS vs DFS 适用场景？""拓扑排序？""Dijkstra 能处理负权吗？"收尾："图的灵魂是建模——把问题抽象成点/边/权重，再选遍历或最短路算法；并查集是连通性问题的瑞士军刀。"

## 8. 排序、查找与算法范式

> 引导：既懂库函数背后的算法与稳定性，也掌握分治/贪心/DP/回溯的适用边界。

## 心智模型
排序是把乱序排整齐，查找是从整齐里快速定位。Java 已经把这两件事做到极致（库函数），但你要懂它背后是什么算法、什么复杂度，才能在对的时候用对的工具，也能在手撕时复现。

## 核心知识点（锚定官方）
依据 OpenJDK Java 17 `Arrays` 官方文档：
- 基本类型排序 `sort(int[])` 等：采用 **Dual-Pivot Quicksort**（Vladimir Yaroslavskiy、Jon Bentley、Joshua Bloch 提出），官方明确"offers O(n log n) performance on all data sets"，通常快于传统单轴快排。
- 对象数组排序 `sort(Object[])`：文档要求**必须是稳定排序(stable)**（不强制具体算法，OpenJDK 实现为 TimSort，一种稳定的归并式排序）。稳定性指相等元素的相对次序不变——对多键排序至关重要。
- `parallelSort`：并行排序-归并，稳定，适合大数组。
- 比较排序下界：**Ω(n log n)**（信息论下界），所以 O(n²) 的冒泡/插入在大数据量下不可用；桶/计数/基数排序可突破下界（但要求特定数据特征）。
- 二分查找 `Arrays.binarySearch`：前提**数组已有序**，O(log n)；无序调用结果未定义。
- 算法范式（经典，非 Java 专属）：**分治**(归并/快排)、**贪心**(局部最优)、**动态规划**(重叠子问题+最优子结构，如背包/最长公共子序列/编辑距离)、**回溯**(试错+剪枝，如全排列/N皇后)。

## 为什么重要
1. 排序是预处理步骤，选错算法在大数据量下直接超时。
2. 稳定性影响"先按 A 排、再按 B 排"的多维排序正确性。
3. DP/回溯是算法题最难也最值钱的部分，区分度极高。

## 常见坑
- **对未排序数组调 binarySearch**：返回结果无意义甚至负数误导。
- **误以为 Arrays.sort 对象数组不稳定**：它可能改变相等元素次序而破坏已有排序，需显式 stable 处理。
- **DP 写成爆搜**：没记忆化导致指数级超时（如递归斐波那契）。
- **二分边界写错**：left/right 更新与退出条件错，导致死循环或漏解（推荐"左闭右开"统一写法）。

## 动手自测
1. 手写快排、归并排序(体现稳定)、堆排序，对比它们与内置 sort 的行为。
2. 写二分查找，并验证"数组必须有序"这一前提。
3. 用 DP 解"最长公共子序列"和"0/1 背包"，用回溯解"全排列"，体会范式差异。

## 面试视角
高频："排序算法有哪些？复杂度？""什么是稳定排序？为什么重要？""二分查找怎么写不踩边界？""DP 和贪心区别？"收尾："库函数优先（Dual-Pivot Quicksort / TimSort 已极致优化），但手撕时要讲清分治/贪心/DP/回溯的适用边界；比较排序下界 Ω(n log n) 是常识锚点。"
