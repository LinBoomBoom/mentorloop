# be-nosql-s1 | NoSQL 全景与 CAP 取舍
> NoSQL 不是"不要 SQL"，是"为特定数据形状放弃部分关系能力换扩展性"。

## 心智模型
关系库像**严格的表格账本**（强一致、联表查询强），NoSQL 像**按用途特制的收纳盒**：文档盒（整块 JSON 随手放）、宽列盒（海量按行键的稀疏表）、图盒（节点关系一拽一串）、键值盒（超快查字典）。选盒子的本质是"你要的是一致性还是扩展性"。

## 核心知识点（锚定官方）
- **CAP 定理（Brewer 猜想 / Gilbert-Lynch 证明）**：网络分区（P）不可避免时，只能在一致性（C）与可用性（A）间取舍；CP 系统分区时拒绝写入，AP 系统分区时返回旧值。
- **BASE（AP 系统的妥协）**：Basically Available、Soft state、Eventual consistency。
- **四大家族**：文档（MongoDB）、宽列（Cassandra）、图（Neo4j）、键值（Redis）。

## 为什么重要
be-c2 只覆盖了 MySQL+Redis。理解 NoSQL 全景才能在设计"海量/高并发/关系密集"场景时选对存储，而不是什么都往 MySQL 塞。

## 常见坑
- 把强一致要求的交易数据放 AP 系统，出现脏读资损。
- 为"显得先进"引入 NoSQL，却失去联表能力后疯狂做应用层 join。
- 误以为 NoSQL 不需建模，导致文档无限嵌套难查询。

## 动手自测
1. 画一个决策表：订单交易（CP/关系）→ MySQL；购物车（AP/简单KV）→ Redis；社交关系（图）→ Neo4j。
2. 解释一次网络分区下，CP 与 AP 系统各自用户看到什么。

## 面试视角
"CAP 是什么？AP 和 CP 取舍？NoSQL 四家族各自适合啥？"——讲清分区不可避、场景选型。

# be-nosql-s2 | 文档数据库 MongoDB
> 当数据天然是"嵌套的文档"，文档库比行表更贴合。

## 心智模型
MongoDB 像**文件柜而非表格**：一条记录就是一份完整 JSON 文档（BSON），订单连同它的商品列表、地址整块存进去，读的时候一次取全，不用像 MySQL 那样把订单拆十张表再 join 回来。

## 核心知识点（锚定官方）
- **BSON 文档（MongoDB 官方）**：类 JSON 二进制，支持日期/二进制/嵌套；`_id` 默认 ObjectId。
- **聚合管道（Aggregation）**：`$match/$group/$lookup` 做服务端数据处理，`$lookup` 近似 join。
- **分片（Sharding）**：按 shard key 水平拆分，应对海量；副本集提供高可用与读扩展。

## 为什么重要
内容管理、目录、IoT 设备上报等"结构易变、读多写少、文档型"数据，用文档库开发效率高、易水平扩展。它是 NoSQL 最主流形态。

## 常见坑
- 无脑嵌太多层，文档超 16MB 限制或查询困难。
- 用 `$lookup` 频繁跨集合 join，退化成慢 SQL。
- shard key 选错（基数低/单调）导致热点分片。

## 动手自测
1. 用聚合管道统计"每个用户最近 30 天订单总额"，对比应用层循环查。
2. 建一个 2 分片集群，观察按 shard key 的分布。

## 面试视角
"文档库适合什么？聚合管道干嘛用？分片解决什么？"——讲清嵌套存储、服务端聚合、水平扩展。

# be-nosql-s3 | 宽列数据库 Cassandra/HBase
> 写多读少、海量时序/事件，宽列表比 B+ 树行表更扛。

## 心智模型
宽列表（Wide-Column）像**按"行键"排的超级稀疏大表**：每一行键下可以挂极多的列（甚至百万），适合"一个设备 ID 下塞进它十年每秒的上报点"。写入是追加日志，极快且天然有序。

## 核心知识点（锚定官方）
- **Cassandra（apache.org）**：LSM-Tree 写优化、无主（masterless）多副本、可调一致性（`QUORUM`）；按 partition key + clustering key 组织。
- **数据模型**：先定查询再建模（query-first），宽行避免跨分区。
- **HBase**：构建在 HDFS 上，强一致、依赖 ZooKeeper，适合 Hadoop 生态。

## 为什么重要
物联网时序、事件日志、消息存储、风控埋点这类"写爆炸、按 key 扫范围"的场景，Cassandra 的写吞吐与线性扩展是 MySQL 难以企及的。

## 常见坑
- 拿关系查询思维建表，频繁跨分区导致全表扫描。
- 一致性级别设 `ONE` 却要求读最新，读到旧值。
- partition key 设计不当造成超大分区（hot partition）。

## 动手自测
1. 为"设备时序上报"设计 Cassandra 表（partition=设备ID+日期，clustering=时间戳）。
2. 用 `CONSISTENCY QUORUM` 写入后多节点读取，验证一致性。

## 面试视角
"宽列表适合啥？LSM 写优化？为什么建模要先想查询？"——讲清写吞吐、查询驱动建模、热点避免。

# be-nosql-s4 | 图数据库与关系密集场景
> 当"关系"比"实体"更重要，图库一拽一串。

## 心智模型
图数据库像**一张人脉网**：节点是人、边是"认识/关注"，要查"张三的朋友里谁也认识李四"这种多跳关系，在关系库里要 join 七八张表，在图库里就是从节点沿着边走几步——复杂度与数据总量无关，只和"要走几跳"有关。

## 核心知识点（锚定官方）
- **属性图模型（Neo4j）**：节点+关系+属性；用 Cypher（`MATCH (a)-[:KNOWS]->(b)`）查询。
- **多跳与最短路径**：社交推荐、反欺诈（资金环路）、知识图谱、依赖分析。
- **对比关系库**：多跳关系查询图库指数级更快；但简单 KV/聚合场景图库无优势。

## 为什么重要
反欺诈、推荐、权限继承、组织架构、知识图谱——这些"关系密集"问题是图库的绝对主场。理解它才能不硬用 MySQL 做痛苦的多表递归。

## 常见坑
- 在图库里存大量无关系的大宽表数据，浪费图优势。
- Cypher 不写关系方向/深度限制，查询爆栈或全图扫描。
- 把图库当主存储放所有业务，忽视其事务/聚合短板。

## 动手自测
1. 用 Neo4j 建"用户-关注"图，查出"二度好友推荐"。
2. 用 Cypher 找"资金环"（A→B→C→A）识别疑似闭环欺诈。

## 面试视角
"图库适合什么？和关系库比多跳优势？典型应用？"——讲清关系密集、多跳成本、欺诈/推荐。

# be-nosql-s5 | 搜索引擎 Elasticsearch 与倒排索引
> 全文检索不是 LIKE%，是倒排索引。

## 心智模型
倒排索引像**书末的索引表**：不是"翻到第几页找词"，而是"词→出现在哪些文档"。Elasticsearch 把每个词建一张"词到文档列表"的映射，搜"手机"瞬间拿出所有含"手机"的文档，再按相关性排序。

## 核心知识点（锚定官方）
- **倒排索引（Elastic 官方）**：term → posting list（docId+位置）；写入先进 translog+内存 buffer，refresh 成可搜段（segment）。
- **分片与副本**：index 拆 primary shard，副本提供高可用与读扩展；近实时（~1s refresh）。
- **分布式查询**：协调节点 scatter 到各 shard，gather 归并结果。

## 为什么重要
商品搜索、日志检索、站内全文都是 ES 的主场。MySQL 的 `LIKE '%词%'` 全表扫描且不支持分词，量级一大就崩。它是"搜索/日志"场景的事实标准。

## 常见坑
- 把 ES 当主数据库用，丢了就麻烦（它本质是检索副本，非源）。
- 字段都用 text 不 mapping，分词/类型错导致搜不到。
- 深分页 `from+size` 过大，协调节点归并爆炸（用 search_after）。

## 动手自测
1. 建商品 index，写入 1 万条，执行中文分词检索验证召回。
2. 用 `search_after` 做深翻页，对比 `from=10000` 报错。

## 面试视角
"倒排索引是什么？ES 为什么快？深分页怎么解？"——讲清 term->doc、近实时、search_after。

# be-nosql-s6 | 全文检索与相关性排序
> 搜得出不等于搜得对，相关性才是搜索体验核心。

## 心智模型
相关性排序像**图书管理员按"贴合度"把书摆到最前面**：他看这本书里词出现多不多（词频 TF）、这个词本身稀不稀有（逆文档频率 IDF）、字段权重高不高（标题命中 > 正文），综合算出分数，分高的排前面。

## 核心知识点（锚定官方）
- **BM25（Elastic 默认评分）**：在 TF-IDF 基础上对词频做饱和、对文档长度归一，避免长文档天然高分。
- **Analyzer 分词链**：char filter → tokenizer → token filter（小写、同义词、停用词），中英文差异大。
- **bool 查询**：must/should/filter/boost 组合权重，filter 不计入评分可缓存。

## 为什么重要
搜索质量直接决定电商转化与日志定位效率。不懂分词与评分，会出现"搜'苹果手机'召回一堆苹果食谱"的尴尬。

## 常见坑
- 默认 standard 分词对中文按字切，召回噪声大（应 IK/jieba）。
- 过度 boost 某字段，长尾query全被少数文档霸榜。
- 把 filter 条件写成 must，白白算评分拖慢。

## 动手自测
1. 对比同一 query 在 standard 与 IK 分词下的召回差异。
2. 用 `function_score` 把"销量高"作为权重叠加到 BM25 上。

## 面试视角
"BM25 是什么？Analyzer 干嘛用？bool 查询各子句区别？"——讲清评分、分词、权重组合。

# be-nosql-s7 | Redis 作为高级数据结构存储
> Redis 不只是缓存，更是带丰富数据结构的"内存数据库"。

## 心智模型
Redis 像**一台超快的多功能工具车**：不光能当 KV 字典（string），还自带队列（list/stream）、集合（set/zset 排行榜）、基数估算（HyperLogLog 算 UV）、布隆过滤器（判断"可能存在/一定不存在"）。把它当"内存里的数据结构瑞士军刀"而非单纯缓存。

## 核心知识点（锚定官方）
- **数据结构（redis.io）**：String、Hash、List、Set、ZSet（跳表，排行）、Bitmap、HyperLogLog、Bloom、Stream（消息流）。
- **持久化**：RDB 快照 + AOF 日志，可配"缓存"或"存储"定位。
- **高级用法**：ZSet 做延迟队列/排行榜；Stream 做轻量消息队列；Bloom 防缓存穿透。

## 为什么重要
be-c2 讲了 Redis 基础。这里强调它"超越缓存"的能力：限流、排行榜、去重、消息流、布隆过滤，都是高并发系统的常用积木。

## 常见坑
- 把 Redis 当主存储却不配持久化，重启丢数据。
- 大 key（巨型 Hash/List）阻塞单线程。
- 用 `KEYS *` 在生产扫全库，阻塞服务（应 SCAN）。

## 动手自测
1. 用 ZSet 实现一个实时排行榜（score=分数），取 Top10。
2. 用 Stream + consumer group 做一个至少一次投递的消息处理。

## 面试视角
"Redis 除了缓存还能干嘛？ZSet/Stream 用途？大 key 危害？"——讲清数据结构、排行榜/消息、单线程陷阱。

# be-nosql-s8 | 多模型选型决策
> 没有"最好的数据库"，只有"最贴合数据的模型"。

## 心智模型
选型像**选交通工具**：去隔壁用自行车（Redis KV）、跨城运货用火车（MySQL 关系/事务）、远洋用船（数据湖）、救急空运（图库）。一个系统常常"多模型并存"——不同数据放不同库，各司其职。

## 核心知识点（锚定官方）
- **按访问模式选**：强事务+联表→关系库；文档型→MongoDB；海量写→Cassandra；关系密集→图；全文→ES；热 KV→Redis。
- **Polyglot Persistence（Martin Fowler）**：单一系统组合多种存储，各取所长。
- **代价**：多存储带来运维、一致性、双写复杂度，需权衡。

## 为什么重要
架构师的核心能力之一就是"不为潮流选 NoSQL，不为熟悉选 MySQL"。清晰的选型决策能避免大规模返工。

## 常见坑
- 一套存储硬扛所有场景，早期省事后期崩溃。
- 为"酷"引入多存储却无一致性与双写方案，数据对不上。
- 忽视团队运维多库的代价。

## 动手自测
1. 给一个电商系统设计存储组合：订单(MySQL)+购物车(Redis)+商品搜索(ES)+推荐关系(Neo4j)。
2. 列出该组合下"下单"需要保证的一致性与双写顺序。

## 面试视角
"怎么选数据库？什么是多模型持久化？引入多存储的代价？"——讲清场景匹配、组合、运维成本。

# be-nosql-s9 | 最终一致性与冲突解决
> AP 系统不保证"立刻一致"，但要保证"最终能对上"。

## 心智模型
最终一致性像**多个分店各自记账**：A 店先记了、B 店网络慢晚点到账，短时间内两店数字不一致，但只要没有新交易、等同步跑完，最终两店账面一定对齐。冲突时（两边同时改）要靠"规则"决定谁赢。

## 核心知识点（锚定官方）
- **Dynamo 论文（DeCandia et al.）**：向量时钟（vector clock）追踪版本因果，冲突时交给应用或 LWW/CRDT 解决。
- **CRDT（无冲突复制数据类型）**：数学上保证并发合并必一致（计数器、集合）。
- **读写 quorum**：`W+R>N` 保证强一致读，否则为最终一致。

## 为什么重要
分布式 NoSQL（Cassandra/DynamoDB）本质是 AP，理解最终一致与冲突解决才能正确设计"购物车、草稿、计数"这类容忍短暂不一致的业务。

## 常见坑
- 假设 AP 系统读到的一定是最新，导致显示陈旧数据引发客诉。
- 用 LWW（最后写入获胜）却有时钟回拨，丢更新。
- 冲突解决逻辑放在客户端却没覆盖所有副本。

## 动手自测
1. 用向量时钟模拟两个副本并发更新，演示冲突检测与合并。
2. 用 CRDT 计数器在三个节点并发自增，验证合并值正确。

## 面试视角
"最终一致是什么？向量时钟干嘛？CRDT 为什么无冲突？"——讲清延迟一致、因果追踪、数学合并。
