## 第9章 · 微服务与分布式架构

**章目标**：理解微服务作为一种"围绕业务能力的自治服务集合"的架构风格；能说清它与单体在部署、数据、团队上的根本差异；掌握 API 网关、消息中间件、可观测性、数据私有等核心组件与最佳实践；能识别常见反模式与分布式带来的新挑战（一致性、网络、运维）。

### be-c9-s1 · 微服务定义与边界（锚定官方）

> 时效 | 核验=2026-08-16 | 风险=低 | 来源=官方

> 心智模型：微服务像**一支"小而全"的特种小队**——每队只负责一块业务（下单、库存、推荐），自己带数据库、自己部署、自己演进；队与队之间只通过**约定好的 API（口令）** 沟通，互不窥探内部。对比单体像"一个大部门共用一套档案"，微服务是"多个小部门各有档案、只走公文往来"。

## 心智模型
微服务是一种流行的架构风格，用于构建**有韧性、高可扩展、可独立部署、能快速演进**的应用。成功的微服务架构需要思维方式的转变——不止是把应用拆小，还要重新思考系统的设计、部署与运维方式。

微服务架构由一组**小而自治的服务**集合构成。每个服务**自包含**，应在**限界上下文（bounded context）** 内实现一个单一业务能力。限界上下文是业务内的自然划分，提供领域模型存在的明确边界。

每个微服务是一个**小且独立的松耦合组件**，单个小开发团队就能编写与维护。每个服务作为**独立的代码库**管理，允许小团队高效掌控。因为可**独立部署**，团队可以更新某服务而无需重建/重部署整个应用。与传统的"集中式数据层"不同，微服务**负责持久化自己的数据或外部状态**，通过**定义良好的 API** 通信，从而向其他服务隐藏内部实现。

## 核心知识点（锚定官方）
- **定义要点**（两源一致）：small / autonomous / independently deployable / loosely coupled；organized around **business capabilities**；每个服务在 **bounded context** 内实现单一能力。
- **独立代码库 + 独立部署**：单服务更新不触发全应用重建；小团队 ownership。
- **数据私有**：每个服务拥有自己的数据与 schema，按服务选存储（**polyglot persistence**，SQL/NoSQL 按需），降低跨服务依赖、允许独立演进。
- **通过 API 通信**：隐藏内部实现；支持 **polyglot programming**（服务不必共用技术栈）。
- **从单体演进的模式（microservices.io）**：**Strangler Fig pattern**——在旧系统外逐步包裹新服务，按功能一块块替换，而非一次性重写。
- **分布式数据管理（microservices.io）**：跨服务的交易用 **Saga**（一组本地事务+补偿）、查询用 **API Composition**（聚合多服务结果）或 **CQRS**（读写模型分离）。

> 来源：[Microsoft Learn · Microservices architecture style](https://learn.microsoft.com/azure/architecture/guide/architecture-styles/microservices) · [microservices.io](https://microservices.io/)

## 为什么重要 / 何时会用到
- 当单体变成"改一行要全量回归、小团队互相踩脚、发布互相阻塞"时，微服务把边界划清、让团队独立推进。
- 当不同模块**扩缩容需求差异巨大**（如推荐算力和下单算力）时，微服务可只扩瓶颈服务。
- 当组织变大、需要**多团队并行**且各自技术选型时，微服务（配合清晰边界）减少耦合。

## 常见坑
- **边界切错**：按技术层切（如"用户服务""订单服务"混了不该混的）而非按业务能力，导致频繁跨服务调用、耦合反而更重。
- **共享数据库**："独立部署"但"共用一张库"，一处 schema 变更全挂——违背数据私有。
- **把微服务当银弹**：小团队/小业务上微服务，运维复杂度（服务发现、分布式事务、链路追踪）反而拖死交付。
- **网关里写业务**：API 网关应只做路由/鉴权/限流，把领域知识塞进网关会制造新的耦合点。

## 动手自测
1. 把一个单体模块的"订单"与"库存"按业务能力拆成两个服务，各自建库，用 HTTP/gRPC 通信，体会"数据私有 + API 契约"。
2. 用 Strangler Fig 思路：在旧订单模块前加一个路由层，新请求逐步切到新服务，旧逻辑按流量灰度下线。
3. 对一个"下单并扣库存"的跨服务操作，用 Saga（本地事务 + 失败补偿）实现，观察部分失败时的回滚。
4. 给两个服务接统一分布式追踪（OpenTelemetry），看一次请求穿过哪些服务、卡在哪。

## 面试视角
"微服务和单体最大区别？"答：部署单元与数据所有权——单体共享代码库与数据库、整体发布；微服务各服务独立代码库、独立部署、数据私有、经 API 通信。"为什么按业务能力而非技术层划分？"答：业务能力对应真实限界上下文，变更内聚、跨服务调用少。"Strangler Fig 是什么？"答：逐步用新服务包裹/替换旧系统的演进模式，降低重写风险。"微服务一定更好吗？"答：否，它用运维与分布式复杂度换团队自治与独立伸缩，业务规模不够时是过度设计。

### be-c9-s2 · 核心组件与最佳实践（锚定官方）

> 时效 | 核验=2026-08-16 | 风险=低 | 来源=官方（Microsoft Learn）

> 心智模型：微服务不是"几个 service 文件"就完事，它是一整套**支撑系统**——网关（门卫）、编排（调度）、消息（传话）、可观测（监控）。缺了任一块，微服务都会从"自治"退化成"各自失联"。

## 心智模型
除服务本身，典型微服务架构还有若干关键组件共同保障系统可运行、可观测、可演进。

## 核心知识点（锚定官方 Microsoft Learn）
- **管理与编排（Management/Orchestration）**：负责微服务编排——跨节点调度部署、检测并恢复故障、按需自动扩缩。Kubernetes 类容器编排平台通常提供此能力；云原生里如 Azure Container Apps 提供托管编排与内置伸缩，降低部署与运维复杂度。
- **API 网关（API Gateway）**：作为客户端的**统一入口**，客户端请求发往网关而非直连服务；网关转发到合适后端服务，并处理**横切关注点**：认证、日志、负载均衡。云原生里 Envoy/Nginx 等轻量服务代理支撑**东西向（east-west）** 内部服务间通信与高级路由。
- **消息中间件（Message-oriented middleware）**：Kafka、Azure Service Bus 等消息平台支撑微服务**异步通信**，促进松耦合、高可扩展，是**事件驱动架构**的基础——服务可实时响应事件、通过异步消息沟通。
- **可观测性（Observability）**：集中式日志便于诊断；用 APM agent 与 OpenTelemetry 等框架做实时监控；**分布式追踪**跨服务边界跟踪请求，定位瓶颈。
- **数据管理**：微服常用 **polyglot persistence**，按各服务需求选 SQL/NoSQL，契合 DDD 与 bounded context；每服务拥有自己的数据与 schema，降低跨服务依赖。

**最佳实践（官方列出要点）**：
- 围绕业务领域建模，用 DDD 识别 bounded context、界定清晰服务边界；**避免过度细粒度**服务（增复杂度、降性能）。
- **彻底去中心化**：团队端到端负责设计构建；不共享代码或数据 schema。
- **标准化技术选型**：限制语言/框架数量，建立日志、监控、部署的全局标准（不扼杀团队灵活性）。
- **数据私有 + 按存储选型**；服务经**良好设计的 API** 通信，不泄露实现细节（API 应建模领域而非内部实现）。
- **避免服务间耦合**：共享库 schema、刚性协议是耦合源。
- 异步通信用消息框架（MassTransit/NServiceBus）处理路由/重试/持久化/工作流，勿自造消息逻辑。
- 服务间加密用 **mTLS**；基于角色的访问控制；API 网关统一执行策略。
- **横切关注点下沉到网关/服务网格（如 Dapr）**：认证、SSL 终止等；网关**不持有领域知识**。
- 服务应**松耦合、高内聚**；易变在一起的功能应同服务部署，否则一改要动两个服务。
- CI/CD 自动化测试部署；独立部署并监控发布健康。
- **隔离故障**：用弹性模式（断路器等）防故障级联；用**混沌工程**验证韧性。

> 来源：[Microsoft Learn · Microservices architecture style](https://learn.microsoft.com/azure/architecture/guide/architecture-styles/microservices)

## 为什么重要 / 何时会用到
这些组件不是"锦上添花"：没有编排，服务多了管不过来；没有网关，客户端直连 N 个服务且每处都要认证；没有消息中间件，服务只能同步互调、一挂全挂；没有可观测性，分布式故障无从下手。

## 常见坑
- **网关变成"万能中间层"**：把鉴权、限流、业务路由、甚至领域逻辑都堆进网关，网关膨胀成新单体。
- **异步消息自造轮子**：自己写重试/持久化/路由，踩遍分布式坑；应直接用成熟框架。
- **只做服务拆分不做可观测**：拆完发现"慢请求"无处溯源，因为没接分布式追踪。
- **无弹性模式**：一个服务慢/挂，同步调用链层层超时、线程耗尽，故障级联。

## 动手自测
1. 在 s1 的拆分上，前置一个 API 网关（如 Nginx/Envoy），统一做认证与路由，客户端只知网关。
2. 引入 Kafka/Redis Streams 做事件驱动：下单服务发"OrderCreated"事件，库存/通知服务异步消费，验证松耦合。
3. 接 OpenTelemetry + 集中日志，模拟一个服务变慢，用追踪定位瓶颈服务。
4. 给一个服务加断路器（如 resilience4j），故意让它故障，观察调用方快速失败而非线程耗尽。

## 面试视角
"微服务里 API 网关做什么？"答：统一入口、路由、认证/日志/限流等横切，客户端不直连服务；但不应塞业务领域逻辑。"为什么需要消息中间件？"答：支撑异步、松耦合、事件驱动，避免同步调用链级联故障。"可观测性在微服务里为什么比单体更重要？"答：请求跨多服务，需集中日志+指标+分布式追踪才能定位。"mTLS 解决什么？"答：服务间通信加密与双向身份认证，防内网横向移动。

### be-c9-s3 · 分布式挑战与反模式（锚定官方）

> 时效 | 核验=2026-08-16 | 风险=低 | 来源=官方（Microsoft Learn）

> 心智模型：微服务的"好处"和"代价"是同一枚硬币——**自治换来的是分布式复杂度**。你获得独立部署，就要承受网络不可靠、数据要最终一致、跨服务测试困难、版本要兼容。低估这些，微服务会从"敏捷"变"混乱"。

## 心智模型
微服务的收益伴随权衡。设计前必须正视以下挑战，否则架构会反噬。

## 核心知识点（锚定官方 Microsoft Learn）
**挑战**：
- **复杂度**：微服务系统"活动部件"比等效单体多；每个服务简单，但整体更复杂——需考虑服务发现、数据一致性、事务管理、服务间通信。
- **开发与测试**：依赖其他服务的写法不同；重构跨边界难；测试服务依赖（尤其快速演进时）困难。
- **治理缺失**：过度去中心化可能导致语言/框架过多、难以维护；需设项目级标准（尤其日志等横切）。
- **网络拥塞与延迟**：大量细粒度服务增加服务间通信；依赖链过长（A→B→C…）引入额外延迟；需谨慎设计 API、避免 chatty API、考虑序列化与异步（Queue-Based Load Leveling）。
- **数据一致性**：每服务自管持久化，跨多服务的数据一致性难；不同服务不同时间/技术/成败地持久化，难以做到 ACID 原子事务，更贴近 **BASE（Basically Available, Soft state, Eventual consistency）**——应"尽可能拥抱最终一致"。
- **管理**：成功微服需成熟 DevOps 文化；跨服务关联日志困难（需为单次用户操作关联多个服务调用）。
- **版本化**：服务更新不能破坏依赖方；多服务随时可能更新，需谨慎设计前向/后向兼容。
- **技能集**：微服是高度分布式系统，需评估团队是否具备相应技能与经验。

**反模式（官方列出要点，须避免）**：
- 不懂业务领域就做微服 → 边界错配。
- 事件依赖过去/未来事件 → 违背"原子且自包含消息"，迫使消费者等待、降低可靠性。
- 用数据库实体当事件 → 泄露内部细节、表达不清业务意图、导致紧耦合。
- **一味避免数据冗余** → 反模式；用物化视图等维护本地副本反而提升自治、减跨服务依赖。
- 用通用事件 → 迫使消费者解释/过滤，增复杂度。
- **微服务间共享公共库/依赖** → 紧耦合、改动风险面广，违背自包含。
- **把微服直接暴露给消费者** → 紧耦合+伸缩/安全问题；应经 API 网关。
- 配置写死在服务内 → 与环境紧耦合、部署困难；应外部化配置。
- 把令牌校验等安全逻辑嵌入服务 → 代码复杂难维护；应下沉到专用组件。
- 不抽象公共任务 → 重复易错代码；用 Dapr 等框架把业务逻辑与基础设施解耦。

> 来源：[Microsoft Learn · Microservices architecture style](https://learn.microsoft.com/azure/architecture/guide/architecture-styles/microservices)

## 为什么重要 / 何时会用到
这些挑战与反模式是"微服务翻车"的高频原因。做架构评审时逐条对照，能在设计阶段避开大多数坑；做故障复盘时，也常能在这里找到根因（如"共享库导致一个改动全线回归"）。

## 常见坑
- **假装分布式事务**：用两阶段提交硬凑 ACID，性能与可用性双输；应改最终一致 + 补偿（Saga）。
- **同步调用链过长**：A→B→C→D 全同步，任一段慢就整体超时；应异步化热点路径。
- **跨服务共享表**："数据私有"被破坏，schema 变更要协调多个团队。
- **版本不兼容升级**：改了接口没做向后兼容，下游集体报错。

## 动手自测
1. 故意让"下单→库存→通知"同步链中间一环慢 2 秒，用压测看整体超时与线程占用，再改成事件驱动观察改善。
2. 设计一个需要跨两服务的"扣款+记账"操作，用 Saga+补偿替代两阶段提交，验证部分失败可回滚。
3. 把一个写死在代码里的配置外部化（环境变量/配置中心），验证同一镜像多环境部署。
4. 对服务接口做向后兼容改造（加字段不删旧字段、老客户端仍可用），验证无破坏升级。

## 面试视角
"微服务的数据一致性怎么保证？"答：难做跨服务 ACID，通常用最终一致（BASE）+ Saga 补偿；关键业务可接受短暂不一致。"微服务的反模式有哪些？"答：共享数据库、共享库、网关塞业务、直接暴露服务、配置写死、事件用实体而非业务语义等。"微服务为什么测试更难？"答：依赖多服务、跨边界重构难、需桩/契约测试与端到端环境。"什么时候不该用微服务？"答：业务规模小、团队小、交付速度优先于独立伸缩时，单体更合适。
