### be-c6-s1 · Redis Streams 实战（锚定官方）

> 时效 | 核验=2026-08-16 | 风险=低 | 来源=官方

> 心智模型：Redis Streams 像一个**带索引的"只追加日志"（append-only log）**——你往尾部追加一条条带 ID 的条目，消费者按 ID 顺序读；它比裸 list/发布订阅强在：能**随机访问（O(1)）**、能**多个消费者组各自独立消费**、能**追踪"已读未确认"的待办（PEL）**，所以既像日志又像队列。

## 心智模型
Redis Stream 是一种"类只追加日志"的数据结构，但额外提供了克服传统日志限制的操作——包括 **O(1) 随机访问**与**复杂消费策略（如消费者组）**。它支持多种**裁剪（trimming）策略**防止无限增长，也支持多种消费策略（见 `XREAD`、`XREADGROUP`、`XRANGE`）。从 Redis 8.2 起，`XACKDEL`、`XDELEX`、`XADD`、`XTRIM` 提供了对"流操作如何与多个消费者组交互"的细粒度控制，简化跨应用的消息处理协调。

## 核心知识点（锚定官方）
- **追加条目 `XADD`**：向流追加带 field-value 对的条目，ID 可用 `*` 自动生成（格式 `<毫秒时间戳>-<序号>`）。ID 必须**单调递增**——若指定的 ID 小于或等于流顶项，会报错 `ERR The ID specified in XADD is equal or smaller than the target stream top item`。
  - 例：`XADD race:france * rider Castilla speed 30.2 position 1 location_id 1`
- **消费者组 `XGROUP`**（容器命令）：
  - `XGROUP CREATE` 创建消费组；`XGROUP CREATECONSUMER` 在组内建消费者；
  - `XGROUP DELCONSUMER` 删除组内消费者；`XGROUP DESTROY` 销毁整个消费组；
  - `XGROUP SETID` 设置消费组最后投递的 ID。
- **消费与确认**：
  - `XREADGROUP` 让组内某消费者读取**新消息**（阻塞式可用，类似 `XREAD` 的阻塞）；
  - `XACK` 确认消息已被处理（返回该消费者组成功确认的消息数）；`XAUTOCLAIM` / `XCLAIM` 用于**转移/认领**因消费者故障而滞留的 Pending 消息（所有权变更）。
  - **PEL（Pending Entries List）**：每个消费组维护"已投递未确认"的条目列表；`XPENDING` 可查看这些信息与条目，用于故障恢复与重投。
- **修剪/裁剪 `XTRIM`**：控制流体积，防止无界增长。
- **复杂度**：`XREAD`/`XRANGE` 等返回 M 个元素约 O(M)；若 M 恒定（如固定取前 10 条 `COUNT 10`）可视为 O(1)。当 `XREADGROUP` 阻塞时，新 `XADD` 会以 O(N) 代价服务 N 个阻塞在该流上的客户端。

> 来源：[Redis · Streams](https://redis.io/docs/latest/data-types/streams/)

## 为什么重要 / 何时会用到
- 把"下单"和"发邮件/扣库存/推推荐"拆开：主流程只负责写一条流条目，下游各自消费，主接口不被慢任务拖垮（**异步解耦**）。
- 秒杀/导入类流量洪峰：消息先入流，worker 按自己节奏消费，保护后端（**削峰填谷**）。
- 多实例部署时，用消费者组让 N 个 worker 分摊同一条流，且每条消息只被一个消费者处理（**竞争消费 + 不重复**）。

## 常见坑
- **忘记 `XACK`**：消息一直在 PEL 里，重启后会被反复重投，造成重复处理。
- **消费者崩溃不认领 PEL**：用 `XCLAIM`/`XAUTOCLAIM` 把死信转移给健康消费者，否则消息永久卡住。
- **不设 `XTRIM`**：流只增不减，内存被吃满。
- **用 Streams 当"任务队列"却不设计幂等**：至少一次投递下，重复消费要靠业务幂等（去重键）兜底。
- **把 Streams 当消息中间件全家桶**：跨服务、需严格顺序/分区、海量堆积时，专用 MQ（Kafka/RabbitMQ）更合适。

## 动手自测
1. `XADD mystream * taskid 1 payload "send_email"` 追加；`XRANGE mystream - +` 查看全部。
2. `XGROUP CREATE mystream g1 $` 建组（从最新开始）；两个 worker 用 `XREADGROUP GROUP g1 w1 COUNT 1 STREAMS mystream >` 竞争消费，验证"一条只被一个 worker 拿到"。
3. 处理完后 `XACK mystream g1 <id>`；故意不 ACK 一条，用 `XPENDING mystream g1` 观察 PEL，再用 `XCLAIM` 把该条转移给另一消费者，验证故障恢复。
4. `XTRIM mystream MAXLEN 1000` 限制长度。

## 面试视角
"Redis Streams 和 list + BRPOP 做队列有什么区别？"答：list 只能简单队列、无消费组、无 PEL、无法多独立消费者组；Streams 有消费者组、ACK、Pending、随机访问、裁剪，是更完整的日志型队列。"什么叫至少一次投递？"答：消息可能重复（消费者拿到后因崩溃未 ACK 被重投），业务必须幂等。"Redis 8.2 对多消费组协调做了什么增强？"答：XACKDEL/XDELEX 等让流操作对多消费组的交互更可控。

### be-c6-s2 · 消息队列通用模型与选型边界（含 Kafka 说明）

> 时效 | 核验=2026-08-16 | 风险=中 | 来源=通用概念（非单一官方抓取）+ Kafka 官方文档 SPA 受限待补

> 心智模型：不论 Redis Streams、Kafka 还是 RabbitMQ，本质都是**"生产者把消息放进一个管道、消费者从管道取出"**——差异在管道的形状（队列 vs 日志）、顺序保证、堆积能力与投递语义。选型的本质是：你的场景更在乎"不丢""不重""有序"还是"海量吞吐"？

## 心智模型
消息队列解决三类问题：**异步**（主流程不等慢任务）、**解耦**（生产者不依赖消费者实现）、**削峰**（缓冲瞬时洪峰）。三种经典消费模式：
- **点对点（竞争消费）**：一条消息只被一个消费者处理——适合任务分发。
- **发布/订阅**：一条消息广播给所有订阅者——适合事件通知。
- **消费组 + 分区/分片**：多个消费者组各自独立消费同一份数据，组内竞争、组间隔离——适合"同一份数据既要算指标又要落库"的场景。

## 核心知识点（通用模型，非特指某产品）
- **核心角色**：Producer（生产）、Broker（中转/存储）、Consumer（消费）、Consumer Group（消费组）。
- **投递语义**（面试高频）：
  - **至多一次（at-most-once）**：可能丢，不重复。
  - **至少一次（at-least-once）**：不丢，但可能重复——需消费端**幂等**兜底（最常见现实语义）。
  - **精确一次（exactly-once）**：既不丢也不重，通常需要产品级事务/幂等写+去重支持，代价最高。
- **顺序性**：单分区/单分片内通常保序；跨分区不保证全局序。
- **堆积与回溯**：日志型 MQ（如 Kafka 类）保留历史、可重放；队列型 MQ 通常消费即删。
- **Kafka 专有项（待补）**：`kafka.apache.org/documentation/` 在沙箱为 SPA 渲染（仅 14 字正文），其 **topic / partition / consumer group / offset / replication** 等规范未能抓取，本节不臆造具体参数。建议后续补抓官方文档并入。

## 为什么重要 / 何时会用到
- 当"调用链变长、某一步变慢就拖垮全链路"时，用队列把同步调用改成异步。
- 当"写请求远超下游处理能力"时，用队列做缓冲。
- 当"一个事件要触发多个后续动作"时，用发布/订阅或消费组。

## 常见坑
- **把 MQ 当 RPC 用**：需要同步返回结果时，队列不是好选择（考虑响应通道或 RPC）。
- **忽视幂等**：至少一次语义下重复消费必然发生，不做幂等会出脏数据。
- **消息体过大**：MQ 擅长小消息，塞大对象（文件内容）会降低吞吐、撑爆内存。
- **消费慢于生产却不扩容/限流**：堆积到 Broker 磁盘/内存上限，引发雪崩。
- **死信无出口**：失败消息无限重试，应有 DLQ（死信队列）与告警。

## 动手自测
1. 用 Redis Streams（s1）搭一个最小竞争消费；再用同一流的第二个消费组模拟"指标计算组"与"落库组"并行消费，体会消费组隔离。
2. 故意让消费者处理一半后崩溃，观察消息是否会因未 ACK 被重投，验证"至少一次"。
3. 设计一条消息的 `biz_key`，在消费端用该 key 做幂等（已处理则跳过），验证重复投递安全。

## 面试视角
"你们为什么选 Redis Streams 而不是 Kafka？"答：量不大、想复用已有 Redis、要简单消费组与 ACK 时用 Streams；要超高吞吐、海量堆积、多分区保序、生态 connector 时选 Kafka。"至少一次 vs 精确一次怎么选？"答：多数业务用至少一次 + 幂等性价比最高；金融对账等极少数才上精确一次。"消费积压怎么排查？"答：先看消费速率是否小于生产速率（扩容消费者/提升单条处理效率），再看是否有慢查询/外部依赖拖慢，最后查是否有消息体过大或死信堆积。
