# MentorLoop 产品化与上线闭环蓝图

> 版本：v1.0（2026-08-18）  
> 定位：从“可演示的学习工具”走向“可对外收费、可持续运营的求职学习产品”的统一需求与验收基线。  
> 使用原则：**代码已经存在，不等于该能力可以对用户承诺；通过本文件的业务、合规、可观测和验收要求，才算上线。**

---

## 1. 产品定义与上线结论

### 1.1 要解决的问题

MentorLoop 面向准备技术岗位面试的学习者，提供“诊断 → 学习 → 练习 → 复盘 → 再验证”的闭环，而不是单纯的课程目录或题库。

产品的核心承诺应收敛为：

> 帮助用户识别当前技术能力缺口，给出可执行的学习与练习路径，并用考试和模拟面试验证提升结果。

### 1.2 目标用户与首发边界

| 用户 | 主要任务 | 首发承诺 |
|---|---|---|
| 应届生/转行求职者 | 补基础、刷题、准备面试 | 前端/后端/DevOps/AI 四方向的学习、题库、考试、错题复习 |
| 有 1–5 年经验的工程师 | 查漏补缺、面试冲刺 | 按技术子类找题、限时模拟、针对薄弱点复习 |
| 运营管理员 | 上新、修订内容、处理用户问题 | 内容/题库/用户/订单管理、审计可追溯 |

首发不应承诺真人 1v1 服务、保证 offer、自动续费、真实内推成功率或“AI 语音面试在所有设备稳定可用”。这些能力在具备人力、资质、SLA 与交付标准之前，只能作为内部规划，不得作为付费卖点。

### 1.3 当前成熟度判断

项目已经具备知识库、考试、错题、学习计划、后台 CRUD、订单/订阅数据模型及语音面试的较完整技术骨架；但仍属于 **Beta/受控试用阶段**，原因是：

1. 真实支付、退款、对账与客服处理尚未完成；sandbox 只能验证代码流程，不能构成交易闭环。
2. LLM、ASR、TTS 依赖外部密钥或降级路径，尚未形成可售服务的可用性、成本和故障承诺。
3. “简历诊断、内推、人工 1v1”等权益尚非完整交付物，不能混入已售套餐。
4. 文档中存在历史状态，必须以运行代码、测试、生产配置和本蓝图的验收记录为准。

**上线分级：**

| 等级 | 含义 | 可否收费 |
|---|---|---|
| 内测 | 指定用户、演示数据或 mock 可用 | 否 |
| 公测 | 免费核心学习闭环对公众开放，有明确 Beta 提示 | 否 |
| 正式免费版 | 免费承诺可稳定交付，隐私/安全/支持机制到位 | 可，但不售 VIP |
| 正式付费版 | 交易、权益、售后、成本、监控均闭环 | 是 |

当前建议目标：先达到“正式免费版”，再单独通过付费发布门槛。

## 2. 北极星与产品度量

### 2.1 北极星指标

**完成一次“诊断后提升验证”的周活跃学习者数。**

定义：用户在 7 天内完成一次考试或专项练习，至少查看一次复盘/学习建议，并在后续完成一次练习、考试或面试。

这比注册量、页面浏览量或单纯付费数更能衡量 MentorLoop 是否真的帮助用户提升。

### 2.2 漏斗指标

| 环节 | 关键事件 | 健康判定 |
|---|---|---|
| 获客 | landing_view、module_view | 可按来源/方向归因 |
| 激活 | register、first_section_done、first_practice | 注册后 24 小时至少完成一个核心动作 |
| 诊断 | exam_start、exam_submit、record_view | 考试能完整出分、复盘可访问 |
| 提升 | plan_view、section_from_plan、wrong_review | 薄弱点能回流到学习/练习 |
| 验证 | retake_exam、interview_finished | 可比较前后结果 |
| 付费（后置） | pay_create、pay_success、entitlement_used、refund | 所有状态可审计、可对账 |

所有事件至少携带 `userId(可为空)`、`sessionId`、`track`、`contentId/setId`、`source`、`occurredAt` 和版本号。不得记录简历正文、回答全文、密码、支付签名等敏感信息。

## 3. 必须成立的业务闭环

### 3.1 免费用户学习闭环（首发 P0）

```text
进入首页 → 选择方向 → 浏览课程/题目 → 注册登录
→ 完成小节或专项练习 → 开始限时模拟考试 → 提交与复盘
→ 识别薄弱点 → 跳转对应课程/错题复习 → 再次练习或重考
→ 成绩对比与阶段性建议
```

验收条件：

- 未登录用户可理解产品、浏览允许公开的内容；所有写操作必须清楚要求登录。
- 考试开始、倒计时、草稿、提交、重复提交、网络中断恢复均有确定行为；最终计时和分数以服务端为准。
- 每道错题至少包含题干、用户答案、正确答案/解析、知识标签、复习状态与下一次复习时间。
- 薄弱点必须能映射到真实课程或明确提示“暂未映射”，不能生成不存在的学习内容。
- 用户可在历史记录中查看成绩、用时、复盘与再次练习入口；同一试卷的重考记录不可覆盖旧记录。
- 重新考试后，应展示同卷/同方向的趋势，但不得用样本不足的数据宣称“能力提升”。

### 3.2 AI 模拟面试闭环（仅在服务能力就绪后 P1）

```text
选择方向/级别/岗位目标 → 告知 AI 与录音数据使用方式并取得同意
→ 开始面试 → 逐轮回答/追问/评分 → 结束报告
→ 薄弱标签与课程、题库关联 → 用户复习 → 再次模拟 → 对比报告
```

验收条件：

- 文字模式必须独立可用；语音/实时模式是增强能力，设备或厂商异常时可无损降级到文字输入。
- 开始前显示当前能力状态（文字、TTS、ASR、实时）和预计消耗；不向用户伪装 mock 结果或未配置服务。
- 一场面试有明确上限、可恢复/放弃规则、最终状态和可查看历史；重复请求不会创建重复会话或重复扣配额。
- 报告必须包含评分依据、做得好的点、待改进点、可执行任务和相关学习链接；不得将模型评分表述为招聘结论。
- 用户可删除面试记录及相关音频/转写；默认最小化存储，媒体设置自动清理周期。
- 必须配置：单用户限额、日成本上限、超时、重试、模型失败降级文案、内容安全与人工申诉入口。

### 3.3 VIP 付费闭环（达到正式付费版才开放）

```text
权益说明 → 选择套餐 → 创建订单 → 第三方支付
→ 服务端验签回调 → 幂等开通订阅 → 用户实时看到权益
→ 使用权益 → 到期提醒/续费（若有明确授权）
→ 退款/取消 → 权益回收或保留至到期 → 对账与客服闭环
```

状态机（必须写入数据库与审计日志）：

| 对象 | 合法状态/迁移 |
|---|---|
| 订单 | `pending → paid`；`pending → expired/canceled`；`paid → refunded/partially_refunded` |
| 订阅 | `active → expiring → expired`；仅在支付成功后 `inactive → active`；退款策略必须明确是否 `active → revoked` |
| 权益 | 按 `subscription.status + expireAt + entitlement` 实时计算，不以客户端缓存为准 |
| 退款工单 | `requested → reviewing → approved/rejected → processing → succeeded/failed` |

验收条件：

- 支付回调必须验证签名、金额、币种、商户订单号和订单状态；回调可重放但不得重复开通。
- 创建订单要有价格快照、套餐快照、用户、渠道、过期时间与幂等键；套餐变价不影响历史订单。
- “自动续费”默认关闭。若将来开放，必须有支付协议授权、显著告知、取消入口、扣款前提醒及独立状态记录。
- 每一项付费权益必须有可验证入口与使用记录。未交付的能力不可以 `implemented=true` 或出现在销售主文案中。
- 退款规则、电子凭证、客服入口、投诉处理时限、对账任务和异常人工补偿流程必须上线前确定。
- sandbox 接口在生产环境必须不可达；生产环境启动时若支付密钥/回调域名不完整，应拒绝开启购买。

### 3.4 内容运营闭环（P0）

```text
选题/来源 → 编辑草稿 → 专家审核 → 发布 → 用户学习/反馈
→ 数据与投诉监测 → 修订/下线 → 变更记录与复审
```

验收条件：

- 每个课程小节、题目、解析、试卷均有作者/来源、版本、状态（draft/review/published/archived）和最后复审日期。
- 管理台不能将无来源、无答案、无解析、无难度标签、无方向归属的题目直接发布。
- 发布、下架、批量改题、用户封禁、手工开通/退款均产生不可篡改审计日志。
- 错误内容有用户举报入口和处理 SLA；高风险错误可一键下线并保留历史证据。

### 3.5 账号、隐私与支持闭环（P0）

```text
注册/登录 → 验证身份 → 使用服务 → 修改资料/密码
→ 导出或删除数据 → 会话失效 → 客服/投诉处理 → 留痕与结案
```

验收条件：

- 生产环境不得返回短信/邮箱验证码；验证码通道、频控、有效期、失败次数、供应商告警可观测。
- 所有会话有过期、撤销、密码变更/封禁强制失效和设备管理策略。
- 隐私政策、服务协议、会员/退款规则在注册、上传简历、录音与支付前按场景展示并记录版本与同意时间。
- 账号删除要明确删除范围、保留法定账务记录的原因和期限；异步删除任务可追踪、可重试。
- 对外提供支持入口、问题分类、工单状态、响应 SLA；至少能处理登录、支付、内容错误、隐私删除四类问题。

## 4. 领域模型与数据责任

| 领域对象 | 关键字段/约束 | 责任 |
|---|---|---|
| 用户与会话 | 唯一身份、角色、封禁、同意记录、会话生命周期 | 鉴权与安全 |
| 内容 | 来源、版本、发布状态、复审日期、关联关系 | 内容运营 |
| 练习/考试 | attempt、服务端开始时间、答卷、评分版本、复盘 | 学习体验与可信统计 |
| 掌握度/错题 | 技能键、错因、复习计划、证据来源 | 个性化推荐 |
| AI 会话 | 模型版本、输入/输出摘要、配额、成本、删除期限 | AI 服务治理 |
| 订单/订阅/退款 | 金额快照、支付凭证、状态机、权益时间窗 | 财务与合规 |
| 审计/事件 | 操作人、对象、前后差异、请求关联 ID | 追责与排障 |

需要补齐的关键原则：业务表不以 JSON 作为唯一事实来源；重要状态变更放在事务中；所有外部回调、提交与开通操作有幂等键；金额始终以最小货币单位存储；时间统一 UTC 毫秒存储、按用户时区展示。

## 5. 上线门槛（Definition of Done）

### 5.1 正式免费版发布门槛：全部必须满足

1. **核心闭环**：3.1 全部验收通过；学习、考试、错题、历史记录和学习建议在真实账号下端到端验证。
2. **安全底线**：Cookie 安全属性、CSRF 策略、CSP、权限校验、限流、密码策略、验证码生产通道、日志脱敏、依赖漏洞扫描均有自动检查。
3. **数据可靠性**：迁移可从空库/旧库升级；每日备份可恢复演练；恢复点和恢复时间目标已记录。
4. **质量保障**：关键路径有单元、集成和浏览器 E2E；每次合并必须通过 lint/typecheck/test/build；不存在 P0/P1 未豁免缺陷。
5. **可观测性**：错误、性能、数据库、外部 AI/支付依赖、磁盘与备份均有监控告警；每个请求可用 request ID 串联日志。
6. **合规与支持**：隐私、协议、数据删除、内容举报、支持入口和故障公告页均可用。
7. **运营准备**：发布/回滚手册、值班人、故障分级、种子数据更新流程、内容审核责任人明确。

### 5.2 正式付费版额外门槛：全部必须满足

1. 真实支付在测试商户和生产小额真实交易中验证：支付成功、重复回调、关单、退款、异常金额、网络超时、对账全部通过。
2. 每个售卖权益可由独立验收用例证明已交付；销售页、订单页、协议、客服话术与实际能力完全一致。
3. 退款和投诉流程已演练，财务日对账差异为零或有明确处理单。
4. AI 服务已进行成本压测、限额验证、故障演练和提示词安全评估；不依赖 mock 作为生产结果。
5. 至少完成一次小范围灰度：观察支付成功率、权益开通延迟、退款率、核心功能使用率、客服工单后再全量发布。

## 6. 分期路线图与优先级

### Phase 0：产品基线与止血（1–2 周）

目标：将“看起来能用”变成“免费核心流程可信”。

- 建立需求编号、验收用例、缺陷分级和发布看板；清理历史文档状态，指定代码为事实源。
- 完成端到端核心流程测试：注册、登录、课程进度、考试、断网/重复提交、错题、账号删除、管理员权限。
- 生产配置隔离：禁止 DEV_CODE、mock 支付、mock ASR/TTS 误入生产；启动自检失败即拒绝对外服务。
- 内容质量首轮审计：随机抽检每方向课程、题库和试卷，修正错误/无来源/重复/错标签内容。
- 建立最小埋点、错误告警、备份恢复演练、发布与回滚 Runbook。

### Phase 1：正式免费版（2–4 周）

目标：把学习闭环做深、做稳。

- 考试历史趋势、错题 SRS、学习计划到课程/练习的回流、空状态与异常状态完整化。
- 课程与题目版本、审核、下架、举报/反馈工作流；后台增加草稿/发布权限边界。
- 完整的移动端、无障碍、性能、SEO 与浏览器兼容性验收。
- 账号与支持中心：资料、密码、会话、删除、工单/反馈、公告。

### Phase 2：受控 AI Beta（2–4 周）

目标：验证 AI 是否产生学习价值，而不是先包装成会员卖点。

- 先上线可靠文字面试；语音仅对已验证浏览器与地区灰度。
- AI 面试报告回流课程/错题，并记录模型版本、时延、失败率、单场成本。
- 简历能力从“文件解析”开始，先定义结构化诊断输出与用户确认；不承诺人工 1v1。
- 以完成率、复练率、用户满意度、成本为准决定是否进入付费权益。

### Phase 3：付费灰度与正式版（3–6 周，依赖资质）

目标：形成可审计的交易与权益闭环。

- 接入一个真实支付通道、支付通知验签、订单/订阅/退款/对账后台。
- 套餐只销售已完整交付的能力；权益按特性开关和订阅时间窗控制。
- 小流量灰度、客服预案、财务日结、退款演练完成后再全量开放。

### 暂缓项

- 真人 1v1 简历服务、内推撮合、自动续费、多支付渠道、多币种、企业版。它们的核心难点是服务履约、资质、风控和客服，而不是页面或数据库字段。

## 8. 发布治理

每一个版本发布必须有以下产物：

1. 需求范围与“不做什么”；
2. 关联的验收用例及执行结果；
3. 数据迁移、回滚和兼容方案；
4. 埋点与监控清单；
5. 用户可见文案/协议变更；
6. 风险、负责人、灰度比例和紧急下线开关；
7. 发布后 24 小时与 7 天复盘：错误率、完成率、投诉、成本、转化（如适用）。

禁止以“功能代码已合并”“页面可以打开”“本地 mock 通过”作为上线依据。

## 9. 需要产品负责人确认的决策

以下决策不应由工程实现自行假设：

1. 首发是否只做免费版；若收费，支付商户、退款规则、发票/凭证与客服责任人是谁？
2. AI 面试是否作为 Beta 功能还是售卖权益；单用户/单日成本上限是多少？
3. 用户数据（简历、面试文本、音频）的保留期、删除策略与第三方模型数据处理边界是什么？
4. 内容审核的负责人、来源标准、复审周期及用户举报 SLA 是什么？
5. 首发地区、部署方式、可接受的可用性目标、故障响应人和预算是什么？
6. 是否明确放弃真人 1v1 与内推服务，直到拥有可规模化的履约团队？

这些问题确认后，研发才能把本蓝图拆成确定的 PRD、技术设计、测试计划和迭代 Backlog。
