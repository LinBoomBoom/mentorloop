## 1. 网络分层与协议栈(OSI/TCP-IP)

> 引导：先建立“封装-解封装”的心智模型，理解每层解决什么问题、数据如何一层层打包。

## 心智模型
把网络想象成寄快递：你写一封信（应用数据），邮局按"信封格式"套一层地址（传输层 TCP/UDP 段），再套上"邮包标签"（网络层 IP 包），最后交给"运输车"发出（链路/物理层帧）。收件方一层层拆包还原。每一层只关心自己那层的事，这种"各管一层、逐层封装"就是协议栈的核心思想。

## 核心知识点（锚定官方）
- OSI 七层（物理/数据链路/网络/传输/会话/表示/应用）是概念模型；实际互联网采用 TCP/IP 四层（网络接口/网际 IP/传输 TCP·UDP/应用 HTTP·DNS 等），IETF 以 RFC 体系而非 OSI 为准。
- 数据单元：传输层叫"段(segment)"，网络层叫"包/数据报(packet/datagram)"，链路层叫"帧(frame)"；每层报头携带本层需要的控制信息（端口、IP、MAC）。
- 封装(encapsulation)与解封装：发送方自顶向下加报头，接收方自底向上剥离；路由器工作在网络层（看 IP），交换机在链路层（看 MAC），而 NAT 在传输层以上改写端口。

## 为什么重要
- 排障时"分层定位"是基本功：连不上先看物理/链路（ping、ARP），再看网络层（路由、防火墙），最后看应用层（证书、HTTP 状态码）。
- 理解边界决定架构：微服务间通常只见应用层（HTTP/gRPC），但性能瓶颈常在网络层 MTU、传输层拥塞或链路层丢包。
- 安全也是分层生效的：链路层有 MAC 过滤，网络层有 ACL，传输层有 TLS，应用层有鉴权，缺一不可。

## 常见坑
- 把"端口"当成网络层概念——端口是传输层(TCP/UDP)的，IP 是网络层的，MAC 是链路层的，别混层。
- 误以为 OSI 是互联网实际标准——面试/工程以 TCP/IP 模型为准，OSI 只是教学框架。
- 以为 MTU(1500) 是"包最大 1500 字节"——那是链路层帧载荷上限，IP 包超过会分片，TCP 则用 MSS 主动避免分片。

## 动手自测
1. 用 `tcpdump -i any icmp` 抓一次 ping，观察以太网头→IP 头→ICMP 的逐层结构。
2. 在 Wireshark 里对比一个 TCP 段与一个 HTTP 请求，指出端口号、IP、MAC 分别出现在哪层。
3. 解释"为什么 tracert 用 TTL 递增"——它正是利用网络层字段逐跳探测。

## 面试视角
- 高频："OSI 和 TCP/IP 区别？""数据从 A 到 B 经过哪些设备、改了哪些字段？"
- 加分点：能说清"路由器改 MAC 不改 IP、NAT 改 IP/端口不改应用数据"，并联系到实际排障顺序。
- 关联题：MTU/MSS、分片、NAT 穿透（打洞）都从这里发散。

## 2. TCP 可靠传输与连接管理

> 引导：吃透三次握手、FIN 关闭、序列号+确认、窗口流控与拥塞控制，这是网络面试的半壁江山。

## 心智模型
TCP 像一条"有签收的可靠传送带"：每箱货贴序号，对方收到回执(ACK)，没回执就重发；传送带太满时对方举"减速"牌(窗口)控流，整条线拥堵时双方自动放慢(拥塞控制)。三次握手是"先对表、再发货"的开局仪式。

## 核心知识点（锚定官方）
- 建立连接用三次握手(3WHS)：RFC 9293 §3.4–3.5 明确，客户端发 SYN(含初始序列号 ISN)→服务端回 SYN,ACK→客户端回 ACK，目的是"防止旧的重复连接初始化造成混乱"。
- 关闭用 FIN 握手：一方发 FIN+ACK，对方 ACK，对方再发 FIN，本端 ACK，进入 TIME-WAIT 必须停留 2×MSL（RFC 9293 §3.6.1），以保证最后 ACK 可达且旧报文消亡。
- 可靠性：每字节都有 32 位序列号，确认是"累积确认"(cumulative ACK)——ACK=X 表示 X 之前全部收到(RFC 9293 §3.4)；丢包靠序列号发现、靠重传纠正，段错误靠 checksum。
- 流量控制：头部 16 位 Window 字段声明"我还能收多少字节"(RCV.WND)，发送方据此不超出接收方缓冲。
- 拥塞控制：RFC 9293 指出这是 TCP 必需但细节在配套 RFC 5681——核心是慢启动(slow start，指数增窗到阈值)、拥塞避免(线性增窗)、快重传/快恢复，目标是"探测可用带宽而不压垮网络"。

## 为什么重要
- 几乎所有后端服务都跑在 TCP 上（HTTP/MySQL/Redis 连接），握手/挥手/丢包重传直接影响延迟与吞吐。
- TIME-WAIT 过多会占满端口（高并发短连接服务的经典坑）；窗口与拥塞控制决定了长肥管道(高带宽高延迟)的利用率。
- 理解这些才能解释线上现象：为什么首次请求慢(握手+慢启动)、为什么偶发超时(丢包重传)、为什么重启服务偶尔绑定端口失败(2MSL)。

## 常见坑
- 以为"三次握手是防止黑客"——它防的是"旧重复连接初始化"，不是安全攻击；安全靠 TLS。
- 以为 TIME-WAIT 只在被动关闭方——主动关闭方才会进入 TIME-WAIT，被动方是 CLOSE-WAIT→LAST-ACK。
- 混淆流量控制与拥塞控制：前者是"接收方能力"的端到端控流，后者是"网络带宽"的拥塞避免，机制不同。
- 把 MSL 当成固定秒数——实际实现可调，常见 30s/60s/120s，2MSL 即 1~4 分钟。

## 动手自测
1. `ss -tan | grep TIME-WAIT | wc -l` 看本机 TIME-WAIT 数量；压测一个短连接服务观察其增长。
2. `ss -tan` 观察一条连接从 ESTABLISHED→FIN-WAIT→TIME-WAIT 的状态迁移。
3. 用 Wireshark 抓三次握手，核对 SYN 的 Sequence 与 ACK 的确认号关系(确认号=对端序列号+1)。

## 面试视角
- 必考："三次握手为什么是三次不是两次？""TIME-WAIT 为什么是 2MSL？""流量控制和拥塞控制的区别？"
- 加分：能讲慢启动指数→拥塞避免线性的拐点(ssthresh)、快重传如何避免等 RTO、BBR 与传统 Reno 的差异。
- 场景题："服务端 TIME-WAIT 爆了怎么处理？"(SO_REUSEADDR/REUSEPORT、连接池、长连接)。

## 3. UDP 与传输层选择

> 引导：理解无连接、不可靠但低延迟的特性，看清 TCP vs UDP 的取舍场景。

## 心智模型
UDP 像"发短信广播"：发出去就不管对方收没收到，没有握手、没有重传、没有顺序保证，但极快、极轻。适合"丢一两帧无所谓、卡顿才要命"的场景。

## 核心知识点（锚定官方）
- RFC 768 定义 UDP：无连接、不保证交付、不保证顺序、不保证去重；头部仅 8 字节(源/目的端口、长度、校验和)，远轻于 TCP 20 字节起步。
- 无拥塞控制、无流控，发送方可以按应用速率直接灌——这是低延迟来源，也是它"会丢会乱"的原因。
- 支持广播(multicast/broadcast)与一对一，TCP 只能点对点单播。

## 为什么重要
- 实时音视频、直播、游戏同步、DNS 查询、健康探测等"宁可丢包不可延迟"的场景，UDP 是首选。
- QUIC/HTTP3 直接建在 UDP 之上（绕过 TCP 队头阻塞与握手），是现代传输层演进方向。
- 理解 UDP 才能正确选型：强一致、可靠传输用 TCP；实时、可容忍少量丢失用 UDP。

## 常见坑
- 以为"UDP 不可靠所以不能用"——很多系统靠应用层重传/前向纠错补可靠性（如 WebRTC、QUIC）。
- 以为 UDP 一定比 TCP 快——在丢包网络里 UDP 可能因无重传导致大量重发请求，反而更慢。
- 在 NAT 后直接用 UDP 需处理"打洞"与映射失效，比 TCP 复杂。

## 动手自测
1. `dig +short example.com` 走 UDP 53，抓包看请求/响应是否单次往返。
2. 写个 UDP 回显：故意不处理乱序，观察接收顺序与发送顺序不同。
3. 对比 `iperf3 -u`(UDP) 与 TCP 模式在弱网下的吞吐与丢包表现。

## 面试视角
- "TCP 和 UDP 区别？各适合什么场景？"
- 加分：能说"为什么 DNS 用 UDP（小包、要快、可重试）""QUIC 为什么选 UDP（避免改内核 TCP）"。
- 陷阱题："UDP 能不能做可靠传输？"(能，应用层实现，如 KCP/QUIC)。

## 4. HTTP 协议与状态码/缓存

> 引导：掌握方法的安全/幂等语义、状态码分类与条件缓存，这是 Web 后端天天打交道的协议。

## 心智模型
HTTP 是"客户端问、服务端答"的请求-响应协议，像点餐：你报菜名(方法+URL)、说忌口(头)；厨房按单做菜(状态码)、附小票(响应头)；缓存像"常点的菜提前备好"，省得每次现做。

## 核心知识点（锚定官方）
- RFC 9110(HTTP Semantics) 定义方法语义：GET/HEAD 安全且 GET 幂等；PUT/DELETE 幂等；POST/PATCH 非幂等；OPTIONS 探测能力。安全=不修改服务器状态，幂等=多次同样请求效果相同。
- 状态码分五类：1xx 信息、2xx 成功(200/201/204)、3xx 重定向(301 永久/302 临时/304 未改/307/308 保留方法)、4xx 客户端错(400/401/403/404/409/422/429)、5xx 服务端错(500/502/503/504)。
- 缓存：RFC 9111(HTTP Caching) 规定 Cache-Control(max-age/no-cache/no-store/private/public)、验证器 ETag/Last-Modified，客户端用 If-None-Match/If-Modified-Since 发条件请求，命中则返回 304 不重传实体。
- HTTP/2(RFC 9113) 多路复用、头部压缩(HPACK)、服务端推送；HTTP/3(RFC 9114) 跑在 QUIC/UDP 上。

## 为什么重要
- 后端每天写接口、定状态码、配缓存，语义错会误导客户端（如把 200 当成功却带 error 字段、该 301 用 302 导致 SEO 丢权重）。
- 缓存配置直接决定 CDN/网关命中率与带宽成本；幂等性决定重试是否安全（支付/下单接口必须幂等）。
- 理解 4xx/5xx 分布是线上质量仪表盘的核心。

## 常见坑
- 用 POST 实现本应幂等的"查询/删除"，导致重试引发重复副作用。
- 把 401(未认证) 和 403(无权限) 混用；把 429(限流) 当 500 处理。
- 缓存不加 Cache-Control 或 ETag，造成"改了不生效"或"每次全量回源"。
- 以为 3xx 都"保留方法"——301/302 历史上会改方法，307/308 才严格保留。

## 动手自测
1. `curl -i https://httpbin.org/get` 看响应头与状态码；`curl -I` 看 HEAD 是否无响应体。
2. 用 `curl -H "If-None-Match: xxx"` 触发 304；对比有/无缓存头的耗时。
3. 故意让接口返回 200 但业务失败，讨论为什么"用状态码表达结果"更利于监控。

## 面试视角
- "GET 和 POST 区别？""哪些方法是安全的/幂等的？""301 vs 302 vs 307？"
- 加分：能从语义层解释"为什么幂等接口才能重试""429 与熔断降级的关系"。
- 关联：HTTP 跑在 TCP 上→连接复用(keep-alive)→HTTP/2 多路复用→HTTP/3 换 QUIC。

## 5. HTTPS 与 TLS 握手

> 引导：理解 TLS 如何用一次性密钥交换+证书+AEAD 提供机密性/完整性/认证。

## 心智模型
HTTPS = HTTP + TLS，TLS 像"在公开电话线上套了个防窃听加密筒"：双方先交换一次性密钥((EC)DHE)，再用证书确认对方身份，之后所有内容用 AEAD 加密。即使线路被窃听，黑客也只看到密文。

## 核心知识点（锚定官方）
- TLS 1.3 规范为 RFC 8446；其在 QUIC 中的应用见 RFC 9001。握手由客户端 ClientHello 发起，服务端 ServerHello 响应。
- 密钥交换：支持 (EC)DHE(椭圆曲线/有限域 Diffie-Hellman) 与 PSK；DHE 提供前向安全(forward secrecy)——密钥销毁后历史流量不可解密。
- 认证：服务端须被客户端认证，通常用 X.509 证书(RFC 5280)链到可信 CA；客户端可选认证。Finished 消息的校验保证握手消息未被篡改。
- 加密：用协商的 AEAD(如 TLS_AES_128_GCM_SHA256) 同时提供机密性+完整性，带 16 字节认证标签。
- 两种模式：1-RTT 完整握手；0-RTT(早期数据)可立即发应用数据，但可能被重放，故不适合带副作用的请求(RFC 9001 §2.2)。

## 为什么重要
- 所有对外接口、支付、登录都必须 HTTPS；理解握手才能解释"首次连接慢""证书过期导致失败""混合内容被拦"。
- 前向安全决定"私钥泄露后历史流量是否安全"——现代合规(如 PCI)要求开启。
- 0-RTT 与性能权衡、证书链与 OCSP 装订(stapling)是运维高频话题。

## 常见坑
- 以为"有 HTTPS 就绝对安全"——TLS 只保护传输，不防应用层漏洞(XSS/SQLi)、不防服务端被入侵。
- 以为 0-RTT 能随便用——它会重放，绝不能用于下单/转账类请求。
- 证书链不完整(缺中间证书)导致部分客户端不信任；自签证书仅测试可用。
- 把 TLS 1.2 当新标准——1.3 已大幅简化握手、移除不安全的静态 RSA 密钥交换。

## 动手自测
1. `openssl s_client -connect example.com:443` 看证书链、协议版本、密码套件。
2. `curl -v https://example.com` 观察 TLS 握手阶段(TLSv1.3, cipher)。
3. 用 SSL Labs 测试某站点评级，对照"为什么丢了 A+"(启用 1.3、HSTS、OCSP stapling)。

## 面试视角
- "HTTPS 怎么保证安全？""TLS 握手过程？""什么是前向安全？"
- 加分：能讲对称加密(快、密钥分发难) vs 非对称(慢、解决分发) 的混合使用、证书链校验流程、1-RTT/0-RTT 取舍。
- 关联：TLS 跑在 TCP(1.2/1.3) 或 QUIC/UDP(HTTP3) 之上。

## 6. DNS 与域名解析

> 引导：看懂从域名到 IP 的递归/迭代解析链路，以及记录类型与缓存对性能的影响。

## 心智模型
DNS 是"互联网的电话簿"：你把"www.example.com"交给查号台，它从根→顶级域(.com)→权威服务器一层层问，最终翻出 IP。本地还会把结果记一段时间(TTL)免得每次都问。

## 核心知识点（锚定官方）
- DNS 规范 RFC 1034(概念架构)/1035(实现)，使用 UDP 53(大响应回退 TCP)。
- 解析流程：浏览器缓存→系统 hosts→本地 DNS 解析器→(递归)根服务器→TLD 服务器(.com)→权威 NS 服务器→返回 A/AAAA 记录 IP。
- 关键记录类型：A(IPv4)/AAAA(IPv6)/CNAME(别名)/MX(邮件)/TXT(校验如 SPF)/NS(授权)。
- 递归 vs 迭代：客户端到本地解析器是递归(它替你问到底)；解析器到根/TLD/权威是迭代(各回下一步该问谁)。
- TTL 决定缓存时长；负缓存(查不到也缓存)减少无效查询。

## 为什么重要
- 域名解析是请求的第一跳，解析慢/失败直接让用户"打不开"；TTL 设置影响发布/切流速度。
- 故障转移靠改 DNS(或配合健康检查)；CDN 通过 CNAME/智能解析把用户导向最近节点。
- DNS 缓存投毒、劫持是常见安全问题，理解解析链才能定位和防护。

## 常见坑
- TTL 设太长导致"切 IP 后老用户半天不生效"；设太短又加重解析器负担。
- 以为 CNAME 能套在根域名(apex)——根记录不能是 CNAME，需用 ALIAS/ANAME 或 CDN 方案。
- 忽略递归解析器的缓存与转发链路，排障只看权威侧。
- 把 hosts 改了却忘记刷新(或浏览器缓存)导致"改了不生效"假象。

## 动手自测
1. `dig +trace example.com` 看从根到权威的完整迭代链路。
2. `nslookup -type=MX gmail.com` 查邮件记录；`dig +short` 看精简结果。
3. 故意把 TTL 设小，观察修改 A 记录后不同递归服务器的生效时间差。

## 面试视角
- "从输入 URL 到页面显示，DNS 起什么作用？""递归和迭代区别？""为什么 DNS 用 UDP？"
- 加分：能讲 DNS 缓存层级、TTL 与发布策略、DNS 劫持/投毒(及 DNSSEC 防护)。
- 关联：解析结果喂给 TCP 连接(拿到 IP+端口)→才进入握手。

## 7. IO 模型(阻塞/非阻塞/多路复用/异步)

> 引导：用“少量线程管海量连接”的视角，对比 BIO/multiplexing/AIO 与 Reactor 模式。

## 心智模型
传统"一连接一线程"像给每个顾客配一个服务员，人多了服务员不够(BIO 撑不住 C10K)。IO 多路复用像"一个服务员盯一整片呼叫器"，谁就绪就服务谁；异步 IO 则是"菜好了系统主动通知你"，彻底不阻塞。

## 核心知识点（锚定官方）
- 阻塞 IO(BIO)：read 直到数据到达才返回，一连接占一线程，线程上下文切换成本高，难扩展。
- 非阻塞 IO：read 立即返回(有数据读数据，无数据返回 EWOULDBLOCK)，需应用轮询，CPU 空转。
- IO 多路复用：select/poll 遍历所有 fd 找就绪者(O(n))；Linux epoll(epoll(7) man page) 用内核事件表，就绪事件 O(1) 回调，支持边缘(ET)/水平(LT)触发，是高并发基石。
- 异步 IO(AIO / io_uring)：内核完成 IO 后通知应用，全程不阻塞；Linux 上 io_uring 是新一代高性能异步接口。
- Reactor 模式：事件循环 + 多路复用，单 Reactor 单线程、单 Reactor 多线程、主从 Reactor(Netty 采用) 逐级拆分。Java NIO 的 Selector(Oracle Javadoc) 即"多路复用器"，一个线程监控多个 SelectableChannel 的 OP_READ/WRITE/CONNECT/ACCEPT 就绪。

## 为什么重要
- C10K/C10M 问题本质就是 IO 模型选择；现代网关、消息中间件、数据库驱动都建立在多路复用之上。
- 选错模型：BIO 撑高并发会线程爆炸；纯轮询浪费 CPU；epoll/io_uring 才能用少量线程扛海量连接。
- 理解 Reactor 才看得懂 Netty、Redis、Nginx 的单线程/多进程事件循环架构。

## 常见坑
- 在 epoll 的 ET(边缘触发)模式下"一次没读干净就丢事件"——ET 必须循环读到 EAGAIN。
- 把"非阻塞"当"异步"——非阻塞是立刻返回(可能没数据)，异步是完成后回调，二者不同。
- 阻塞在 Selector 线程里做重计算，拖垮整个事件循环(Reactor 线程不能干重活)。
- 误以为多路复用"并行处理"——它只是"并发发现就绪"，真正的并行靠多线程/多 Reactor。

## 动手自测
1. 用 Java NIO 写个单线程 EchoServer：一个 Selector 同时 accept+read 多个客户端。
2. 对比 `strace` 下 select/poll 与 epoll 在 1000 个空闲连接下的系统调用次数。
3. 在 ET 模式故意只读一次，复现"收不全"bug，再改成循环读到 EAGAIN 修复。

- "BIO/NIO/AIO 区别？""select/poll/epoll 区别？""什么是 Reactor？"
- 加分：能讲 ET vs LT、epoll 为什么 O(1)、io_uring 相对优势、Netty 主从 Reactor 线程模型。

## 8. 网络编程与高性能 IO(Socket/NIO/零拷贝)

> 引导：落到 Java NIO/Netty 与零拷贝，理解高并发服务端的 IO 骨架与调优点。

## 心智模型
高性能网络服务的骨架就是"事件循环 + 缓冲 + 零拷贝"：用 Reactor 接活，用 ByteBuf 搬运数据，用零拷贝跳过"内核→用户→内核"的多余来回，让数据尽快抵达目的地。

## 核心知识点（锚定官方）
- Java NIO 三件套：Channel(双向通道)、Buffer(结构化字节容器)、Selector(多路复用)，构成非阻塞 IO 基础(Oracle java.nio 文档)。
- Netty：在 NIO 之上封装 EventLoop(事件循环)、ChannelPipeline(责任链处理器)、ByteBuf(池化、读写指针分离的可扩缓冲)，是事实上的 Java 高性能网络框架。
- 零拷贝：sendfile(文件→socket 不经过用户态)、mmap(文件映射到内存)；Java 中 FileChannel.transferTo 在 Linux 走 sendfile，Kafka/Netty 借此避免多次拷贝。
- 背压(Back-pressure)：消费慢时由下游向上游传递限速信号，防止缓冲无限堆积(OOM)；Netty 用 writable 水位、Reactive 流用 request(n)。
- 调优点：TIME-WAIT 回收(tcp_tw_reuse)、端口范围、文件描述符上限(ulimit)、缓冲区大小、连接池与长连接减少握手开销。

## 为什么重要
- 网关、RPC、消息队列、数据库代理的吞吐天花板基本由这套 IO 骨架决定。
- 零拷贝能显著降低 CPU 与内存带宽占用，是大数据传输(文件服务、日志收集)的关键优化。
- 背压设计错误会导致连锁雪崩(OOM→Full GC→超时→重试风暴)。

## 常见坑
- 在 Netty 的 channelRead 里做同步阻塞调用(查库/HTTP)，卡死 EventLoop。
- ByteBuf 不 release 导致堆外内存泄漏(Netty 用引用计数，须配对 release)。
- 误以为 transferTo 一定零拷贝——跨文件系统或老内核可能退化，需实测。
- 调大连接数却忘了 ulimit 与 ephemeral 端口范围，出现"bind 失败/端口耗尽"。

## 动手自测
1. 用 Netty 写个 HTTP 文件服务器，对比加不加零拷贝(transferTo)的吞吐差异。
2. 故意不 release ByteBuf，用 `-Dio.netty.leakDetectionLevel=PARANOID` 抓泄漏。
3. 压测时观察 `ss -s` 的 TCP 内存/端口与 `cat /proc/sys/fs/file-nr` 的文件描述符使用。
