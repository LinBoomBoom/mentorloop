## 1. 微服务是什么：从单体到微服务的权衡

> 引导：建立微服务的本质心智——按业务边界拆成可独立部署的小服务，并说清它换来了什么、失去了什么。

## 心智模型
把微服务想成「一家拆成多个专科诊所」：每个诊所只管一类病（单一职责），病人（请求）先在分诊台（网关）登记，再被转介到对应诊所；诊所之间不共用病历柜，而是通过转诊单（消息/接口）沟通。单体应用则像一家啥都看的全科医院——初期方便，但人多了走廊（代码）就堵死。微服务的本质是把「一个大家伙」按业务边界切成「多个能独立开发、部署、扩容的小家伙」。

## 核心知识点（锚定官方）
Martin Fowler 对微服务的经典定义强调「通过服务拆分组织并围绕业务能力构建、自动化部署、去中心化治理」。Spring Cloud 项目页明确定位：它提供「构建分布式系统常见模式（配置管理、服务发现、断路器、智能路由、微代理、控制总线）」的工具集。关键收益是独立部署与独立扩容；代价是分布式固有的网络不可靠、数据一致性难、运维复杂。不是「拆得越细越好」，而是按业务边界（DDD 限界上下文）切分。

## 为什么重要
面试几乎必问「为什么用微服务 / 和单体区别」——这是架构观的试金石。实际工作中，拆不好会比单体更糟：跨服务调用把延迟和故障放大、分布式事务把一致性变难。能说清「什么时候该拆、拆了失去什么」，比背组件列表重要得多。它决定了你后续所有选型（注册中心、网关、事务方案）的出发点。

## 常见坑
- 按「技术层」拆（用户服务/订单服务混着拆成 controller 服务、dao 服务），导致一次请求跨七八个服务，延迟爆炸。应「按业务能力」拆。
- 过早微服务：团队小、业务不稳时就上全套，运维成本压垮迭代速度。
- 共享数据库：服务间直接连同一个库，等于用数据库做耦合，微服务名存实亡。
- 忽视分布式本质：把单体里「方法调用一定成功」的假设照搬，忘记网络会失败。

## 动手自测
1. 给你一个「电商」场景，列出你认为是合理限界上下文的服务（如用户、商品、订单、库存、支付），并说出哪两个之间最容易产生分布式事务。
2. 画一张图：单体应用 vs 微服务，在「部署频率、故障爆炸半径、跨模块调用成本」三个维度上各有什么不同。

## 面试视角
高频题：「微服务有什么优缺点？什么时候该用？」标准答法：先讲单体的瓶颈（部署耦合、技术栈绑定、扩容粒度过粗），再讲微服务收益（独立部署/扩容/团队自治），最后补代价（网络、一致性、运维、分布式事务）并强调「取决于团队规模与业务稳定性」。能主动说出「康威定律（系统结构映射组织结构）」是加分项。

## 2. 服务拆分原则：限界上下文与单一职责

> 引导：讲清怎么拆才合理——沿业务能力（DDD 限界上下文）下刀，而非按技术层或组织关系。

## 心智模型
拆服务像切蛋糕：切少了（一个大服务）没意义，切多了（一个方法一个服务）反而黏成一团。好切法是沿「业务变化的边界」下刀——两块业务如果总是一起改、一起上线，就该放一个服务；如果改一个不影响另一个，就该分开。DDD 的「限界上下文」就是这把刀的刻度。

## 核心知识点（锚定官方）
DDD（领域驱动设计）用「限界上下文（Bounded Context）」界定模型的适用边界，每个上下文内术语一致、对外通过「上下文映射」交互。拆分原则可归纳为：单一职责（一个服务一个业务能力）、高内聚低耦合（频繁一起变的逻辑放一起）、团队粒度（康威定律：团队结构决定系统结构）。Spring Cloud 不规定怎么拆，只提供拆开后的「连接工具」——这正是它定位为「模式工具集」而非「架构圣经」的原因。

## 为什么重要
拆分粒度直接决定系统的可维护性与故障半径。粒度太粗，微服务退化为「分布式单体」；太细，服务数爆炸、调用链超长、排障绝望。工作中大量「微服务失败」案例根因在拆分阶段，而非技术选型。能基于业务边界给出拆分方案，是 senior 与 junior 的分水岭。

## 常见坑
- 共享库耦合：把实体类打成 common.jar 所有服务依赖，一改全升，等于隐式强耦合。
- 数据库共享：见第 1 节，服务应有各自的数据存储（数据库 per service）。
- 按组织汇报关系而非业务流拆，导致核心链路跨多个不协作的团队。
- 忽视「聚合根 / 领域事件」，把领域建模退化成 CRUD 表映射。

## 动手自测
1. 设计一个「外卖平台」的服务拆分，要求至少写出 6 个服务，并标注哪两个之间会产生「下单减库存」的跨服务调用。
2. 什么信号说明你拆太细了？（提示：一次用户操作触发 >5 次同步 RPC、链路追踪图比组织架构图还复杂。）

## 面试视角
「如何做服务拆分？」答法：从业务能力/限界上下文出发 + 单一职责 + 高内聚低耦合，并点出「数据库私有」与「避免共享库」。进阶可提「绞杀者模式（Strangler Fig）」——在单体外包一层逐步替换，而非一次性重写。能区分「逻辑拆分」与「物理拆分」更显老练。

## 3. 服务注册与发现：DiscoveryClient 与负载均衡

> 引导：锚定 Spring Cloud 官方：classpath 自动注册、按服务名寻址、LoadBalancer 解析实例。

## 心智模型
服务多了，谁在哪台机器、端口多少，不能写死在代码里（今天 A 在 10.0.0.3:8080，明天容器漂移到 10.0.0.9:31022）。注册中心就是「公司的内部通讯录」：每个服务启动时把自己的地址「登记」进去，调用方「查通讯录」拿到地址再打。这样扩缩容、故障迁移对调用方透明。

## 核心知识点（锚定官方）
Spring Cloud Commons 提供 `DiscoveryClient` 抽象：只要某个 `DiscoveryClient` 实现（Eureka / Consul / Zookeeper / Nacos）在 classpath 上，应用**默认自动注册**到远端注册中心（可通过 `spring.cloud.service-registry.auto-registration.enabled=false` 关闭）。调用方通过**服务名（虚拟主机名）而非 host:port** 发起请求，如 `restTemplate.getForObject("http://stores/...", ...)`；`Spring Cloud LoadBalancer` 基于 DiscoveryClient 获取的实例列表，把服务名解析为真实物理地址，并提供轮询/随机算法。官方文档明确 URI「需要使用虚拟主机名（即服务名，而非主机名）」。

## 为什么重要
没有服务发现，微服务就是一堆写死 IP 的单体——失去动态扩缩容与故障转移能力。这是「微服务能跑起来」的基础设施之一，面试常考「Eureka 原理 / 和 Nacos 区别 / 注册中心挂了怎么办」。理解 classpath 自动注册与服务名寻址，能解释为什么加个 starter 就能用。

## 常见坑
- 把服务名当主机名直接配到 nginx 或浏览器——服务名只在内部 LoadBalancer 解析，外部不认识。
- 注册中心与健康检查脱节：实例已宕机但注册信息未剔除，调用方打到死节点。
- 客户端缓存实例列表太久，扩缩容不生效；或太短，注册中心被打爆。
- 把注册中心当配置中心用（职责错位）。

## 动手自测
1. 在 classpath 引入 `spring-cloud-starter-netflix-eureka-client` 后，应用启动时发生了什么？（提示：自动注册 + 拉取实例列表 + 定时心跳。）
2. 注册中心整个宕机，已运行的服务还能互相调用吗？为什么？（提示：客户端通常有本地缓存，但无法发现新实例。）

## 面试视角
「Eureka 和 Nacos 有什么区别？」可从 CAP 切入：Eureka 偏向 AP（可用性优先，弱一致），Nacos 可切换 CP/AP。也可问「服务下线为什么不是立刻生效」（自我保护机制 / 心跳超时 / 客户端缓存）。重点展示「服务名→实例列表→负载均衡寻址」这条链路的理解。

## 4. 配置中心：外部化配置与动态刷新

> 引导：讲清配置与代码解耦、环境隔离、git 后端、@RefreshScope 动态刷新。

## 心智模型
配置中心像「全公司的公告板」：数据库连接串、开关开关、限流阈值这些「随环境变、但代码不该写死」的东西，统一贴到公告板上。服务启动时来看一眼，改了还能被通知「公告更新了，请重新读」。这样改个阈值不用重新打包上线。

## 核心知识点（锚定官方）
Spring Cloud Config 官方定位为「以 git 仓库为后端的集中式外部化配置管理」，配置资源直接映射到 Spring `Environment`，也能被非 Spring 应用使用。它的核心思想是：配置与代码分离、环境差异化（dev/test/prod 同一份代码不同配置）、版本化（git 历史即配置历史）。配合 `@RefreshScope` 与 `actuator/refresh` 端点（或 Spring Cloud Bus 广播），可在不重启的情况下动态刷新 Bean。这与第 3 节注册发现、第 5 节网关共同构成 Spring Cloud 三大基石。

## 为什么重要
没有配置中心，配置散落在各服务的 application.yml，改一处要发十次版，且敏感信息（密码）易泄露进代码仓库。它是「环境无关部署」和「动态调参（如限流阈值热更新）」的前提，也是合规审计（谁改了什么配置）的基础。

## 常见坑
- 把密钥明文放 git 配置仓库——应使用加密（Config Server 的 `{cipher}` 或 KMS / Vault）。
- `@RefreshScope` 用错位置：加在 `@Scheduled` 或某些代理 Bean 上不生效，且刷新会产生新代理实例，注意有状态 Bean 的重建副作用。
- 配置中心挂了导致服务起不来——应允许本地 fallback 或启动时缓存。
- 环境配置（如密码）提交到公共仓库分支。

## 动手自测
1. 为什么「配置中心」和「注册中心」不能互相替代？（提示：一个管「地址在哪」，一个管「参数是什么」。）
2. 改了配置中心的限流阈值，如何让正在运行的服务生效而不重启？列出你知的两种机制。

## 面试视角
「配置中心解决了什么问题？」答：配置与代码解耦、环境隔离、动态刷新、版本可追溯。追问「敏感配置怎么保护」答加密/KMS。能对比「本地配置 vs 配置中心 vs 环境变量（K8s ConfigMap/Secret）」体现工程视野。

## 5. API 网关：Gateway 的路由模型与边缘职责

> 引导：锚定官方：Route=ID+URI+Predicate+Filter，响应式非阻塞，统一出入口。

## 心智模型
API 网关是「大楼的前台 + 总机」：所有外部访客（客户端）只跟前台打交道，前台负责查证件（鉴权）、指路（路由）、限流（一次放几个人进）、记日志。后端各个微服务躲在后面，不直接暴露给外网。没有网关，每个服务都得自己装门禁、自己写路由，重复又易漏。

## 核心知识点（锚定官方）
Spring Cloud Gateway 官方定义：基于 Spring Boot、Spring WebFlux、Project Reactor 构建的**响应式、非阻塞** API 网关，运行于 Netty（不能在传统 Servlet 容器/WAR 中跑）。核心模型是 **Route（路由）= ID + 目标 URI + 一组 Predicate（断言）+ 一组 Filter（过滤器）**：当断言聚合为 true 时路由匹配；Predicate 基于 HTTP 请求属性匹配（Path、Method、Header、Host、Query）；Filter 在转发前后修改请求/响应（如 AddRequestHeader、RewritePath）。客户端只与网关交互，由网关统一承担安全、监控、弹性等横切关注点。

## 为什么重要
网关是微服务的「统一出入口」，承担路由、认证、限流、灰度、日志、CORS 等边缘职责。它是系统安全边界与流量入口，也是面试「微服务架构怎么落地」必画的一层。理解 Route/Predicate/Filter 三元模型，就能读懂任何网关配置。

## 常见坑
- 把网关写成「巨型转发器」，把业务逻辑塞进 Filter——网关只做横切，业务下沉到服务。
- 网关单点：应多实例 + 前置 LB，且网关本身不能成为性能瓶颈（响应式选型正是为此）。
- Predicate 顺序/通配导致错误路由（如 `/api/**` 吞掉更具体的 `/api/v2/**`）。
- 在网关做重 JWT 校验但没统一异常，下游 500 被网关包装后丢失语义。

## 动手自测
1. 写一个 Gateway 路由：把所有 `/order/**` 请求转发到 `lb://order-service`，并加上请求头 `X-Source: gateway`。给出 Route/Predicate/Filter 的对应。
2. 为什么 Gateway 要选 WebFlux/Netty 而非传统 Servlet？（提示：非阻塞、高并发连接、避免线程被慢下游耗尽。）

## 面试视角
「网关能做什么 / 和 Nginx 区别？」答：网关是应用层（L7）的、可编程的、与微服务生态集成的路由（能解析服务发现、注入鉴权、集成限流）；Nginx 是通用反向代理，规则静态。能说出「Predicate 匹配 + Filter 链式处理」即到位。

## 6. 熔断、限流与容错：Resilience4j 状态机

> 引导：锚定官方：CLOSED/OPEN/HALF_OPEN 三态转换与阈值，以及限流、舱壁、重试。

## 心智模型
熔断器像「家里的总闸 + 漏电保护」：某个下游服务开始疯狂超时（像电路过载），与其让每个请求都傻等直到线程池耗尽，不如先「跳闸」——直接快速失败，给下游喘息时间，过会儿再「半开」试一下，好了再合上。限流则是「门口限流栏」：单位时间内只放 N 个请求进，多余的排队或拒掉，保护系统不被洪峰冲垮。

## 核心知识点（锚定官方）
Resilience4j CircuitBreaker 是**有限状态机**，含三种常态：CLOSED、OPEN、HALF_OPEN。官方明确：当失败率 ≥ 阈值（默认 failureRateThreshold=50%）或慢调用率 ≥ 阈值时，从 CLOSED→OPEN 并短路调用（`CallNotPermittedException`）；经过 `waitDurationInOpenState`（默认 60000ms）后转 HALF_OPEN，允许 `permittedNumberOfCallsInHalfOpenState`（默认 10）个试探调用；若试探失败率仍高则回 OPEN，低于阈值则回 CLOSED。需满足 `minimumNumberOfCalls`（默认 100）才计算比率。此外还有 RateLimiter（限流）、Bulkhead（舱壁隔离）、Retry（重试）等模块。

## 为什么重要
分布式系统中「一个慢依赖拖垮整条链路」是头号事故源。熔断+限流+隔离是系统韧性的三件套，也是面试「如何保证高可用 / 雪崩怎么防」的核心答案。光会用注解不够，要懂状态机与阈值含义，才能调参而非盲配。

## 常见坑
- 把熔断阈值配得极低（如失败 1 次就开），正常抖动即误熔断。
- 熔断后没有 fallback，直接把异常抛给用户而非降级响应。
- 限流只限入口不限下游并发，下游仍被打满。
- 在熔断的 OPEN 期重试风暴——应配合退避（Retry 的 backoff）而非立即重试。
- 把超时设得比下游 SLA 还长，熔断形同虚设。

## 动手自测
1. 画出 CLOSED→OPEN→HALF_OPEN→CLOSED 的状态转换图，并标注每次转换的触发条件（失败率/等待时长/试探结果）。
2. 限流、熔断、舱壁三者分别防的是什么？（提示：洪峰 / 级联失败 / 单依赖耗尽全部线程。）

## 面试视角
「熔断和降级区别？」「雪崩怎么防？」答：熔断是故障时的快速失败开关（状态机），降级是熔断/异常时的兜底逻辑（返回缓存/默认值），限流是事前流量整形。能结合 Resilience4j 状态机与「超时+重试+隔离」组合讲，是稳定性方向的加分项。

## 7. 服务间通信：REST/OpenFeign 与异步消息

> 引导：对比同步（简单但阻塞、可用性乘性下降）与异步（解耦削峰、最终一致）的选型。

## 心智模型
服务间「说话」有两种腔调：一种像打电话（REST/HTTP，问一句答一句，同步，等对方回）；另一种像发邮件/留言（消息队列，发完就走，对方有空再处理，异步）。OpenFeign 是把「打电话」这事发声明式地写好——你只写接口，框架帮你拼请求。选哪种腔调，取决于「调用方要不要等结果」。

## 核心知识点（锚定官方）
Spring Cloud OpenFeign 通过自动配置与绑定到 Spring Environment，为 Boot 应用提供声明式 HTTP 客户端：用 `@FeignClient("service-name")` + 接口方法即可发起跨服务调用，底层由 LoadBalancer 解析服务名。同步 REST 简单直观但「调用方阻塞等响应、下游慢则级联」；异步（消息队列，见第 7 章消息队列）解耦更强、削峰更好，但语义变「最终一致」。技术选型上还有 gRPC（基于 HTTP/2 + Protobuf，强类型、高性能、双向流）适用于内部高性能服务间通信。

## 为什么重要
服务间通信方式决定了系统的耦合度与韧性。同步调用链一长，可用性呈乘法下降（每个 99% 相乘）；异步用消息解耦可把「可用性」和「一致性」解绑。这是架构权衡题的常客，也是把第 3 章（发现）、第 7 章（MQ）串起来的枢纽。

## 常见坑
- 长同步调用链（A→B→C→D 全同步），任一环慢则整条超时，且超时层层放大。
- 在同步链里混用「事务」期望强一致，却未处理下游失败回滚（见第 8 节分布式事务）。
- Feign 默认不超时或超时过长，下游挂起上游线程。
- 把本该异步（如发短信、计日志）的事用同步 RPC 做，白白拉长主链路。

## 动手自测
1. 什么场景该用同步 REST，什么场景该用消息队列？（提示：要即时结果且强一致→同步；可延迟、要削峰解耦→异步。）
2. 用 OpenFeign 调 `user-service` 的 `GET /users/{id}`，写出接口声明骨架（@FeignClient + 方法）。

## 面试视角
「服务间通信有哪些方式、怎么选？」答：同步（REST/OpenFeign，简单但阻塞、可用性乘性下降）vs 异步（消息队列，解耦削峰、最终一致）vs gRPC（高性能强类型）。能点出「可用性乘法 vs 一致性」「同步链要设合理超时与熔断」即专业。

## 8. 分布式事务：2PC、Saga 与 TCC 的取舍

> 引导：锚定 2PC 两阶段与阻塞代价，对比 Saga 补偿链与 TCC 三步走。

## 心智模型
跨服务做「要么都成、要么都不成」像「多人合伙转账」：传统做法（2PC）是大家先举手表决「能 commit 吗」，全举手才一起提交——但只要有个协调者中途晕倒，所有人举着手僵住（阻塞）。Saga 则是「一步步来、每步留好后悔药（补偿）」：A 扣了钱，B 加库存失败，就调 A 的补偿把扣的钱加回去。TCC 是把「后悔药」拆成 Try 预留 / Confirm 确认 / Cancel 取消三步走。

## 核心知识点（锚定官方）
两阶段提交（2PC）是分布式原子提交协议：准备阶段协调者向所有参与者发 query-to-commit，参与者执行到可提交点并投票（Yes/No）；提交阶段仅当全票 Yes 才发 commit，否则发 rollback。其最大缺点是**阻塞协议**——协调者永久失败则参与者永远阻塞、需人工介入；协调者是单点。Saga 用「本地事务序列 + 每步事件触发下一步 + 补偿事务回滚」规避阻塞，适合长流程。TCC（Try-Confirm-Cancel）是应用层变体：Try 预留资源、Confirm 提交、Cancel 释放。Seata 等框架提供 AT/TCC/Saga 模式实现。

## 为什么重要
「跨服务数据一致性」是微服务最难的一道题，没有银弹。理解 2PC 的阻塞代价，才能明白为什么大厂多转向最终一致（Saga/消息）；理解补偿而非回滚，才能设计可恢复的长事务。这是高阶后端面试的分水岭题。

## 常见坑
- 在微服务里硬要用 2PC 跨多个独立库，结果协调者一挂全阻塞，可用性暴跌。
- 用「本地事务 + 忽略下游失败」假装一致，实际产生脏数据（如订单成了库存没减）。
- Saga 补偿写错：补偿不是「反向 SQL」，而是业务上的对冲动作，且补偿本身也要幂等。
- 把「最终一致」当「不用一致」，不设对账/人工兜底，资损后才发现。

## 动手自测
1. 画「下单→扣库存→扣余额」流程，若扣余额失败，用 Saga 补偿应如何回滚前两步？（提示：补偿 = 释放库存预留 + 取消订单。）
2. 为什么 2PC 在协调者宕机时比 Saga 更危险？（提示：参与者永久阻塞 vs Saga 可继续推进局部事务。）

## 面试视角
「分布式事务怎么保证一致？」答：强一致选 2PC/XA（但阻塞、可用性差），生产多取最终一致：Saga（补偿链）/ TCC（预留-确认-取消）/ 本地消息表 + MQ 可靠投递。能说出「CAP 下的一致性取舍」「补偿要幂等」「要有对账兜底」即到位。

## 9. 可观测性：日志、指标与链路追踪三件套

> 引导：建立 Logs/Metrics/Traces 三大支柱心智，以及 TraceId 串联跨服务调用。

## 心智模型
微服务像「分布式乐队」，一出故障你不知道是哪个乐手跑调。可观测性就是给乐队装「监控系统」：日志（谁说了什么）、指标（心跳/CPU/QPS）、链路追踪（一段请求经过了哪些乐手、各花了多久）。三件套齐了，才能「出事前预警、出事后 5 分钟定位」，而不是靠猜。

## 核心知识点（锚定官方）
可观测性三大支柱：Logs（离散事件记录）、Metrics（可聚合的数值时间序列，如 QPS/延迟/错误率）、Traces（一次请求跨服务的完整调用链）。Spring 生态通过 Micrometer（指标门面，统一对接 Prometheus 等）采集 Metrics；分布式追踪（Micrometer Tracing / 原 Sleuth）借助 TraceId 串联跨服务调用。工程上还需定义 SLI（如成功率、P99 延迟）、SLO（目标值）、SLA（对外承诺），并用告警把「异常」变「可行动信号」。它与第 5 节网关的监控职责互补。

## 为什么重要
「看不见就管不了」。单体时代打日志就能排障；微服务里一次请求横跨十几个服务，没有统一追踪只能人肉翻每台机器。可观测性直接决定 MTTR（故障恢复时间），也是 SRE 文化的核心。面试中常被问「怎么定位一个跨服务慢请求」——答案就是这三件套。

## 常见坑
- 只打日志不打 TraceId，跨服务日志无法串联，排障靠 grep 全集群。
- 指标维度爆炸（每个请求打几十个 tag），监控存储被打爆、查询变慢。
- 埋点只在网关，下游服务无指标，链路半盲。
- 有告警无 SLO，告警全是噪声，真正的故障被淹没；或 SLO 设得无人负责。

## 动手自测
1. 一次「下单接口变慢」的投诉进来，你如何用 Trace + Metric + Log 三步定位到具体慢服务？（提示：Trace 看各 span 耗时 → Metric 确认该服务 P99 升高 → Log 看该服务报错/慢 SQL。）
2. SLI / SLO / SLA 三者区别？（提示：指标 / 内部目标 / 对外承诺。）

## 面试视角
「微服务怎么排障 / 什么是可观测性？」答：三大支柱 Logs/Metrics/Traces，用 TraceId 串联跨服务调用，Micrometer 采指标、Prometheus 存、Grafana 看、告警联动 SLO。能说出「MTTR 取决于可观测性建设」「SLO 驱动告警而非凭感觉」即 SRE 思维。
