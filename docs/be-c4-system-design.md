# 第11章 · 系统设计与高并发实战

> 目标：掌握从需求到权衡的系统设计方法论,并能独立设计短链、Feed 流、秒杀等典型系统;理解缓存三问题(穿透/击穿/雪崩)与缓存一致性、缓存缺失的处理;用读写分离与分库分表突破单库天花板;把限流、CDN、高可用容灾收口成一套稳定性体系。

> 来源：Kleppmann《Designing Data-Intensive Applications》/ AWS Well-Architected / Wikipedia(Token bucket、CDN) / Redis 官方(eviction、分布式锁) / MySQL 8.4 复制手册 / RFC 9110(重定向) / Resilience4j

## 1. 系统设计方法论:从需求到权衡

> 引导：建立先问量级、再做权衡的系统设计心智,避免一上来就拍技术栈。

## 心智模型
系统设计不是"选个炫酷技术",而是像盖楼前先勘测地形、出蓝图再施工。先想清楚"这栋楼给多少人住(量级)、几级抗震(可用性)、要不要扩建(扩展性)",再去决定梁用什么、墙怎么砌。一上来就搬砖,多半会盖歪。

## 核心知识点（锚定官方）
经典方法论强调从"需求"出发,分两层拆解:功能需求(系统要做什么)与非功能需求(性能、可扩展性、可用性、一致性、可维护性)。Martin Kleppmann 在《Designing Data-Intensive Applications》开篇即指出,数据密集型应用的核心难点不在算法,而在"数据量、数据复杂度、数据变更速度"带来的权衡;书里把"可靠性、可扩展性、可维护性"列为系统设计的三大目标。AWS Well-Architected 框架进一步把架构质量拆成六大支柱:运营卓越(operational excellence)、安全(security)、可靠(reliability)、性能效率(performance efficiency)、成本优化(cost optimization)、可持续性(sustainability)。

落地的标准动作是:① 理清功能与约束(QPS、存储、带宽、延迟 SLA);② 画高层架构(客户端→网关→服务→存储);③ 逐组件定方案并做量级估算;④ 识别瓶颈与单点,加冗余/缓存/异步;⑤ 明确一致性、可用性、容灾边界。量级估算常用"二八/峰值翻倍":日活×人均请求÷86400 得平均 QPS,再乘峰值系数;存储按"行数×行大小×保留期";带宽按"响应大小×QPS"。

## 为什么重要
面试与实战都考"权衡"而非死记。同一个需求,10 万 QPS 和 10 QPS 的架构天差地别;只背组件不背量级,一被追问"为什么用 Redis 不用 MySQL"就露怯。把方法论练成肌肉记忆,才能在白板上从空白推导出合理架构。

## 常见坑
上来就定技术栈(Kafka/Redis 全家桶),却说不清为什么;只算平均 QPS 不算峰值,低估洪峰;忽略非功能需求(忘了"可用性 99.99% 意味着每月只能宕 4 分钟");把单机思维直接套分布式(以为自增 ID、本地锁够用);不做容量估算导致存储/带宽预算爆表。

## 动手自测
设计"1 亿用户、日活 1000 万、人均 20 次/day 的短链服务":估算平均 QPS ≈ 1000万×20÷86400 ≈ 2300,峰值约 ×3 ≈ 7000;存储按 1 亿条×约 100 字节 ≈ 10GB(长期);重定向读多写少,缓存命中率目标 >95%。再反过来问:如果要求"全年可用性 99.99%",每月允许的宕机时间是多久?(答:约 4.3 分钟)

## 面试视角
高频开场题:"设计一个 XX 系统"。答题套路=澄清需求(功能+量级+SLA)→ 高层图 → 核心组件选型与理由 → 量级估算 → 瓶颈与优化(缓存/异步/分片)→ 容灾降级。评委看的是"有没有先问量级、有没有权衡意识",而不是最后用了什么中间件。

## 2. 短链系统设计

> 引导：用读多写少、发号+映射的典型微型系统,串起发号、存储、缓存与重定向。

## 心智模型
短链本质是"发号 + 映射":把任意长 URL 映射成一个短码,访客拿到短码后系统再把它"翻译"回原 URL 并跳转。难点不在跳转,而在"怎么生成不重复且够短的码"以及"海量映射怎么存、怎么快"。

## 核心知识点（锚定官方）
短码生成常用 62 进制(0-9a-zA-Z)发号:一个自增序号或分布式 ID 转成 62 进制即得短串,长度随总量增长很慢(62^7 ≈ 3.5 万亿,7 位够用很久)。分布式 ID 方案可直接复用 Snowflake 类发号器(第 10 章已讲:64 位 = 41 位时间戳 + 10 位机器 + 12 位序列)。存储是一张"短码→长 URL + 创建时间 + 有效期"的映射表,读远大于写,天然适合缓存前置。跳转用 HTTP 重定向:RFC 9110 定义 301(Moved Permanently,浏览器缓存,省流量但难统计)与 302(Found,每次回源可统计点击,短链场景常用)。防遍历/防刷可加签名或限流。

## 为什么重要
短链是"读多写少 + 海量映射 + 高并发跳转"的典型微型系统设计题,能串起发号、存储、缓存、重定向、限流多个考点,是面试高频且能深挖的母题。

## 常见坑
短码冲突(发号不全局唯一导致覆盖旧链接);用自增 ID 直接当码被轻易遍历出所有链接;301 缓存导致点击统计失真;不做有效期与防刷,被人批量生成打爆存储;短码长度固定却未预估上限,后期位数不够。

## 动手自测
给定分布式 ID = 1234567890,转 62 进制:反复除 62 取余(字符表 0-9a-zA-Z),得 "1LY7U2"(示意)。写出映射表 SQL:`short_code VARCHAR(10) PRIMARY KEY, long_url TEXT, created_at BIGINT, ttl BIGINT`。用 Redis 缓存热点:`GET short:xxx → long_url`,未命中再查库并回写。

## 面试视角
深挖方向:① 短码如何保证不重复(号段/雪花/预生成池);② 301 vs 302 取舍;③ 映射表上亿行怎么分库分表(按短码 hash);④ 防遍历与限流;⑤ 高并发跳转如何让 Redis 扛住 99% 读。答出"读多写少→缓存+重定向"这个骨架即过关。

## 3. Feed 流设计:推拉模型

> 引导：理解写扩散与读扩散的权衡,以及大 V 这一特殊热点的处理。

## 心智模型
Feed 流(微博/朋友圈时间线)要解决的是"我关注了 500 人,怎么在我打开 App 时瞬间聚合出按时间排序的内容"。核心矛盾是:写入时聚合,还是读取时聚合?这就是推(Push)与拉(Pull)的取舍。

## 核心知识点（锚定官方）
推模式(fan-out push):用户发帖时,系统把这条内容写入其所有粉丝的"收件箱"列表。读时直接拉自己收件箱,极快;代价是写扩散——一个大 V 发一条,要写几百万个收件箱。拉模式(fan-out pull):发帖只存自己的发件箱,读时去遍历关注列表每个人的发件箱再归并排序。写快读慢,粉丝多的人打开首页会很慢。工程上普遍采用"推拉结合":普通用户用推(收件箱小),大 V 用拉(不写扩散,读时单独拉取合并),再配合游标分页与缓存。

底层存储常用"宽列/有序表 + 时间序"或消息流服务(Kafka 类)做写扩散管道;归并读可借助 Redis 有序集合(ZSET,score=时间戳)或时序存储。Kleppmann《DDIA》在"数据模型"章节专门讨论了聚合 feed 的推拉权衡。

## 为什么重要
Feed 是"写扩散 vs 读扩散"这一分布式经典权衡的最直观载体,能考察你对存储选型、分页、缓存、热点账号(大 V)特殊处理的综合把控。

## 常见坑
无脑全推:大 V 一发帖,写队列瞬间几百万写入,打爆存储;无脑全拉:粉丝多的人首页延迟爆炸;分页用 OFFSET 深翻页性能塌方;没处理"取关后收件箱残留/新关注补推"的一致性。

## 动手自测
画推拉结合模型:用户 A(50 粉丝)发帖→写 50 个收件箱;大 V B(500 万粉丝)发帖→不写扩散,仅存自己发件箱,粉丝读时单独拉 B 的发件箱与自身收件箱归并。用 Redis ZADD feed:{uid} {ts} {postId} 写入, ZREVRANGE 分页拉取。

## 面试视角
必问题:"推和拉怎么选?"标准答:小号推、大 V 拉、推拉结合;说明写扩散/读扩散的成本点;给出分页(游标/score)、热点账号、取关一致性的处理。能点出"大 V 是特殊case"就已经超过多数候选人。

## 4. 秒杀/抢购高并发

> 引导：把限流、缓存、异步、锁、降级串成一条层层削峰的实战链路。

## 心智模型
秒杀是"瞬时洪峰 vs 有限库存"的对抗。正确思路不是让系统硬扛每一笔请求,而是像水库分洪——层层削峰,把不可控的尖峰流量变成后端能平稳消化的平流。

## 核心知识点（锚定官方）
分层削峰链路:① 静态资源与页面走 CDN(见第 9 知识点),不回源;② 前端按钮防重复点击 + 答题/排队 human check;③ 网关层限流,令牌桶算法按固定速率发放令牌、请求消耗令牌、空桶则拒绝(Wikipedia Token bucket);④ 库存预扣用 Redis 原子扣减(`DECR`/`Lua` 保证原子),避免超卖;⑤ 校验通过的下单请求投进消息队列(Kafka 类,见第 7 章)异步落库,削峰填谷;⑥ 防超卖用乐观锁(`UPDATE ... WHERE stock>0`)或分布式锁(Redis `SET key randval NX PX ms`,官方锁模式)。每一层都在"尽早拒绝"无效请求,保护最贵的数据库。

## 为什么重要
秒杀把"限流、缓存、异步、锁、降级"几乎所有高并发手段串成一条实战链路,是检验后端是否真的懂高并发的最佳试金石。

## 常见坑
库存直接在 MySQL 里 `UPDATE stock=stock-1` 不加条件→超卖变负数;缓存热点 key(如库存)在活动开始瞬间过期→击穿打爆 DB;不做限流,洪峰直接冲垮订单服务;下单同步落库,RT 高导致线程池耗尽;重复提交没防,一人下一百单。

## 动手自测
用 Redis Lua 原子扣库存:`if redis.call('GET',KEYS[1])>0 then redis.call('DECR',KEYS[1]) return 1 else return 0 end`,返回 0 即售罄。网关用令牌桶:容量 1000、速率 500/s,突发最多放 1000 请求进内部。售罄后直接返回,不再碰 DB。

## 面试视角
经典连环问:怎么防超卖?(原子扣减/乐观锁)→ 怎么抗瞬时流量?(CDN+限流+MQ 异步)→ 库存热点怎么处理?(Redis 预扣+本地缓存+防击穿)→ 失败了怎么补偿?(订单超时未支付回补库存)。能画出"层层削峰"链路图就赢了。

## 5. 缓存架构:穿透/击穿/雪崩

> 引导：准确区分三种缓存失效模式并各给对症解法,是后端必考核心。

## 心智模型
缓存是挡在数据库前的护盾,但有三把"破防"利刃:穿透(穿过去打 DB)、击穿(一个点被集中打)、雪崩(整面盾碎掉)。理解这三者的差异,才能针对性布防。

## 核心知识点（锚定官方）
缓存穿透:查询根本不存在的数据(恶意刷/误用 ID),缓存与 DB 都没有,每次都打到 DB。解法:布隆过滤器(Bloom Filter,用位数组+多个哈希预判"是否存在",不存在直接拒)或缓存空值(对查不到的 key 也写一个带短 TTL 的空标记)。缓存击穿:某个极热点 key 在过期瞬间,大量并发同时发现"没了",一齐打到 DB。解法:互斥锁(只放一个线程回源重建,其余等待)、逻辑过期(值里带过期时间,异步刷新不删 key)、热点 key 永不过期+后台刷新。缓存雪崩:大量 key 同一时刻过期,或 Redis 整体宕机,请求全部涌向 DB。解法:过期时间加随机抖动避免同时失效、多级缓存(本地+Redis)、Redis 高可用(Cluster/哨兵)。Redis 官方文档明确,达到 maxmemory 后会按 `maxmemory-policy`(如 allkeys-lru/volatile-lfu)驱逐键,且 LRU/LFU 均为采样近似实现。

## 为什么重要
缓存三问题是后端面试几乎必考、且极易与实际事故对应的核心知识。答不清三者区别,实战里就会用错解法(比如用布隆过滤器去解决雪崩,完全不对症)。

## 常见坑
把三者和"缓存不一致"混为一谈(它们是不同维度的问题);空值缓存不设 TTL,导致"不存在"被永久缓存、真数据写入后读不到;热点 key 用"互斥锁"却忘了设锁超时,重建线程挂了全员阻塞;雪崩只加随机 TTL 却没做 Redis 高可用,宕机照样崩。

## 动手自测
穿透:ID 不存在时 `SET nx:{id} "" EX 60` 缓存空标记,下次直接命中空值返回。击穿:用 `SET lock:key NX PX 3000` 抢锁,抢到才查 DB 重建并写回,没抢到 sleep 重试读缓存。雪崩:基础 TTL 300s + 随机 0~120s,避免集体失效。

## 面试视角
高频对比题:"穿透、击穿、雪崩分别是什么、怎么解决?"标准答:穿透=查不存在→布隆/空值;击穿=热点过期瞬间并发→互斥锁/逻辑过期;雪崩=大量同时失效/宕机→随机 TTL+高可用+多级缓存。能张口区分三者并各给解法即满分。

## 6. 缓存一致性

> 引导：讲清先更新 DB 还是先删缓存,以及延迟双删与订阅 binlog 的取舍。

## 心智模型
缓存与数据库是两份数据,改了 DB 还要让缓存跟着变,否则下次读到的就是旧值。缓存一致性研究的就是"这两份数据怎么尽量同步、以及在什么情况下允许短暂不一致"。

## 核心知识点（锚定官方）
最常用的是 Cache-Aside(旁路缓存)模式:读时"缓存没有就查 DB 并回写";写时"先更新 DB,再删除缓存"(删而非更新,避免并发双写不一致)。更稳妥的是"延迟双删":更新 DB 前删一次缓存,更新完 DB 后延迟一小段时间再删一次,兜住"删缓存→读线程查旧 DB→写回旧值"的窄窗口。更彻底的异步方案:订阅数据库 binlog(MySQL 复制的二进制日志,官方文档称其为复制与 CDC 的基础),通过 Canal 等组件把变更实时同步到缓存,业务代码无感。选择哪条路取决于对一致性的要求——强一致几乎只能走"更新 DB + 删缓存 + 补偿",最终一致可接受 binlog 异步。

## 为什么重要
缓存一致性的坑极其隐蔽,是线上"明明改了价格却还显示旧价"类故障的头号原因。架构上怎么选,直接决定你敢不敢把核心数据放缓存。

## 常见坑
"先删缓存再更新 DB":删除后、更新前的窗口里,读线程把旧值又写回缓存,导致长期脏读;只更新缓存不更新 DB:缓存是易失的,重启即丢真相;延迟双删的延迟时间拍脑袋,太短兜不住、太长放大不一致窗口;忘了缓存也有 TTL,依赖过期兜底却不知道过期前已脏。

## 动手自测
标准 Cache-Aside 写:`UPDATE product SET price=? WHERE id=?;` 然后 `DEL cache:product:{id}`。延迟双删:删缓存 → 更新 DB → `sleep(500ms)` → 再 `DEL cache:product:{id}`。异步方案:监听 binlog 的 UPDATE 事件 → 触发 `DEL/SET cache:product:{id}`。

## 面试视角
必问题:"先删缓存还是先更新 DB?为什么?"答:推荐"先更新 DB 再删缓存",并解释"先删缓存"的脏读窗口;能补一句"延迟双删/订阅 binlog 做最终一致"即高分。再问"为什么是删不是更新"——避免双写竞态。

## 7. 读写分离与分库分表

> 引导：用复制做读扩展、用分片突破单表天花板,分片键是命门。

## 心智模型
单机数据库迟早会到天花板:CPU、连接数、磁盘 IO、单表行数都是硬限。突破方式两条路——读写分离把"读"分流出去,分库分表把"数据"拆小,本质都是"别让一件事压在一台机器上"。

## 核心知识点（锚定官方）
读写分离锚定 MySQL 官方复制文档:复制把源(source)的数据拷贝到一个或多个副本(replica),默认异步(replica 不必常连);官方明确"Scale-out"模式——所有写和更新在源,读可分散到一个或多个副本,从而提升写性能并线性提升读速度。配合"读从写源"的路由即可做读写分离。分库分表分两类:垂直拆分(按业务/字段,把大表拆到不同库或把不常用字段剥离)与水平拆分(按分片键 hash/范围/一致性哈希把行分布到多表多库,一致性哈希见第 10 章,扩缩容只迁移相邻段)。分片键选择是核心:选错(如按随机字段)会导致跨分片查询灾难。

## 为什么重要
当单表过千万行、连接数打满、读 QPS 顶不住时,读写分离与分库分表是绕不开的扩容手段,也是区分"会用数据库"和"会设计数据库架构"的分水岭。

## 常见坑
读从延迟导致"刚写就读不到"(异步复制的固有窗口,用"写后读走主库"或延迟容忍化解);分片键选错,常用查询全变跨分片广播;分库后自增 ID 冲突(必须用分布式 ID,见第 10 章);跨分片 JOIN/事务难做,忘了提前把数据聚到同片;只分表不分库,单实例连接/IO 仍是瓶颈。

## 动手自测
读写分离:数据源配一主两从,写操作走主、读操作按权重走从(读从设 1s 内延迟阈值)。水平分表:订单按 `user_id % 16` 落到 `orders_00`~`orders_15`;或用一致性哈希让扩到 32 片时只迁移一半数据。分片键选 `user_id`(因为查询大多按用户维度)。

## 面试视角
连环问:读写分离怎么保证读不到旧数据?(写后读走主/容忍延迟)→ 分库分表怎么分?(垂直+水平,强调分片键)→ 分片键怎么选?(按最高频查询维度)→ 跨分片事务怎么办?(尽量同片/最终一致/Saga)。能讲清"分片键是命门"即过关。

## 8. 限流算法落地:令牌桶/漏桶/滑动窗口

> 引导：给流量装闸,区分单实例与分布式限流,令牌桶允许突发。

## 心智模型
限流就是给流量装一道"闸":不管后面多想冲,闸口只允许额定速率过人。它保护的是系统不被突发洪峰冲垮,也是秒杀、网关、API 的标配。

## 核心知识点（锚定官方）
令牌桶(Token bucket,锚 Wikipedia):系统以固定速率往桶里加令牌,请求要消耗一个令牌才放行,桶满则丢弃多余令牌;桶里有余量时允许突发(最多突发到桶容量)。它兼顾"平均速率限制"与"有限突发",工程最常用。漏桶(Leaky bucket):请求进桶、以恒定速率从桶底流出,超出容量则拒绝,输出绝对平滑、不支持突发。滑动窗口/计数器:按时间窗口计数,实现简单但边界有临界突刺。分布式限流(多实例共享额度):网关层统一限流,或用 Redis + Lua 做原子计数(`INCR`+`EXPIRE` 或滑动窗口 zset)。进程内限流可复用 Resilience4j(第 9 章),但多节点需集中式。

## 为什么重要
没有限流,一个慢接口或一波恶意请求就能拖垮整条链路。它是系统稳定性的第一道闸门,也是高并发设计里性价比最高的防御手段。

## 常见坑
单实例限流以为全局限流(多节点各自限流,实际总流量是 N 倍);令牌桶容量设太大失去限流意义、设太小误杀正常流量;分布式限流用非原子操作(`INCR` 和 `EXPIRE` 分开)导致计数失效;限流后没配降级,被拒请求直接报错而非走兜底;只限制 QPS 不限制并发数,长连接把线程池占满。

## 动手自测
单机令牌桶:Guava `RateLimiter.create(500)` 限 500/s,`tryAcquire()` 拿不到即拒。分布式:Redis Lua 实现滑动窗口——`ZADD window:{api} {now} {reqId}; ZREMRANGEBYSCORE window:{api} -inf {now-1000}; ZCARD` 超阈值则拒。多节点统一走一个 Redis 即共享额度。

## 面试视角
对比题:"令牌桶和漏桶区别?"答:令牌桶允许突发到桶容量、漏桶恒定平滑无突发;各自适用场景。再问分布式怎么限?答网关集中/Redis+Lua 原子。能点出"单实例限流≠全局限流"这个坑即高分。

## 9. CDN 与静态资源优化

> 引导：把读从源站卸载到边缘节点,配合动静分离与文件指纹刷新。

## 心智模型
CDN 像把内容预先搬到你家楼下的便利店:原本要跨省去总仓(源站)取的货,现在小区门口就能拿。距离越近,拿到越快,总仓也不被挤爆。

## 核心知识点（锚定官方）
CDN(Content Delivery Network,锚 Wikipedia)是地理分布的代理服务器网络,通过边缘节点(edge nodes)把内容(image、JS、CSS、视频、可下载对象)缓存到离终端用户最近的地方,从而降低延迟、减少源站带宽成本、提高可用性。填充方式两种:pull caching(用户首次请求时 CDN 去源站取并缓存,之后命中边缘)与 push caching(源站主动预推到 CDN)。适用"静态、读多、体积大"的资源;与之配合的是"动静分离"——动态请求走源站/API,静态资源走 CDN。

## 为什么重要
前端加载慢、源站带宽贵、跨地域访问卡,绝大多数能用 CDN 解决。它是成本最低、收益最高的一项性能优化,也是高并发里"把读从源站卸载"的第一关。

## 常见坑
静态资源更新后用户仍拿到旧版(CDN 缓存未失效)——解决:文件名加哈希指纹(如 `app.a1b2c3.js`)或 URL 加版本参数,内容变了文件名就变,旧缓存自然失效;全部走 CDN 却没配回源容灾,源站抖一下边缘也跟着错;把本该动态的接口(带用户态)误缓存,泄露他人数据;忽略回源风暴(缓存集中过期瞬间全回源)。

## 动手自测
构建时给静态文件加 contenthash:`output.filename = '[name].[contenthash].js'`,部署后 HTML 引用新名,旧缓存自动作废。Nginx 对 `/static/*` 设长 Cache-Control:`add_header Cache-Control "public, max-age=31536000, immutable"`。动态 API 一律 `Cache-Control: no-store`。

## 面试视角
常考题:"CDN 是什么、怎么加速?"答:边缘节点缓存静态资源、就近返回、降延迟降源站负载;pull/push 区别;配合动静分离与文件指纹刷新。能顺带说出"缓存刷新用 hash 文件名避免脏读"就是加分项。

## 10. 高可用与容灾:降级/熔断/限流/异地多活

> 引导：把前面所有单点手段收口成一套稳定性体系。

## 心智模型
高可用追求的是"系统打不垮、垮了也能快速恢复"。它不是某个组件,而是一套组合拳:冗余打底、限流挡峰、熔断止损、降级保命、容灾兜底。

## 核心知识点（锚定官方）
冗余:多副本、多节点、多机房,单点失效不影响整体(数据库主从、服务多实例、存储多副本)。限流(第 8 知识点)挡住超出容量的流量。熔断:依赖服务异常时快速失败、不再傻等,给下游喘息;状态机为 CLOSED→OPEN→HALF_OPEN(锚 Resilience4j 文档,第 9 章已讲)。降级:非核心功能在压力下主动让路(如大促时关闭商品评价实时数、返回默认兜底),保住交易主链路。超时与重试:调用必须设超时,重试要带退避与幂等(避免重试风暴放大故障);雪崩常因"一个慢依赖拖死调用方线程池"链式扩散。容灾:异地多活/单元化,把用户流量按地域封闭在本地单元,单地域故障只影响局部。

## 为什么重要
功能再强,一宕机就归零。高可用是"系统能不能上生产"的及格线,也是大厂对后端的基本要求。它把前面所有单点手段(缓存、限流、异步、熔断)收口成一套稳定性体系。

## 常见坑
只有冗余没有故障转移(主挂了从不会顶上);重试不带退避/幂等,故障时被重试流量放大成雪崩;熔断阈值拍脑袋,该断不断或误断正常;降级开关没预案,真出事时手忙脚乱翻代码;把"高可用"等同于"加机器",忽略慢依赖、连接池、超时这些隐性单点。

## 动手自测
给下游调用加 Resilience4j:熔断(`failureRateThreshold=50%`, `waitDurationInOpenState=5s`, `permittedCallsInHalfOpenState=5`)+ 限流(`rateLimiter`)+ 重试(`maxAttempts=3, waitDuration=1s`)。降级:商品详情页在依赖"推荐服务"超时时,返回空推荐块而非整页 500。多实例 + 健康探针,摘除不健康节点。

## 面试视角
综合题:"怎么保证系统高可用?"答:冗余(多副本/多活)+ 限流(挡峰)+ 熔断(止损)+ 降级(保主链路)+ 超时重试幂等(防雪崩)+ 容灾(异地多活)。能结合前面章节(限流、熔断、缓存)串成体系,而非罗列名词,即为资深水平。
