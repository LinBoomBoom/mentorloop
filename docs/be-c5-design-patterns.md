# 第12章 · 设计模式与架构原则

> 目标：掌握 GoF 设计模式三大分类与代表模式,能区分创建型/结构型/行为型的动机与适用场景;理解依赖注入(IoC)这一 Spring 基石;用 SOLID 五大原则衡量代码质量;用 DDD 战术(实体/值对象/聚合/仓储)消灭贫血模型;建立 Clean/Hexagonal 架构观,并能识别贫血模型、上帝类、过度设计等反模式。

> 来源：GoF《Design Patterns》(Gamma et al., 1994) / Wikipedia(Software design pattern, SOLID) / Martin Fowler《IoC Containers and the Dependency Injection pattern》《Anemic Domain Model》 / Eric Evans《Domain-Driven Design》 / Robert C. Martin Clean Architecture

---


## 1. 设计模式全景：GoF 三大分类与价值

> 引导：先建立全局地图：设计模式是什么、GoF 怎么分类，后面每类挑代表逐个拆。

## 心智模型
把"设计模式"想成**一套经过验证的、可复用的解题模板库**。它不是能直接粘进项目的代码,而是"在某种反复出现的问题面前,高手通常这样切"。正如 Wikipedia 所定义:软件设计模式描述了对软件中常见所需行为的一种**可复用解决方案**。就像木匠有"榫卯""燕尾榫"这样的标准接法,你不必每次重新发明连接两块木头的方式;程序员面对"对象怎么创建""类怎么组合""对象怎么协作"时,也有 GoF 沉淀出的标准套路。理解了分类,你就拿到了一张"问题 → 套路"的地图:看到"创建逻辑到处散落"就知道去创建型里找,看到"对象要动态加功能"就去装饰器里找。

## 核心知识点（锚定官方）
- **起源与定义**:设计模式在计算机科学中流行,源于 1994 年"四人组"(Gang of Four, Erich Gamma、Richard Helm、Ralph Johnson、John Vlissides)的著作《Design Patterns: Elements of Reusable Object-Oriented Software》(常缩写为 GoF)。Wikipedia 明确:它是对某一类常见问题的**描述与模板**,可用于很多不同上下文,而非可直接拷贝的僵化结构。
- **GoF 三大分类**(Wikipedia 原文口径):
  - **创建型(Creational)**:负责创建对象。代表:Abstract Factory、Builder、Factory Method、Prototype、Singleton。
  - **结构型(Structural)**:组织类与对象以形成更大结构、提供新功能。代表:Adapter、Bridge、Composite、Decorator、Facade、Proxy。
  - **行为型(Behavioral)**:描述对象之间的协作/通信。代表:Observer(发布-订阅)、Strategy、Command、Iterator、Template Method、Visitor 等 11 种。
- 模式 ≠ 银弹:GoF 书本身强调模式是用于"组合、复用、解耦"的心智工具,不是越多越好。

## 为什么重要
- **共同语言**:当评审时说"这里用个工厂方法吧",全组立刻懂,省去长篇解释。模式是工程师之间的术语压缩。
- **复用经验**:每个模式背后是对"何时用、何时别用"的踩坑总结,直接复用前人的权衡,避免重蹈覆辙。
- **面试高频**:几乎每家后端面试都会问"单例怎么写才安全""装饰器和代理区别""策略模式解决了什么问题",这是工程素养的硬通货。
- **与后续衔接**:第8章 Spring 的 IoC/DI、本章的依赖注入、DDD 战术,本质上都是"解耦"这一主题的不同切面。

## 常见坑
- **模式滥用(过度设计)**:一个小项目硬套抽象工厂 + 策略 + 观察者,反而比直接写死更难读。先有"重复/变化点"再引入模式。
- **为模式而模式**:把本可以用普通函数解决的问题,硬塞成 Command 对象,徒增样板。
- **混淆"模式"与"框架"**:Spring 是框架,它**运用了**模板方法、代理、依赖注入等模式,但模式是思想、框架是实现。
- **以为模式能替代理解**:背下 Singleton 代码却不懂"为何要控制实例数",换场景就翻车。

## 动手自测
1. 把"创建一个连接池""序列化不同格式""跨数据库兼容 DAO"三类需求,各自匹配到合适的创建型模式。
2. 用一句话分别说出创建型/结构型/行为型各自"管的是对象生命周期的哪一段"。
3. 找出你项目里一个"加功能要改很多类"的地方,判断它本该用结构型还是行为型模式化解。
4. 画一张三列表,把 Singleton/Adapter/Observer 分别归入对应分类并写出它解决的核心问题。

## 面试视角
- "设计模式有什么用?" → 答:复用成熟权衡、建立共同语言、对抗变化;但强调**不要过度设计**,模式服务于解耦而非炫技。
- "GoF 三大分类的区别?" → 答:创建管对象诞生、结构管对象组合、行为管对象协作,各举一两个代表模式。
- "你实际用得最多的模式是哪些?" → 准备一两个真实案例(如用策略模式替换一堆 if-else 的计费逻辑),比罗列名词更有说服力。

## 2. 创建型：单例与工厂方法/抽象工厂

> 引导：创建型管对象怎么诞生；重点吃透线程安全单例和工厂家族的边界。

## 心智模型
**创建型模式**解决的核心问题是:把"对象怎么被造出来"和"造出来后怎么用"解耦。直白 new 一个对象看似最简单,但当"创建逻辑复杂""要根据条件造不同子类""要保证全局只有一个"时,散落在各处的 new 就成了维护噩梦。创建型模式就是把"造"这件事收口到专门的地方——工厂管"造哪一类",单例管"只能造一个",建造者管"分步造复杂对象"。类比:你不需要知道手机在富士康哪条线、用什么螺丝拼出来,你只要说"我要一部 Pro 款",工厂就给你对的产物。

## 核心知识点（锚定官方）
- **Singleton(单例)**:确保一个类只有一个实例,并提供全局访问点。GoF 列在创建型中。经典实现要点:私有构造器 + 静态实例 + 静态获取方法。
- **Factory Method(工厂方法)**:定义创建单个对象的接口,由子类决定实例化哪个类。GoF:把"new 哪个具体类"推迟到子类。
- **Abstract Factory(抽象工厂)**:提供创建**相关/依赖对象家族**的接口,而无需指定具体类。例如一个 UI 工厂同时产出配套按钮+文本框,保证风格一致。
- **Builder(建造者)**:将复杂对象的构建与其表示分离,同样的构建过程可产出不同表示。适合"参数很多、构造步骤固定"的对象(如构造一个 HTTP 请求 / 一个查询)。
- **Prototype(原型)**:用原型实例指定创建种类,通过复制(克隆)来创建新对象,而不是通过 new。适合"创建成本高于拷贝"的场景。

## 为什么重要
- **控制实例边界**:单例用于线程池、连接池、配置中心等"全局只能有一个"的资源,避免重复占用。
- **屏蔽创建复杂度**:调用方只说"我要什么",不关心具体子类与构造细节,符合"依赖抽象"。
- **统一家族约束**:抽象工厂保证产出的对象彼此兼容(不会把 macOS 按钮配到 Windows 窗口)。
- **面试必考**:手写线程安全单例(DCL + volatile)、工厂 vs 抽象工厂区别,是后端基础题。

## 常见坑
- **单例的线程安全**:懒汉式不加锁会创建多个实例;双重检查锁(DCL)忘了 `volatile` 会因指令重排出问题(可见性与有序性)。
- **单例变全局变量**:过度用单例 = 隐式全局状态,增加测试难度与耦合,能注入就别硬单例。
- **工厂膨胀**:当有几十种产品时,工厂方法类爆炸;此时可转抽象工厂或结合配置+反射/注册表。
- **Builder 的空构造陷阱**:忘了校验必填项,造出半成品对象。

## 动手自测
1. 用 DCL + `volatile` 手写一个线程安全单例,并用注释标出 volatile 防重排的作用。
2. 设计一个"日志输出器"工厂:支持控制台/文件/远程三类,调用方只传类型字符串。
3. 对比单例与静态工具类(如 Math)的本质区别:状态持有 vs 无状态。
4. 给一个"导出报表"需求(支持 PDF/Excel/CSV),用抽象工厂组织"文档+图表+样式"的配套产出。

## 面试视角
- "手写单例,要线程安全" → DCL 写法 + `volatile` 关键字解释重排;或枚举单例(最简洁且防反序列化破坏)。
- "工厂方法和抽象工厂区别?" → 前者造一类产品的一个变体,后者造一族互相兼容的产品。
- "单例有什么缺点?" → 全局状态难测试、违反单一职责、并发下若实现不当有坑;能注入优先注入。

## 3. 结构型：适配器、装饰器、代理

> 引导：结构型管对象怎么拼；把最容易混的适配器/装饰器/代理一次讲清。

## 心智模型
**结构型模式**解决的是"怎么把类或对象拼在一起,形成更大、更有弹性的结构"。如果说创建型决定零件怎么造,结构型就是决定零件怎么组装。最常用的是三兄弟:**适配器**(转换接口)、**装饰器**(动态加功能)、**代理**(控制访问)。一个好记的类比——你给手机套壳是装饰器(原功能不变、外加保护),你用转接头连 Type-C 耳机是适配器(把不兼容变兼容),你让前台代收快递是代理(替你挡在前面、可加验身份)。

## 核心知识点（锚定官方）
- **Adapter(适配器)**:将一个类的接口转换成客户期望的另一种接口。GoF:让原本因接口不兼容而不能一起工作的类协同。典型:旧支付 SDK 接口和新订单系统不匹配,写个 Adapter 包一层。
- **Decorator(装饰器)**:动态地给对象附加职责,同时保持相同接口。GoF:比生成子类更灵活地扩展功能。典型:Java I/O 的 `BufferedInputStream` 包 `FileInputStream`,层层叠加缓冲/压缩。
- **Proxy(代理)**:为其他对象提供一种代理以控制对这个对象的访问。GoF:常见用途——远程代理(本地桩代表远程对象)、虚拟代理(懒加载大对象)、保护代理(加权限校验)。Spring AOP 底层就是 JDK 动态代理/CGLIB 代理。
- 其他结构型:Bridge(抽象与实现解耦)、Composite(树形部分-整体)、Facade(给子系统统一门面)。

## 为什么重要
- **接口翻译**:系统集成时对方接口不合你的规范,Adapter 让你不改旧代码就能接入。
- **无侵入增强**:装饰器给对象加日志/缓存/重试,不碰原类,符合开闭原则。
- **AOP 基石**:理解代理,才真正懂第8章 Spring AOP "基于代理的运行时织入"到底织的是什么。
- **面试常考三者区分**:尤其装饰器 vs 代理,新手极易混。

## 常见坑
- **装饰器和代理混淆**:装饰器目的是"增强功能",代理目的是"控制访问"(是否真的替你挡在前面)。虽都包一层,意图不同。
- **适配器套太多层**:适配来适配去,链路深、排查难,优先推动上游改接口而非无限适配。
- **装饰器顺序敏感**:`A(B(C))` 与 `B(A(C))` 行为可能不同(如先压缩后加密 vs 先加密后压缩),顺序即语义。
- **用代理做业务**:把本该显式的业务逻辑藏在代理里,反而让调用方看不出发生了什么。

## 动手自测
1. 写一段代码:用装饰器给一个 `DataSource` 接口依次加上"缓存装饰""日志装饰",并说明叠加顺序如何影响行为。
2. 给出一个第三方 SDK 返回 `LegacyUser`,而你需要 `User`,写 Adapter 完成字段映射。
3. 画一张图区分:Decorator(增强) vs Proxy(控制) vs Adapter(翻译) 三者各自的"包一层的目的"。
4. 找出你代码里"before/after 横切逻辑",判断它更适合装饰器还是 AOP 代理。

## 面试视角
- "装饰器和代理的区别?" → 装饰器为增强(功能叠加)、代理为控制(访问/权限/远程);但从结构上都"包一层",关键看意图。
- "适配器在真实项目哪用过?" → 答:对接老系统/第三方 SDK、统一不同供应商返回结构。
- "Spring AOP 用的是什么代理?" → JDK 动态代理(接口)与 CGLIB(类),并呼应第8章"代理-based AOP"。

## 4. 行为型：策略与观察者

> 引导：行为型管对象怎么协作；策略替换 if-else、观察者解耦发布订阅是面试常客。

## 心智模型
**行为型模式**关注"对象之间怎么通信、职责怎么分配"。如果说结构型解决"怎么拼",行为型解决"怎么协作"。最常用的两个:**策略(Strategy)**把"算法族"抽出来让它们可互换;**观察者(Observer)**建立"一对多"的通知机制。类比:策略像"导航 App 的出行方式——驾车/公交/骑行可随时切换,但到达目的地这件事不变";观察者像"公众号——你关注后,号主一发文章,所有粉丝都收到推送",发布者根本不认识订阅者。

## 核心知识点（锚定官方）
- **Strategy(策略)**:定义一系列算法,把它们封装起来,使它们可互相替换。GoF:让算法独立于使用它的客户而变化。典型:电商的"运费计算"有普通/会员/包邮多种策略,运行时选一个。它常用来**替换一大堆 if-else / switch**。
- **Observer(观察者 / 发布-订阅)**:定义对象间一对多依赖,当一个对象状态改变,所有依赖者自动收到通知并更新。GoF 原文即 "publish/subscribe"。典型:GUI 事件、消息总线、前端响应式。
- 二者与结构型的区别:策略是"选一个算法",观察者是"状态变化时广播",动机完全不同。

## 为什么重要
- **干掉条件分支**:策略模式把"根据 type 走不同分支"变成"注入不同策略对象",新增一种只需加类,不改老代码(开闭原则)。
- **解耦发布与订阅**:观察者让生产者不依赖具体消费者,系统更易扩展(新加一个监听者即可)。
- **事件驱动基础**:消息队列(第7章)、Spring 事件(第8章 ApplicationEvent)、前端响应式,底层思想都源自观察者。
- **面试高频**:策略替换 if-else、观察者实现原理是必问。

## 常见坑
- **策略类爆炸**:每种微小差异都建一个策略类,反而类太多。可用"策略 + 函数/枚举"或更轻的表驱动收敛。
- **观察者内存泄漏**:被观察者持有观察者引用,若观察者已不用却不取消订阅(尤其在用匿名类/闭包时),对象无法被回收。
- **观察者链循环通知**:A 收到通知改状态又通知 B,B 又通知回 A,造成无限循环,需打断或合并刷新。
- **通知顺序假设**:不要依赖观察者被通知的先后次序,它可能随注册顺序变化。

## 动手自测
1. 把一段"根据订单类型算折扣"的 switch 代码,重构成策略模式(定义 `DiscountStrategy` 接口 + 多个实现 + 上下文选择)。
2. 用观察者实现一个简易"主题-订阅者":主题价格变动时,所有订阅者 print 出新价。
3. 分析观察者模式为何要提供 `unsubscribe`,并在你的实现里加上防泄漏逻辑。
4. 对比策略模式与工厂方法:一个选"算法"、一个选"产品",意图差异在哪。

## 面试视角
- "策略模式解决了什么问题?" → 替换条件分支、让算法可互换、符合开闭;举"计费/折扣/序列化"真实例子。
- "观察者模式的缺点?" → 通知顺序不确定、易内存泄漏(忘了 unsubscribe)、调试时调用链不直观。
- "观察者靠什么解耦?" → 发布者只依赖抽象观察者接口,不认识具体订阅者;呼应第7/8章事件机制。

## 5. 行为型：模板方法与命令

> 引导：另两个极实用的行为型：固定流程用模板方法、把请求变对象用命令。

## 心智模型
行为型里还有两个极实用但常被低估的:**模板方法(Template Method)**和**命令(Command)**。模板方法是"把算法骨架定在父类,把可变的步骤留给子类",像做蛋糕的通用流程(打蛋→搅拌→烘烤)固定,但"加什么口味"由子类决定。命令则是"把'请求'本身封装成一个对象",于是请求可以被排队、撤销、记录日志——就像餐厅里服务员把每桌的点单写成一张小票(命令对象),后厨照着做,小票还能撤销或重做。

## 核心知识点（锚定官方）
- **Template Method(模板方法)**:在父类中定义算法骨架,将某些步骤延迟到子类实现。GoF:让子类在不改变算法结构的情况下重定义算法的某些步骤。典型:`AbstractController` 定义 `handle()` 流程,子类只实现 `doService()`。
- **Command(命令)**:将请求封装成对象,从而使你可用不同的请求、队列或日志来参数化其他对象,并支持可撤销操作。GoF 强调"封装成对象"带来的参数化与撤销能力。典型:GUI 的菜单项、事务型操作、任务队列。
- 二者动机:模板方法固定"流程"、变化在"步骤";命令把"动作"变成"一等公民数据"。

## 为什么重要
- **避免重复流程**:多个类有相同的前后处理(鉴权→日志→业务→收尾),模板方法把公共骨架抽上来,只留差异点。
- **撤销/重做与异步**:命令对象让"操作"可存储、可回放、可入队,是实现 Undo、宏、任务调度的关键。
- **与框架呼应**:Spring 的 `JdbcTemplate`、Servlet 的 `doGet/doPost` 都是模板方法思想的体现;消息队列里的一条消息本质上也是命令对象。
- **面试加分项**:能讲清模板方法 vs 策略(一个靠继承固定流程、一个靠组合替换算法),显得理解深入。

## 常见坑
- **模板方法过度抽象**:把不该固定的步骤也锁死在父类,子类反而被束缚;只固定真正稳定的骨架。
- **钩子方法(hook)误用**:本该由子类决定的钩子被写死,失去弹性;或钩子语义不清让子类困惑。
- **命令对象膨胀**:每个操作都建命令类,类数量激增;轻场景可用闭包/函数替代。
- **撤销实现遗漏**:只实现了 execute 忘了 undo,或 undo 没逆序处理多步副作用。

## 动手自测

2. 用命令模式实现一个"文本编辑器"的撤销栈:每个操作(插入/删除)封装为命令,支持 undo。
3. 对比:模板方法(继承,父类控流程) vs 策略(组合,调用方换算法)——何时用哪个?
4. 指出你们项目里"固定流程 + 可变步骤"的代码,设计成模板方法。

## 面试视角
- "模板方法和策略模式的区别?" → 模板靠继承固化流程、子类填空;策略靠组合注入算法、运行时替换。两者一个纵向一个横向。

- "JdbcTemplate 是哪种模式?" → 模板方法(固定资源管理骨架,SQL 回调交给调用方)。

## 6. 依赖注入与 IoC

> 引导：DI 是 IoC 最具体的形式，也是 Spring 的心脏；衔接第8章。

## 心智模型
**依赖注入(Dependency Injection, DI)**是控制反转(IoC)最具体的一种形式,也是第8章 Spring 的核心。它的心智模型一句话:**别在自己类里 new 依赖,让"外人"把依赖塞进来**。原来类像个自己买菜自己做饭的人;用了 DI,类只声明"我需要一把菜刀(接口)",至于菜刀是铁的还是陶瓷的、谁造的,由外部组装器决定。这样类只认"菜刀能切"这个抽象,不认具体实现,换实现、做测试都轻松。

## 核心知识点（锚定官方）
- **IoC 本质**:Martin Fowler 在《Inversion of Control Containers and the Dependency Injection pattern》中指出,IoC 是框架掌握主控权、应用代码被框架调用;对轻量容器而言,反转的是"如何查找插件实现"。Fowler 认为 "Inversion of Control" 一词太泛,遂与社区商定更具体的名字——**Dependency Injection**。
- **DI 定义**:由一个独立对象(组装器/容器)把接口所需的实现"注入"到应用类,而非类内部直接 new。Fowler 原文:让一个单独的 assembler 用合适实现填充 lister 类的字段。
- **三种注入形式**(Fowler):①构造函数注入(通过构造参数,如 PicoContainer);②设值注入(setter,如 Spring 早期偏好);③接口注入(实现注入接口,如 Avalon)。
- **与 Service Locator 的区别**:二者都解耦,但 Service Locator 是"类主动向定位器要",DI 是"服务自己出现",故称控制反转;DI 下组件不依赖注入器,配置完不能再向其要更多服务。

## 为什么重要
- **依赖抽象**:类只依赖接口,具体实现可替换、可并行开发、可多环境切换(测试用 mock、生产用真实)。
- **可测试性**:单元测试时注入假实现(stub/mock),无需起真实数据库/网络。
- **Spring 的心脏**:第8章所有 `@Autowired`、构造器注入、IoC 容器,本质都是 DI。不懂 DI 就看不懂 Spring。
- **面试必问**:"什么是 IoC/DI""构造器注入和 setter 注入区别""DI 和 Service Locator 区别"是后端标配题。

## 常见坑
- **构造器注入循环依赖**:A 构造要 B、B 构造要 A,构造器注入直接报错(Spring 无法解决构造器循环);字段/setter 注入可经三级缓存救活(见第8章)。优先构造器注入 + 必要时重构破环。
- **过度注入**:把所有依赖都注入,类变得"什么都依赖",反而暴露设计问题(可能该类职责过多)。
- **用 DI 容器当 Service Locator**:在业务代码里到处 `ctx.getBean()`,又把耦合悄悄搬回来了。
- **字段注入(@Autowired 私有字段)难测**:无法在构造后单独设 mock,且隐藏了真实依赖;推荐构造器注入。

## 动手自测
1. 写一段"朴素"代码:`OrderService` 内部 `new MySQLRepo()`,再改成构造器注入 `OrderRepository` 接口,对比可测试性。
2. 用构造器注入实现两个服务互相依赖时报错,分析为何构造器循环无解。
3. 列出 DI 三种形式的代码样例,并说明 Spring 为何推荐构造器注入(不可变、必填依赖显式)。
4. 解释"为什么 DI 比 Service Locator 更利于组件复用"——呼应 Fowler 对组件外交付的论述。

## 面试视角
- "什么是 IoC 和 DI?" → IoC 是主控反转的大原则,DI 是它最具体的形式:依赖由外部注入而非内部创建。
- "构造器注入 vs setter 注入?" → 构造器保证必填依赖、不可变、易测;setter 适合可选/可变的依赖。
- "DI 与 Service Locator 区别?" → 一个被动接收(控制反转)、一个主动索取;DI 组件不依赖容器,更利于复用与测试。

## 7. SOLID 五大原则

> 引导：五条让代码不腐烂的纪律，Robert C. Martin 提出；原则是目的、模式是手段。

## 心智模型
**SOLID**是五个面向对象设计原则的缩写,是写出"好改、好测、好扩展"代码的地基。把它们想成**五条让代码不腐烂的纪律**:S 一个类只为一类变更负责;O 加功能改扩展不改老代码;L 子类能无缝替父类;I 接口要小而专;D 依赖抽象不依赖具体。Robert C. Martin 在 2000 年论文《Design Principles and Design Patterns》中提出这些基本原则,2004 年由 Michael Feathers 归纳为 SOLID 这个缩写(据 Wikipedia)。它们不是框架,是写每个类时心里该有的尺子。

## 核心知识点（锚定官方）
Wikipedia 对五原则的定义(SOLID 条目):
- **S 单一职责(SRP)**:一个类应当只有一个导致其变化的原因(never more than one reason to change)。即每个类只承担一项职责。
- **O 开闭(OCP)**:软件实体应当对扩展开放、对修改关闭(open for extension, closed for modification)。
- **L 里氏替换(LSP)**:使用基类指针/引用的函数,必须能在不知情的情况下使用派生类的指针/引用(子类必须可替换基类)。
- **I 接口隔离(ISP)**:客户不应被迫依赖它们用不到的接口方法(clients should not be forced to depend on unused interface methods)。
- **D 依赖倒置(DIP)**:应当依赖抽象,而非具体(depend upon abstractions, not concretes)。
- 起源:Robert C. Martin 2000 年论文提出基础原则, acronym 约 2004 年由 Michael Feathers 提出(Wikipedia 引用 Clean Architecture p.58)。

## 为什么重要
- **对抗软件腐化**:Martin 提出这些原则正是为了对抗 "software rot"(软件腐烂)——改动一处引发连锁故障。
- **可维护可测试**:单一职责让类更小、更易单测;依赖倒置让 mock 替换顺理成章。
- **与本章其他主题呼应**:DIP 就是 DI 的理论来源(第6点);OCP 是策略/装饰器模式的设计动机。
- **面试标配**:几乎必问"讲讲 SOLID""OCP 怎么理解""为什么依赖倒置"。

## 常见坑
- **SRP 误读为"只做一件事"**:它指"一个变化原因",不是"只能有一个方法";一个类可有多个方法,只要都因同一类需求变化。
- **OCP 走向过度抽象**:为了"不修改"而层层接口 + 工厂,小项目反而更绕;OCP 适合**稳定抽象点**,别到处套。
- **LSP 被违反还不知**:子类悄悄加强前置条件或削弱后置条件(如 Square 继承 Rectangle 改宽时偷偷改高),调用方按父类契约用就崩。
- **ISP 缺失**:一个"大接口" `Worker` 含 `code()/test()/deploy()`,让只写代码的同事也被迫实现部署——应拆小接口。

## 动手自测
1. 找一个"又管数据库又管发邮件又管校验"的类,按 SRP 拆成三个协作类。
2. 用策略模式实现一个新计费规则,证明全程没改原有 `BillingService`(演示 OCP)。
3. 写出一个违反 LSP 的继承(如子类抛父类不抛的异常),并修复为组合。
4. 把 `Machine` 大接口按 ISP 拆成 `Printer`/`Scanner`/`Fax` 小接口,让实现类只挑要的。

## 面试视角
- "讲一下 SOLID" → 五字母各一句话定义,最好每点配一个项目中的真实例子。
- "OCP 会不会导致过度设计?" → 承认:只在真正稳定的变化点用,小项目权衡收益。
- "SOLID 和之前的设计模式什么关系?" → 原则是目的,模式是手段;模式(策略/装饰/DI)正是落实 SOLID 的工具。

## 8. DDD 战术：实体/值对象/聚合/仓储

> 引导：领域建模的积木，消灭贫血模型；和第8章 Spring Repository 同源。

## 心智模型
**DDD(领域驱动设计,Domain-Driven Design)**由 Eric Evans 在 2003 年《Domain-Driven Design》提出,核心是"让软件结构贴近业务语言"。战术设计解决"领域对象怎么建模"——用**实体、值对象、聚合、仓储**这些积木,把混乱的"一堆表 + 一堆 Service"重组成有业务语义的对象。类比:贫血模型像"只有姓名年龄、行为全在外部 HR 系统里的人";DDD 的实体像"自己知道怎么涨薪、怎么转正的人",业务规则内聚在对象里。

## 核心知识点（锚定官方）
- **实体(Entity)**:有唯一标识、经历状态变化仍同一的对象(如 `Order` 靠 orderId 区分,不在乎属性变了没)。Evans:由身份而非属性定义。
- **值对象(Value Object)**:无标识、靠属性值相等判等、通常不可变(如 `Money`(金额+币种)、`Address`)。相同属性即相同,可放心共享/拷贝。
- **聚合(Aggregate)与聚合根(Aggregate Root)**:一组相关对象的边界,对外只暴露聚合根;对聚合的修改必须通过根,保证内部一致性。典型:订单(根)包含订单项,删除订单项要走订单的方法而非直接改集合。
- **仓储(Repository)**:封装"聚合的持久化与查询",对外像内存集合,内部可能是 SQL/NoSQL。让领域层不依赖具体数据库。
- **领域服务(Domain Service)**:当某个行为不属于任何单一实体/值对象时(如"跨账户转账"),用领域服务承载,但优先放进实体。

## 为什么重要
- **消灭贫血模型**:把业务规则从散落 Service 收回领域对象,代码读起来像业务文档,改需求时改对地方。
- **一致性边界**:聚合根控制变更入口,避免"订单项负数""库存超卖"这类破坏 invariant 的状态。
- **解耦持久化**:Repository 让领域层只认"存/取",切换 MySQL/Redis/ES 不影响业务。
- **与架构衔接**:第9章微服务"按限界上下文拆分"、第8章 Spring 的 Repository 抽象,思想都源自 DDD。
- **面试加分**:能聊 DDD 战术,说明你不是只会 CRUD,而是懂"为什么这样分层"。

## 常见坑
- **万物皆实体**:把本该是值对象的(如 Money)建成带 ID 的实体,导致无谓的相等判断与持久化开销。
- **聚合边界过大**:把半个系统塞进一个聚合,锁竞争与一致性成本飙升;或边界过小,跨聚合不变量无法保障。
- **聚合根泄漏**:外部直接改聚合内部子对象(绕过根),破坏不变量;坚持"只通过根操作"。
- **Repository 滥用**:在 Repository 里写业务规则,或让 Service 直接拼 SQL 绕过 Repository——二者都让领域层被污染。

## 动手自测
1. 把 `User`(有 id、姓名、地址)拆成实体 `User` + 值对象 `Address`(不可变、按字段相等),写相等性测试。
2. 设计 `Order` 聚合根:提供 `addItem()/removeItem()`,内部维护不变量(订单项不能为负、总额同步),禁止外部直接改 items 集合。
3. 为一个聚合定义 `OrderRepository` 接口(只有 `save/findById`),实现层藏在 infrastructure,领域层只依赖接口。
4. 找你们项目的"贫血 Service",把一段业务规则(如"下单校验库存")移回领域对象。

## 面试视角
- "实体和值对象区别?" → 实体靠标识(identity)、值对象靠属性值相等且通常不可变;举 Money/Address 例子。
- "什么是聚合根?为什么要它?" → 一致性边界 + 唯一变更入口,防止不变量被破坏。
- "Repository 解决什么问题?" → 隔离持久化细节,让领域层不依赖具体存储;呼应第8章 Spring Data。

## 9. 架构风格：Clean/Hexagonal 与分层

> 引导：从全局看依赖往哪指：依赖指向圆心，技术细节推到边缘。

## 心智模型
**架构风格**回答的是"代码怎么分层、依赖往哪指"的全局问题。最经典的是**分层架构**(表现层→业务层→数据层,上层依赖下层)。但传统分层容易让业务层反向依赖框架细节。于是有了 **Clean Architecture(整洁架构)**和**六边形(Hexagonal / 端口与适配器)**:它们的共同信条是——**依赖指向圆心(领域),外圈(框架/数据库/UI)都是可替换的插件**。类比:领域核心像电脑主机(不关心显示器是 Dell 还是三星),外设(端口+适配器)随时可换,主机不受影响。

## 核心知识点（锚定官方）
- **分层架构(Layered)**:经典四层——表现层(Controller)、应用层(用例编排)、领域层(业务规则)、基础设施层(DB/中间件)。上层依赖下层,禁止反向依赖。
- **Clean Architecture(Robert C. Martin)**:同心圆,由内到外是 Entities(企业规则)→ Use Cases(应用规则)→ Interface Adapters → Frameworks & Drivers。核心规则:**源码依赖只能指向圆心**;内圈不知道外圈存在。这样业务规则不依赖 Web 框架、数据库、UI。
- **Hexagonal / 端口与适配器(Alistair Cockburn)**:应用核心通过"端口"(抽象接口)与外界交互,具体"适配器"把端口接到真实技术(DB、HTTP、MQ)。核心不认技术细节,换技术只换适配器。
- 三者一脉相承:都主张"把会变的技术细节推到边缘,把稳定的业务留中央"。

## 为什么重要
- **技术可替换**:哪天从 Spring MVC 迁 WebFlux、从 MySQL 迁 PostgreSQL,只要换适配器,领域与用例不动。
- **可测试**:核心不依赖框架,纯单元测试即可覆盖业务,不需起容器。
- **对抗耦合腐烂**:明确"依赖指向",禁止表现层逻辑漏进数据层、数据层反向污染业务。
- **与前面呼应**:DDD 战术(第8点)落在领域层;Repository 就是典型的"端口",基础设施是它的"适配器"。

## 常见坑
- **依赖反向**:业务层 import 了 Controller 或具体 DAO 实现,破坏"依赖指向圆心",重构时牵一发动全身。
- **贫血分层**:每层只是"转发",业务逻辑全挤在 Service 里变成"事务脚本",分层形同虚设。
- **过度分层**:小项目硬套四层 + 六边形,样板代码淹没业务;架构服务于复杂度,不匹配就简化。
- **把框架当核心**:直接在实体里写 JPA 注解、在 Use Case 里调 HttpServletRequest,核心被框架绑架。

## 动手自测
1. 画一张 Clean Architecture 同心圆,标出你的项目里哪些类属于 Entities / Use Cases / Interface Adapters / Frameworks。
2. 找出一处"业务层反向依赖了框架/DAO 具体类"的代码,用依赖倒置(抽接口到内层)修正。
3. 把"发邮件"功能设计成端口(EmailPort)+ 两个适配器(SMTP / 第三方 API),核心只调端口。
4. 对比分层架构与六边形:一个"上下分层"、一个"内外端口",它们解决的是不是同一类耦合问题?

## 面试视角
- "Clean Architecture 的核心是什么?" → 依赖指向圆心、业务不依赖框架;内圈不知外圈,换技术只换外圈。
- "六边形架构解决了什么?" → 通过端口与适配器把技术细节推到边缘,核心可测、可换。
- "你们项目的分层合理吗?" → 能结合真实架构谈"依赖方向""哪里破了规则",比背定义更可信。

## 10. 设计反模式与演进

> 引导：知道好模式还不够，更要识别贫血模型、上帝类、过度设计这些反模式。

## 心智模型
知道"好模式"还不够,更要警惕**反模式(anti-patterns)**:那些"乍一看能跑、长期必然拖垮项目"的写法。最常见的几个:**贫血领域模型**(对象只有数据、行为全在外)、**上帝类/大泥球**(一个类啥都干)、**意大利面条代码**(逻辑交织无边界)、**过度设计**(为不存在的变化堆抽象)。它们就像"用胶带和绳子修桥"——今天能过,明天塌。识别反模式,比背熟 23 个 GoF 模式更能决定代码寿命。

## 核心知识点（锚定官方）
- **贫血领域模型(Anemic Domain Model)**:类只有 getter/setter,业务逻辑散在 Service 里(Martin Fowler 专门撰文批评)。它看似面向对象,实则"过程式",丧失封装与 invariant 保障。
- **上帝类(God Class)/ 大泥球(Big Ball of Mud)**:一个类承担过多职责、或系统无清晰模块边界,所有东西耦合在一起(Fowler、Foote & Yoder 均有论述)。改动风险极高。
- **意大利面条(Spaghetti)**:控制流靠全局状态与随意跳转,无分层、无边界,读不懂也改不动。
- **过度设计(Over-engineering)**:为"将来可能"的变化提前抽象,引入无谓的接口/工厂/反射,反而增加认知负担——与 SOLID 的 OCP 滥用同源。
- 对策:用本章前面所有正面原则(SRP、聚合边界、分层、DI)反向消解这些反模式。

## 为什么重要
- **预防胜于治疗**:能在写代码时就避开反模式,远比重构已腐化的系统便宜。
- **团队共识**:当评审说"这是上帝类""这是过度设计",大家有共同语言,能快速对齐。
- **面试隐性加分**:能主动指出"我这段其实有 X 反模式风险,准备这样改",比只会正面答题显得成熟。
- **与全文呼应**:反模式是"原则没守住"的结果——SRP 没守住→上帝类,OCP 过度→过度设计,DDD 没落地→贫血模型。

## 常见坑
- **把"必要复杂度"当过度设计**:有些抽象确实当前就该有(如多支付渠道),别一味删,看是否真有第二个变化点。
- **贫血模型的"假重构"**:把 Service 改名 DomainService,但逻辑仍在外部,本质没变。
- **大泥球无人敢动**:长期积累后谁都不敢改,靠"复制粘贴续命",技术债利滚利。
- **只识别不行动**:评审指出反模式却没给出迁移路径,问题原地搁着。

## 动手自测
1. 在你项目里找一个"上帝类"或"贫血 Service",写出它的三个具体问题(职责过多/逻辑外溢/难测)与拆分草图。
2. 判断一个抽象是"必要"还是"过度":列出它当前和近期(半年)的真实变化点,若只有一个就降级为简单实现。
3. 把一段贫血代码(实体只有字段、校验在 Service)重构成带 invariant 的领域对象(呼应第8点 DDD)。
4. 起草一条团队 Code Review 清单:出现哪 3 个信号就标记为潜在反模式。

## 面试视角
- "你见过哪些代码反模式?" → 举贫血模型/上帝类/过度设计,并各说一个你实际的处理办法。
- "怎么平衡 SOLID 和过度设计?" → 只在真实变化点抽象,小项目优先简单直白;OCP 不滥用于稳定代码。
- "为什么 DDD 反对贫血模型?" → 行为外置丧失封装与一致性保障;领域对象应自持业务规则(呼应第8点)。
