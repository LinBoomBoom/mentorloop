> 数据来源：直接读取 `data/devmentor.db`（1 次只读查询）、`data/seed-content.json`、源码静态统计。**未改动任何数据。**

## 0. 一句话结论

**这是一个"内容过度供给、验证严重不足、商业闭环未接通"的产品：内容侧堆到了 16,453 题 / 1,810 知识点，而真实用户只有 5 个、学习完成记录 1 条、真实成交 0 笔。**

当前阶段应判定为 **Pre-Pilot（受控内测之前）**，而不是 MVP 或 Beta。项目自定的上线蓝图里有一句话最准确：「代码已经存在，不等于该能力可以对用户承诺」。

真正卡住的不是技术能力 —— 恰恰相反，**数字人 + 语音 + 实时面试这条技术链的完成度是全项目最高的**；卡住的是三件事：

1. **没有真实用户与埋点**，因此产品是否真的帮人提升，目前无法证明，北极星指标无法计算；
2. **内容合规性出现红线风险**：71.4% 的面试题没有任何权威来源标注，与项目自己定的"仅官方权威资料、禁止虚构"原则冲突；
3. **付费闭环最后一公里是断的**：支付走 sandbox，VIP 五项权益自标未实现，按蓝图门槛连"正式免费版"都还没到。

**建议把未来 30 天的重心从"继续产内容"切换到"用 20 个真人跑通闭环 + 堵住内容合规漏洞"。** 内容已经是资产，不再是瓶颈。

## 2. 产品业务分析

### 2.1 产品在卖什么

价值承诺写在 `docs/product-launch-blueprint.md`：*帮助用户识别能力缺口，给出可执行的学习练习路径，并用考试和模拟面试验证提升结果。*

这个承诺本身是成立的，而且**比"题库"更有差异化** —— 因为它的北极星是"完成一次诊断后提升验证的周活跃学习者数"，不是注册量、不是 PV。这是产品定义层做得对的一件事。

### 2.2 三块业务的成熟度落差极大

| 业务 | 成熟度的现状 | 判断 |
|---|---|---|
| **内容消费**（学 / 刷 / 考） | 4 方向 411 章 1,810 节（平均 3,182 字/节）、16,453 题、57 套卷 | 供给过剩，瓶颈是质量与可信度，不是数量 |
| **AI 模拟面试** | 文字/语音/视频/数字人/实时五种模式，4 个 TTS provider、双通道 ASR、真 RMS 口型 | **技术完成度最高**，但零配额治理、零成本上限、零 Eval 集 |
| **VIP 会员** | ¥29/79/199 三档，13 个 VIP 接口，订单+订阅表齐全 | **商业闭环未通**：支付 sandbox，5 项权益自标 `implemented: false` |

三者的节奏严重不同步：**内容做完了、AI 做出来了、钱没收起来。**

### 2.3 关键链路的断点（实测）

主链路本身是通的：`/` → 登录 → 学习小节 → 关联面试题 → `/interview/sim` → 出分 → `/exam/sets/[id]` 复盘 → `/vip`。

但有三处体验断点：

1. **核心入口不在主导航** —— `/interview/sim`（1138 行，全项目最大的页面，也是最有价值的差异化能力）**不在** `app/layouts/default.vue` 的 7 项导航里，只能从题库页、学习路径页、个人中心绕进去。同理 `/resume`、`/referral`。
   → 这是 **花了最大成本造的功能被藏起来了**，属于高性价比修复项。

2. **VIP 页面明示"演示版本"**（`app/pages/vip/index.vue:68`），且部分权益按钮灰显"敬请期待"。
   → 诚实是对的，但意味着付费入口当前没有转化意义。

3. **AI 面试的逐字稿从未落库** —— `interview_sessions` 47 行，`interview_transcripts` 0 行。
   → 需要排查是"本就不写库"还是"写入失败"。这直接决定用户能不能回看面试历史，也决定 Eval 有没有原料。

### 2.4 内容合规：最高优先级红线

项目自定的内容原则是「仅官方权威资料，AI 仅做策展与结构化，严禁虚构」。实测结果与之冲突：

| 指标 | 数值 | 占比 |
|---|---|---|
| 面试题总数 | 16,453 | 100% |
| **`source` 为空** | **11,750** | **71.4%** |
| 有 source URL | 4,703 | 28.6% |
| 题干/答案正文内含 http 链接 | 1,692 | 10.3% |
| **知识小节 `sections` 有来源字段** | **0** | **表结构中根本没有 source 列** |

来源集中在少数站点：MDN、nodejs.org、prometheus.io、microservices.io、Oracle Java Docs、MySQL 8.4、K8s、man7、react.dev、Spring、RabbitMQ —— 这些是真实权威站点，**说明有来源的那部分是认真做的**。

问题在于：8 月 16 日基线是 6,565 题，今天是 16,453 题，**一个月内增加 9,888 题**，而新增的大部分没有来源。速度本身说明是批量生成。

同时 `sections` 表结构只有 `id, chapter_id, title, objective, content, position` —— **没有 source、没有 version、没有 status、没有 reviewed_at、没有 author**，而蓝图 §3.4 明确要求每项内容有来源、版本、发布状态与复审日期。这是**结构性缺失，不是数据没填**。

> **结论**：这不是"写得不够多"，而是"有一批内容经不起审计"。一旦对外引流或收费，这是最先出事的地方。

### 2.5 双轨战略冲突：Web 端 vs 桌面端

- Web 端：SSR + 预渲染，目标是 SEO 与自然流量。
- Electron 桌面端：离线单机，**本机独立 SQLite**（`extraResources` 只带 `seed-content.json`），账号与 Web 端不互通（2026-08-18 已拍板）。

这个组合在今天是自洽的，但埋着一个战略问题：**同一个品牌、两套互不相认的数据**。用户在 Web 端积累的学习进度、错题、面试记录，装了桌面端之后全部归零。

短期（0 真实用户）无痛；一旦 Web 端开始有真实用户，这就是**留存杀手**。

> 建议：现在不必改，但要把"账互通"作为 Web 端产生第 100 个真实用户时的强制门槛提前记入 backlog，届时走云端中心化（部署 Nitro + 桌面端直连远程 API）。

## 3. 架构技术分析

### 3.1 选型评价：务实且正确

| 决策 | 评价 |
|---|---|
| Nuxt 4 SSR 同构，一套代码同时出 Web 与 Electron 桌面端 | **优秀**。省掉一整套后端 API 团队与客户端重复开发 |
| 系统 Node 子进程拉起 Nitro server（`electron/main.mjs`） | **正确**。规避 Electron ABI 重建 better-sqlite3 的巨坑 |
| 服务端倒计时 + `(user_id, set_id, submit_nonce)` 唯一索引防重复提交 | **正确**。分数以服务端为准，这是考试类产品的及格线 |
| 版本化迁移 `MIGRATIONS` v1–v20+，`schema_migrations` 记录版本 | **正确**。34 次迁移说明一直在演进，机制是健康的 |
| 非 JWT，用随机 token + SQLite sessions 表 + HttpOnly Cookie | **合适**。注销/封禁可即时失效，优于无状态 JWT |
| scrypt 密码哈希 + 登录失败锁 15 分钟 + 统一延迟防时序侧信道 | **到位** |
| 单词发音/千人千面的数字人走 DiceBear 2D 而非 3D VRM | **务实**。零资源开销，规避 VRM 资源成本 |

选型整体挑不出毛病，而且踩坑记录（`docs/desktop-stale-content-root-cause.md`）写得比多数团队认真。

### 3.2 三个承重瓶颈

**瓶颈一：`server/utils/db.ts` 1845 行的 God Module。**
Schema 定义、20+ 次迁移、全部业务查询、鉴权（`getUser`/`requireAdmin`/`requireVipUser`）、订单发货、会员有效期计算全塞在一个文件里。任何一处改动都有回归风险，且无法按业务域拆分测试。
→ 建议拆成 `db/schema.ts` / `db/migrations/` / `db/queries/*.ts` / `db/auth.ts`。这是**低风险高收益**的重构，因为纯搬运、不改语义。

**瓶颈二：内存限流 + 单文件 SQLite，锁死了横向扩容。**
`rateLimit()` 是进程内 Map 滑动窗口（`server/utils/security.ts:20`），共 23 处调用。一旦 Web 端真上生产且跑多实例，**同一 IP 的限流计数会按实例数放大**，session 也存在库里需要粘性或共享。
→ 单实例部署无碍；若要上量，先换 Redis 限流 + 连接池/读写分离，或者干脆把 SQLite 换成 Postgres。**这是"部署时延后付的债"，不是现在的 bug。**

**瓶颈三：前端状态管理近乎缺失。**
Pinia 只有 1 个 store（`app/stores/auth.ts`）。`sim.vue` 单页持有 30+ 个 ref（phase/mode/messages/wsConnected/rtActive…），1138 行。加上 Tailwind 语义类与 ant-design-vue 双 UI 栈并行（`a-button` 256 次、自写 `.btn` 并存），以及 antd 未配 dark theme token（暗色下大概率不跟随）。
→ **建议在重构 sim.vue 之前先补 store**，否则拆分只会把 30 个 ref 从一个大文件搬进另一个大文件。

### 3.3 AI 能力：技术最优，治理最弱

完成度值得肯定：DeepSeek 流式 SSE + AbortSignal 支持打断（barge-in）、首题优先命中本地题库降级才调 LLM、prompt 记忆化设计提高前缀缓存命中率、4 通道 TTS（含阿里云 CosyVoice 43 音色）、双通道 ASR（浏览器 SpeechRecognition + MediaRecorder 上传）、真 RMS 驱动的口型。

**但治理侧几乎是空白：**

| 缺口 | 证据 | 风险 |
|---|---|---|
| 无成本存储 | LLM usage 仅进程内累加 + 打日志（`server/utils/llm.ts:157`），不落库 | 无法回答"一场面试多少钱""今天花了多少" |
| 无配额/预算 | 全仓 grep 无 daily budget / quota 实现 | 一个恶意用户可刷爆 API 账单 |
| 无 Eval 集 | 46 个测试文件全是单元测试，无 AI 输出质量评测 | "效果不好"时无法归因，只能凭感觉改 prompt |
| 无 Trace | 无按 session 串联的模型版本/时延/失败率记录 | 线上 bad case 不可复现 |
| 无降级开关 | 依赖 mock 蜂鸣与"敬请期待"兜底 | 厂商异常时体验断崖 |

蓝图 §3.2 明确要求"单用户限额、日成本上限、超时、重试、模型失败降级文案"—— **目前只有超时（`AbortSignal`）和部分降级**。

### 3.4 工程保障

| 项 | 现状 | 评价 |
|---|---|---|
| 单元测试 | 46 个文件 / 4,183 行（vitest） | 覆盖扎实，尤其 TTS/ASR/头像/限流 |
| E2E | **无** | 蓝图 R0-02 要求浏览器自动化覆盖核心流程，**未达成** |
| lint / typecheck | **package.json 无对应脚本** | 蓝图 §5.1.4 要求 lint/typecheck/test/build 全过，**未达成** |
| CI | `.github/workflows/ci.yml`（npm ci + test + build） | 有，但缺少 lint/typecheck/E2E/依赖漏洞扫描 |
| 埋点/可观测 | **无事件埋点系统**；有 healthReport（db/tts/disk）与 request 日志 | 北极星指标**无法计算** |
| CSP | 含 `'unsafe-inline'`（因首屏内联主题脚本），待 nonce 方案 | 已知，需改 nonce |
| CORS | **全仓无任何 CORS 配置** | 依赖同源 + `sameSite=lax` 隐式防护，跨域场景未显式处理 |
| 备份 | `scripts/backup-db.mjs` + `tests/backup.test.mjs` | 有，但未见恢复演练记录（蓝图 §5.1.3 要求） |

## 5. AI 机会门：哪些值得继续做 AI 化

按业务价值 × 频率 × 数据可得 × 可实现 × 可评测 × 风险打分：

| 候选场景 | 价值 | 数据 | 可行性 | 结论 |
|---|---|---|---|---|
| **已做**：AI 模拟面试（文字） | 高 | 高（题库 + 47 场 session 记录） | 已实现 | **P0 守**——补 Eval + 配额，别再加模式 |
| **已做**：AI 模拟面试（语音/数字人） | 中 | 中 | 已实现 | **P0 稳**——技术已最强，但成本未知，先限量灰度 |
| AI 面试报告 → 错题/课程回流 | 高 | 高（`user_wrong_items`、`skill_section_map` 已建表） | 高 | **P0 做**——把测评结果变成学习动作，是"闭环"缺的那一环 |
| 面试答案质量自适应评分 | 中 | 低（无标注样本） | 中 | **P1**——先攒 100 场真人数据再谈 |
| 简历诊断 → 岗位匹配 | 中 | 低 | 中 | **P2 暂缓**——已实现文件解析与 AI 诊断，但"人工 1v1"不可承诺 |
| 学习路径个性化生成 | 中 | 中（`study_plans` 4 条） | 高 | **P1**——依赖掌握度信号，先有用户数据 |
| 内容策展/批量出题 | **负** | — | — | **停止**——这是当前风险的来源，不是机会 |

> 最重要的一句话：**本项目不缺 AI 场景，缺的是"证明 AI 有用"的证据。** 在拿到真实用户行为之前，再增加一个新 AI 功能都是在增加不可评估的成本。

### 90 天：再谈钱

## 7. 需要你拍板的 6 个决策

1. **内容策略**：11,750 道无来源题，是补录来源、降级为草稿，还是直接下线？（我的建议：先冻结不再发布，分批补源，补不上就下线）
