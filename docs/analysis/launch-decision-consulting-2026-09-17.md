## 1. 内容合规：能标注，但标注 ≠ 合规

### 1.1 先分清三个性质不同的问题

你把"标注"当作解法，但合规其实是三件事，**标注只能解决其中一件半**：

| 风险类型 | 标注能否解决 | 说明 |
|---|---|---|
| **学术/商业诚信**（不注明出处） | ✅ 能 | 标注来源即可消除"抄袭""不正当竞争"的指责 |
| **许可传染**（CC BY-SA 的 ShareAlike） | ⚠️ 部分 | 署名是必要条件，但 ShareAlike 要求你的衍生作品**同样以 CC BY-SA 发布**——这与收费闭源产品实质冲突 |
| **版权侵权**（未经许可复制受保护表达） | ❌ 不能 | 权利人明示禁止再分发时，**标注了来源依然是侵权**。Oracle MySQL 手册原文写得很清楚 |

### 1.2 实测分级（16,453 题）

我按来源域名跑了许可分级，结果见对话中的图。核心数字：

| 档位 | 题数 | 占比 | 含义 |
|---|---|---|---|
| **无来源** | 11,750 | 71.4% | 无法评估，风险未知 |
| 🟡 黄灯 | 2,464 | 15.0% | ShareAlike 传染或待核实（MDN 1,296 / microservices.io 337 / RabbitMQ 122 / Redis 119 / Vue 115 / OpenAI 100 / OWASP 79 / Docker 75 等） |
| 🟢 绿灯 | 1,303 | 7.9% | Apache-2.0 / MIT / CC-BY-4.0，署名即可（Node 406 / Prometheus 387 / K8s 220 / React 149 / Spring 141） |
| 🔴 红灯 | 936 | 5.7% | 权利人明示禁止复制·再分发·出版 |

**红灯明细**：man7.org（Linux man-pages）373 · docs.oracle.com（Java Docs）324 · dev.mysql.com（MySQL 8.4 手册）239。

MySQL 手册的法律声明原文（我已核实）：

> 「除非您的许可协议中明确允许或法律允许，否则您不得以任何形式、通过任何方式使用、复制、重制、翻译、广播、修改、许可、传输、分发、展示、执行、出版或呈现任何部分。」

这句话的意思很直白：**你标了"来源：MySQL 8.4 手册"也不能复制它的内容。**

### 1.3 比"无来源"更麻烦的发现：source 字段本身不可信

我在核查时发现：有 source 的 4,703 题里，**95 题的 source 是从答案正文里误抓的示例字符串**。真实例子：

```
https://bank.com/api/change-email"      ← 一道 CSRF 题的示例代码
https://your-site.com（不能是            ← 后面还带着中文
http://order-svc/orders`                ← 微服务题里的假服务名
https://{{                              ← 模板占位符没渲染
https://cdn.../1.2.3/entry.js"          ← 省略号
https://api.com'
```

这说明 source 的生成方式是「**从答案文本里正则抓第一个 http 链接**」，而不是真实溯源记录。

由此得出两个结论：

1. **source 字段当前不能作为合规依据**。即使补满了，也需要换成"生成时显式指定"的机制才有意义。
2. 那些批量指定的（MDN 1,296、Node 406 这类整数聚集的域名）可信度相对高，因为它们是"出题时指定参考站点"，不是抓取的。

### 1.4 真正决定风险的是"改写度"，不是"来源"

法律上有个关键分界，你需要知道：

> **事实、知识、操作方法本身不受版权保护；受保护的是"具有独创性的表达"。**

所以：

| 做法 | 风险 |
|---|---|
| 问"MySQL RR 隔离级别如何解决幻读"，用自己的话写答案 | **低**。这是事实性知识，且表达该事实的方式有限（法律上的"合并原则"） |
| 照搬手册的句子结构、示例、图示 | **高**。这是复制表达 |
| 复制官方示例代码 | **高**，除非该代码示例是 CC0（MDN 代码示例是 CC0，可放心用） |

**所以真正的风险判定需要看"改写度"，而这件事我还没做** —— 需要拿源文档做文本比对。

### 1.5 可执行方案（按性价比排序）

**第 1 步：给内容打上可审计的字段（1 天，纯结构改动）**

给 `sections` 和 `interview_questions` 加列：

```
source_url TEXT        -- 生成时显式指定，不再从正文抓取
source_type TEXT       -- official-docs / book / blog / llm-generated / human-written
license TEXT           -- cc-by-4.0 / apache-2.0 / cc-by-sa / proprietary / unknown
rewrite_level TEXT     -- verbatim(照搬) / paraphrased(改写) / original(原创)
status TEXT            -- draft / review / published / archived
reviewed_at INTEGER
version INTEGER
```

这一步不做任何内容判断，只是把"能不能审计"的先决条件建起来。**建议今天就做**，因为越晚加，新增内容越难补。

**第 2 步：红灯 936 题优先处理（2–3 天）**

按 `license='proprietary'` 标记，**默认不发布**。逐批判断：
- 是"引用事实 + 自己改写" → 补 `rewrite_level='paraphrased'` 后可发
- 有大段照搬 → 重写或下线

936 题占 5.7%，工作量可控。

**第 3 步：清洗 95 条污染 source + 冻结抓取逻辑**

改生成脚本：source 必须由出题流程**显式传入**，不允许从正文正则提取。已污染的改成 NULL 并重跑分级。

**第 4 步：无来源 11,750 题的分类处置**

这是大头，建议按赛道分批，每批处理时用这个规则：
- 能追溯生成时参考站点的 → 补 `source_url` + `license`
- 追溯不到、且判断是 LLM 自由生成的 → 标 `source_type='llm-generated'`，**这类需要人工抽检**（LLM 可能复现训练语料中的受保护表达）
- 抽检不合格的 → 下线

**第 5 步：建立"发布门禁"**

管理台不允许 `status='draft'` 或 `license='proprietary'` 的内容被发布。这是蓝图 §3.4 已经要求的，现在正好一起做。

### 1.6 什么时候必须做完

| 场景 | 要求 |
|---|---|
| 仅自己/小范围演示 | 第 1 步即可 |
| **公开免费上线** | 1–4 步，红灯必须清零 |
| **开始收费** | 全部 5 步 + 一次专业 IP 复核。商业性使用会让"合理使用"抗辩显著变弱 |

## 2. 数字人 / 语音 / 实时面试：建议降级为"增强层"

### 2.1 "效果差"要先归因，笼统优化会白花钱

"数字人和语音都很差"是一个模糊判断。它至少包含六个独立问题，**解法完全不同**：

| 环节 | 典型症状 | 怎么验证 | 修复成本 |
|---|---|---|---|
| **TTS 音色/自然度** | 机械、断句怪、音色不搭 | 5 人盲听打分（对比真人录音） | 低——换音色 / 调速 / 调参 |
| **口型同步** | 嘴动得不对、幅度怪 | 录屏逐帧看 | 低——调 `smoothMouth` attack/release |
| **ASR 识别率** | 技术术语听不懂（八股文术语密集） | 20 条真实回答测字错率 WER | 中——需要**热词表**（把技术名词灌进去） |
| **LLM 追问质量** | 不像面试官、追问泛泛 | 10 场人工评分 | 中——改 prompt + 加真实面试脚本做 few-shot |
| **端到端延迟** | 说完要等 3–5 秒 | 分段计时（ASR/LLM/TTS 各多少） | 中——改流式、三跳并行 |
| **实时模式链路** | WebSocket 断连、状态不同步 | 完整走一遍并抓 trace | 高 |

**建议先花半天做归因，再决定投不投。** 如果是"ASR 术语识别差"，加热词表就能解决大半，成本极低；如果是"LLM 不像面试官"，那是产品定位问题，投多少钱都未必能变好。

### 2.2 一个硬证据：链路确实没走通

`interview_sessions` 有 47 行，`interview_transcripts` 是 **0 行**。

逐字稿一条都没落库。这意味着：
- 用户无法回看自己的面试历史（功能缺失）
- 你没有任何可用于评测的语料（**这才是"效果差却无法改进"的根因** —— 没有原料就没法做 Eval）

建议把它当作 P0 缺陷排查，不管这条线最终做不做，这个数据都要能落库。

### 2.3 我的决策建议：三线分离

不是"做"或"不做"，而是**分成三条独立决策**：

| 线 | 建议 | 理由 |
|---|---|---|
| **文字面试** | **P0，做到可靠** | 成本最低、效果最可控、是真实面试的主体形态。语音只是交互方式，不是价值本身 |
| **语音（ASR + TTS）** | **P1，默认关闭，可开启** | 作为文字面试的输入输出替代。有降级路径：ASR 失败 → 手动输入，TTS 失败 → 纯文字 |
| **数字人** | **P2，暂时冻结** | 纯视觉装饰，不产生学习价值，却是三条线里维护成本最高的一条（口型、渲染、资源） |

**为什么建议冻结数字人**：它不解决用户的任何核心问题。用户要的是"通过面试"，不是"看一个头像动嘴"。在一个 0 用户、合规待处理、链路未通的项目里，把资源压在这上面是错配。

**什么时候该解冻**：当你有真实用户，且他们明确表示"数字人让我更愿意练"时。

### 2.4 如果坚持要继续做，先建评测

没有 Eval 集，"效果差"永远只能靠感觉。最小可行做法：

- 30 道题的面试题库 × 期望评分维度（追问相关性、专业深度、表达清晰度）
- 5 人盲评，得出 baseline 分
- 每次改 prompt / 换模型，重跑一遍对比
- 成本指标同时记录：单场 token 数、延迟 P50/P95

**没有这个，你无法回答"改了之后是变好还是变差"。**

## 4. 上线是否具备盈利可能：诚实回答

### 4.1 先看竞争格局，这决定你的定价权

IT 面试准备赛道已经非常拥挤：

| 对手 | 特点 | 对你的压力 |
|---|---|---|
| **牛客网** | 题库 + 校招社区 + 内推，品牌强 | 题库免费、社区活跃 |
| **极客时间 / 慕课网** | 付费课程，有名师背书 | 同样的 ¥29 档，人家有品牌 |
| **力扣** | 算法霸主 | 拿走了算法这块 |
| **JavaGuide / CS-Notes 等开源仓库** | **完全免费、质量高、10w+ star** | **这是最直接的替代品** |

残酷但必须面对的事实：**你的 16,453 道题，如果不能明显超过 JavaGuide 这类免费开源仓库，就没有定价权。**

而"题目数量"本身不是壁垒 —— 你已经证明了批量生成很容易（一个月能从 6,565 涨到 16,453）。**别人也能。**

### 4.2 当前形态的三个问题

1. **差异化最贵的那一环，恰好效果最差。** AI 语音面试是你的差异化卖点，但你自己说"效果很差、没走通"。这意味着你准备拿最贵的能力去做最不确定的卖点。
2. **前端 / 后端是最卷的两个方向**，你的 411 章里前端 152 章、后端 117 章，主力压在红海。
3. **没有品牌、没有名师、没有社区**，直接卖 ¥29/月 缺乏信任基础。

### 4.3 我认为真正可行的差异化（按可行性排序）

| 差异化 | 为什么可行 | 难度 |
|---|---|---|
| **① 桌面端离线单机** | **几乎没人做**。目标用户：不想把简历、面试录音、学习记录上传云端的隐私敏感用户。这是真实存在的需求，且你的 Electron 架构已经支持 | 已有，需打磨 |
| **② 垂直切入运维 / AI 工程** | 前端/后端是红海；运维 78 章、AI 工程 64 章，竞争小得多，且 AI 工程是增量市场 | 中 |
| **③ 闭环而非题库** | "学 → 练 → 考 → 面 → 复盘 → 回流"是完整的，牛客偏社区、极客偏课程，没人把闭环做透 | 中（需要把回流接上） |
| ④ AI 面试 | 有想象空间，但**当前效果不支持作为付费卖点** | 高 |

### 4.4 盈利的前提条件（缺一不可）

- [ ] 有真实用户数据证明"用了能提升"（不是自我感觉）
- [ ] AI 面试要么做到可用，要么不作为卖点
- [ ] 内容合规过关（收费会显著提高侵权风险等级）
- [ ] 找到免费替代品覆盖不到的点（隐私 / 垂直 / 闭环）
- [ ] 有获客渠道（内容 SEO 是一条，但慢）

### 4.5 我的判断

**当前形态直接盈利的可能性：低（我估 15–20%）。**

不是因为产品做得差 —— 恰恰相反，代码质量在同类个人项目里是上游水平。而是因为：

> **它现在是一个"什么都有的通用产品"，而通用产品在成熟赛道里赢不了。**

**如果目标是盈利，我建议的方向**：砍掉"全方向通用"的幻想，聚焦 **「运维 / AI 工程垂直 + 桌面端离线隐私」**，先把一个细分做透、做出口碑，再横向扩展。

**如果目标不是盈利**（比如作为作品集、技术验证、自用工具），那当前形态完全够用，不必为此焦虑 —— 只是要诚实标注"演示版"，不收费。

## 5. 技术栈需要改吗：不需要

### 5.1 结论与理由

**Nuxt 4 + SQLite + better-sqlite3 这套选型，撑到你盈利都没问题。**

- SQLite：当前库几十 MB，SQLite 轻松处理 GB 级。WAL 模式一写多读，你这个场景（读远大于写）完全够
- Nuxt 4 SSR 同构一套代码出 Web + Electron：**这是全项目最正确的架构决策**，别动
- 唯一真实约束是写并发，但你的写操作（学习进度、答卷、打卡）QPS 极低

**换栈是此刻最不划算的事** —— 它会消耗掉你本该用来解决"合规 + 链路 + 定位"的所有时间，换来一个你三年内都用不上的扩展性。

### 5.2 什么时候才该改（触发条件）

满足任一才考虑：

| 触发条件 | 改什么 |
|---|---|
| 需要多实例水平扩容 | 限流换 Redis；session 外置 |
| 需要 Web 与桌面端账号互通（云端中心化） | SQLite → **PostgreSQL**（这一步要提前规划） |
| 单表超过千万行且查询变慢 | 分表 / 迁 Postgres |
| 团队扩张到需要按域分工 | 拆服务 |

### 5.3 现在真正该改的是这些（都不是技术栈）

1. 加 lint / typecheck（半天，收益立竿见影）
2. 拆 `db.ts`（1–2 天，纯搬运）
3. 建 Pinia store 再拆 `sim.vue`（2–3 天）
4. 加埋点（1 天起）
5. 补内容合规字段（1 天）
