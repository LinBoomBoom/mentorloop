# 叶子登记与挂枝规则（宪章第三条操作化）

> 操作化宪章 **第三条（准入）** 与 **第八条（变更纪律）**，回答一个问题：**当我要新增一个具体工具 / 版本 / 配置 / 技巧（叶子），怎么登记、挂到哪、写什么、标什么时效**。
> 配套脚手架：`scripts/leaf_register.mjs`（生成合规草稿，降低登记门槛）。

---

## 1. 什么是"叶子"

宪章分层模型三层：

| 层 | 含义 | 示例 | 典型寿命 |
|---|---|---|---|
| `trunk` | 稳定核心原理 | 事件循环、CAP、TCP | > 10 年 |
| `branch` | 技术域 / 框架 | React、K8s、MySQL | 3–10 年 |
| `leaf` | 具体工具 / **版本** / 配置 / 技巧 | React 19 的 `use` hook、K8s 某 API 版本、某 CLI 参数 | < 3 年 |

叶子是树**生长最快、最易过期**的一层。登记门槛不是"值不值得写"，而是"能不能挂到既有 trunk/branch 之下、是否重复、来源可不可锚"。

---

## 2. 五问准入快查（宪章 3.1）

拟新增任一节点，五问全过才准入，任一不过即驳回：

| # | 问 | 不过的处理 |
|---|---|---|
| 1 | 过去 12 个月真实面试被问到（或明显将被问）？ | 不入 |
| 2 | 掌握它是否提升工程能力，而非记忆谈资？ | 不入 |
| 3 | 能否指向官方文档 / RFC / 论文 / 源码作事实来源？ | 补来源，否则不入 |
| 4 | 现有 330 节中是否已有等价内容？ | **增强旧节，不新增**（见 §6） |
| 5 | 能否明确挂到某个 trunk/branch 之下？ | 挂不上 → 走提案流程（缺枝干而非叶子） |

> 第 4 问是高频错误源：多数人想"新开一章"，其实 90% 情况是增强某节。先用 `grep`/`doc:` 图谱确认无重复。

## 3. 挂枝决策树（宪章 3.1 #5）

```
新知识点
  │
  ├─ 是「稳定原理 / 跨框架通用」？ ──→ 挂 trunk（如 op-c1 Linux）
  │
  ├─ 是「某框架 / 技术域」且会演进？ ──→ 挂 branch（如 fe-c9 React）
  │
  └─ 是「该框架下的具体工具 / 版本 / 配置 / 技巧」？
        │
        ├─ 能找到承载它的 branch/trunk 章？ ──→ 作为该章下新 section（叶子）
        │
        └─ 找不到（如一个全新框架）？
              │
              ├─ 该框架够格成 branch（有面试/有生态/有继任关系）？ ──→ 提案新 branch 章
              │
              └─ 不够格？ ──→ 不登记（或仅作「演进脉络」历史对比）
```

**关键纪律**：叶子永远挂在既有章之下，**不单独成章**。单独的"工具章"会稀释 trunk 骨架（宪章红线：trunk 章占比 < 40% 即崩）。

## 4. 命名规范（宪章 8.5）

- section 标题用「名词短语」，避免动词句；同一章内体例一致。
- 含版本号的叶子，标题可带版本：`React 19 的 use() hook` 优于 `use hook`。
- 锚定具体 CLI / API 时，写明版本边界：`kubectl apply --prune（K8s ≥ 1.17）`。
- 不造缩写、不中英混杂（专有名词保留英文即可，如 `Backstage`）。

---

## 5. 最小完备件 DoD（宪章 3.2）

新叶子合入时**必须同时具备**，缺一不可：

- ✅ **V1 六段式完整**：心智模型 / 核心知识点（锚定官方）/ 为什么重要 / 常见坑 / 动手自测 / 面试视角
- ✅ **事实锚定官方**，不臆造（给出来源链接或版本号）
- ✅ **时效元数据块**（第四条 4.1）：`> 时效 | 核验=日期 | 风险=… | 版本=… | 来源=…`
- ✅ **至少 1 条 `doc:` 互链**（前置 / 对比 / 后续三选一），杜绝孤岛
- ✅ **命名符合规范**（第八条 8.5）

---

## 6. 增强旧节 vs 新增：判定口诀

> **"同一框架下的不同版本/技巧 → 增强；不同框架但同类能力 → 新叶子挂同 branch；全新领域 → 提案 branch。"**

例：
- 「React 19 `use` 支持异步」→ 增强 `fe-c9` 下相关节（或新增该章下新 section）。
- 「SolidJS 的细粒度更新」→ 新叶子，挂在 `fe-c9` 同级的"响应式框架"比较节，或 `fe-c9` 内对比段。
- 「一个全新的前端框架 X」→ 提案新 branch 章（走评审，非随手加）。

## 7. 登记脚手架用法

```bash
node scripts/leaf_register.mjs \
  --module devops --parent op-c8 \
  --title "Backstage 软件目录与脚手架" \
  --source 官方 --risk 高 --version "Backstage 1.x"
```

脚本输出一段合规草稿（时效块 + 六段式骨架 + 互链提示），复制进 `docs/` 审稿稿，经 `scripts/inject_any.mjs` 注入对应章即可。全程**零 schema 漂移**——只在 markdown 内容内工作。
