# 第13章 · 安全与认证授权

> 目标：建立认证(Authentication)与授权(Authorization)的分层认知(AAA);掌握 Session-Cookie 与 JWT 两种会话范式的取舍;理解 OAuth 2.0(RFC 6749)授权码流程与 JWT(RFC 7519)结构及 alg=none / 算法混淆伪造风险;用 OWASP 规范落地密码加盐哈希(Argon2id)与 SQL 注入参数化防护;区分 XSS 与 CSRF 并各自设防;用 RBAC/ABAC 构建可扩展授权体系;以纵深防御框架串联安全响应头与 OWASP Top 10 自查。

## 1. 认证与授权:AAA 基础

> 引导：先分清 authentication 与 authorization 这对最常被混用的概念,建立 AAA 分层视角,这是后面所有安全机制的认知底座。

## 心智模型
把安全想成一套「钥匙与门禁」系统:认证(Authentication)回答「你是谁」,授权(Authorization)回答「你能进哪扇门、做什么」。很多人把这两个词混为一谈,但一个是验明正身,一个是发放权限。再往外一层是「审计」(Audit)——记录谁在什么时候做了什么,三者合称 AAA(Authentication、Authorization、Accounting)。理解这套分层,安全设计就不会一锅粥。

## 核心知识点（锚定官方）
- **认证 vs 授权**:认证是验证主体身份(密码、OTP、生物特征、证书),授权是决定该身份能访问哪些资源、执行哪些操作。OAuth 2.0 规范(RFC 6749)开篇即明确它是「authorization framework(授权框架)」,解决的是第三方受限访问的委托,而非身份识别本身。
- **鉴权三要素**:你知道的(密码/ PIN)、你拥有的(手机/ 硬件 token)、你本身的(指纹/ 人脸)。多因素认证(MFA)即叠加其中两类以上。
- **常见认证协议**:Session-Cookie(服务端保存状态)、JWT(无状态声明)、OIDC(在 OAuth2 之上叠加身份层,补齐「认证」语义)。
- **纵深防御(Defense in depth)**:没有银弹,网络层、应用层、数据层各自设防,任一层被突破都不致全盘崩溃。

## 为什么重要
认证授权是系统的「门锁」。一旦错配,轻则越权看到他人数据,重则被接管管理员账户、拖库。OWASP Top 10(2021)中 A01 失效的访问控制(Broken Access Control)已跃居榜首,说明「授权」这一环在实际漏洞里最普遍也最致命。

## 常见坑
- 把登录接口返回的用户 id 当作用户身份信任,却不在每次请求校验会话合法性,导致可篡改 `userId` 越权。
- 用「前端隐藏按钮」做权限控制,后端不校验,攻击者用 curl 直接打接口。
- 混淆认证与授权:以为签发了 JWT 就等于完成认证,实则 JWT 只是承载声明的载体,签发前的身份核验才是认证。

## 动手自测
1. 画出「用户登录 → 访问 /api/order/{id}」全流程里,认证与授权分别发生在哪一步?
2. 如果删掉后端的所有权限注解(如 `@PreAuthorize`),仅靠前端不显示按钮,系统还安全吗?为什么?
3. 列举你项目中用到的 MFA 场景,并说明它叠加了哪两类要素。

## 面试视角
八成会被问「认证和授权有什么区别?JWT 和 Session 怎么选?」。回答要落到权衡:Session 服务端可控、易注销、但有状态需共享存储;JWT 无状态、易水平扩展、但注销难(需短有效期+ 黑名单或刷新令牌机制)。别只背定义,要讲场景取舍。

## 2. 会话管理:Cookie/Session 与 JWT

> 引导：对比有状态会话与无状态令牌两种范式,理解各自的安全属性(HttpOnly/SameSite/刷新令牌),为鉴权方案选型打底。

## 心智模型
会话(Session)是服务器给「这次来访」发的一张临时通行证,存在服务端;JWT 是把通行证信息刻在票面上、由服务器签名、客户端自己携带的「防伪票据」。一个状态在服务器端,一个状态在票据里。选哪个,本质是「要不要让服务端记住你」。

## 核心知识点（锚定官方）
- **Cookie + Session**:用户登录后服务端生成 sessionId 存入内存/Redis,通过 `Set-Cookie` 下发,浏览器自动携带。服务端按 sessionId 查状态,注销只需删服务端记录。**HttpOnly + Secure + SameSite** 属 Cookie 安全基础属性。
- **JWT 无状态**:RFC 7519 定义 JWT 为紧凑、URL 安全的声明载体,由 base64url 编码的 Header.Payload.Signature 三部分以点拼接;服务端用密钥(HMAC)或私钥(RS256/ES256)签名,资源方验签即可信任,服务端不保存状态。
- **刷新令牌(Refresh Token)**:access token 短期有效,JWT 过期后用长期 refresh token 换发新 token,缩小盗用窗口。
- **SameSite Cookie**:`Strict/Lax/None` 决定跨站请求是否携带 Cookie,是防御 CSRF 的重要底座。

## 为什么重要
会话方案直接决定系统的可扩展性、注销能力与攻击面。水平扩展的微服务里,Session 需要共享存储(Redis);JWT 则把扩展压力转嫁到签名校验。选错会让注销、单点登出、并发控制都变痛苦。

## 常见坑
- JWT 存 localStorage 被 XSS 一锅端;应优先 HttpOnly Cookie。
- 把 JWT 当 Session 用且不设短过期,泄露后无法吊销。
- 误以为 JWT 加密了——默认 JWT 只是签名(base64url 明文),敏感声明应额外加密(JWE)或干脆不放。

## 动手自测

2. 给 Cookie 加 `SameSite=Strict` 后,从第三方站点跳转回来还会自动登录吗?为什么?
3. 设计一个支持「单点登出」的 JWT 方案,你会用黑名单还是短时效+ 刷新?列出取舍。

## 面试视角
高频题「JWT 和 Session 区别、怎么选」。讲清无状态/ 有状态的本质差异,并主动提到 JWT 的吊销难题与 refresh token 机制;能顺带提 JWE 与 XSS 存储风险,基本就过关了。

## 3. OAuth 2.0 授权框架

> 引导：锚定 RFC 6749,厘清四大角色与授权码流程,明确它是授权框架而非认证协议,避免把 access token 误当身份。

## 心智模型
OAuth 2.0 不是「让第三方登录」这么简单,它是一套「授权委托」协议:你(资源所有者)告诉授权服务器「允许这个 App 代我看我的资料」,授权服务器发给 App 一张「访问令牌」,App 凭令牌去资源服务器取数据——全程不碰你的密码。

## 核心知识点（锚定官方）
- **四大角色(RFC 6749 §1.1)**:Resource Owner(你)、Client(第三方 App)、Authorization Server(授权服务器)、Resource Server(资源服务器)。
- **授权码流程(Authorization Code,§4.1)**:Client 把用户重定向到授权端点,带 `response_type=code` + `client_id` + `redirect_uri` + `state`;用户登录并同意;授权服务器重定向回 `redirect_uri` 带上 `code`;Client 在后端用 `code` + `client_secret` 向令牌端点换 `access_token`(及可选 `refresh_token`)。
- **access token vs refresh token**:access token 是访问资源的凭据,通常 opaque、短命;refresh token **只发给授权服务器、从不下发到资源服务器**,用于换发新 access token。
- **state 参数防 CSRF**:`state` 应是不 guesses 的随机值,回调时校验,避免攻击者诱导用户发起授权后劫持结果。

## 为什么重要
OAuth 2.0 是开放生态的钥匙:微信/ 支付宝/ GitHub 登录、云厂商 API 授权、企业内部系统互信全靠它。理解它的角色边界,才不会把「拿着 access token」误当成「已经认证了用户」(它只是授权,认证应交给 OIDC)。

## 常见坑
- 把 `client_secret` 写进前端 SPA/ 手机端公开代码里,机密客户端(secret 型)的 secret 必须放后端。
- 授权码流程用裸重定向而不校验 `state`,遭 CSRF 绑定他人账号。
- 混淆 OAuth 与认证:OAuth 是授权框架(RFC 6749),要认证身份应叠加 OIDC(OpenID Connect)。

## 动手自测
1. 用一张时序图画出授权码流程中 code 与 token 各自的传递路径,标出哪一步绝不该出现在浏览器。
2. 如果去掉 `state` 参数,攻击者能如何把授权结果「嫁接」到受害者账号上?
3. 为什么 refresh token 不能发给资源服务器?从泄露面角度解释。

## 面试视角
必考题之一。要把「授权而非认证」讲透,能完整复述授权码流程、说清四种角色与两种 token 的分工,并点出 PKCE(对公开客户端把 `client_secret` 换成 `code_challenge`)的动机——基本就是高阶答案。

## 4. JWT 结构与安全

> 引导：锚定 RFC 7519,讲清三部分结构与签名,重点剖析 alg=none 与算法混淆这两类真实伪造漏洞。

## 心智模型
JWT 像一张盖了公章的介绍信:Header 是抬头(用什么算法)、Payload 是正文(谁、权限、何时过期)、Signature 是公章(对前两部分的签名)。验章通过,你就信这封信;章是假的或算法被调包,整封信作废。

## 核心知识点（锚定官方）
- **结构(RFC 7519 §3)**:`base64url(Header).base64url(Payload).base64url(Signature)`,三部分点分隔,Header 典型为 `{"typ":"JWT","alg":"HS256"}`。
- **签名计算(§3.1)**:对「编码后的 Header + . + 编码后的 Payload」做 HMAC(HS256,共享密钥)或 RSA/ECDSA(RS256/ES256,私钥)签名,再 base64url。
- **alg 头部参数**:声明所用算法;`HS256`(对称)与 `RS256`/`ES256`(非对称)是 MUST/ 推荐实现。
- **致命风险——alg=none 与算法混淆**:RFC 7519 第 6 节定义了 `alg:"none"` 的无签名 JWT(签名值为空串);若服务端错误接受 `none` 或把非对称验证端误配成对称(用公钥当 HMAC 密钥),攻击者可自行伪造任意令牌。第 11.1 节强调:除非令牌被密码学绑定发行方密钥,否则内容不可用于信任决策。

## 为什么重要
JWT 把「无状态鉴权」落到工程,但也把信任完全押在签名与算法配置上。一行错误的验签配置(`alg` 白名单缺失)就可能让全站鉴权形同虚设,这类漏洞在真实渗透里屡见不鲜。

## 常见坑
- 验签时不固定 `alg` 白名单,接受客户端在 Header 里指定的任意算法,导致算法混淆攻击。
- 接受 `alg:"none"`,任何人都可造令牌。
- 把敏感信息(密码、身份证)塞进 Payload——它默认只是 base64url 明文,不是密文。
- 用对称密钥 HS256 却把密钥硬编码在前端,等于没签名。

## 动手自测
1. 找一个 HS256 token,把 Payload 里 `sub` 改成 admin,用原密钥重新算签名,观察能否通过验签(应能通过,说明改密文必须重签)。
2. 把 Header 的 `alg` 改成 `none` 去掉签名,丢给一个「未限制算法」的服务端,会发生什么?
3. 你会如何用 RS256 避免算法混淆?说明验签端只接受非对称公钥、且校验 `alg` 在白名单内。

## 面试视角
JWT 必考安全点:结构、签名、为什么不能放敏感数据、`alg:none` 与算法混淆攻击、密钥管理。能现场讲清「验签必须锁死 alg 白名单」,就甩开大多数候选人。

## 5. 密码存储:加盐哈希

> 引导：锚定 OWASP 密码存储备忘单,确立 Argon2id 首选、唯一随机盐、慢哈希的工作因子原则,替代明文与快速哈希。

## 心智模型
存密码不能「加密」,要「加盐哈希」——加密是可逆的(钥匙一丢全完),哈希是单向的(只进不出),加盐让相同密码也得到不同结果。就像每个保险箱都先随机混入一把独特沙子再铸模,即便两人口令相同,铸出来的模也不一样,彩虹表(预计算对照表)直接失效。

## 核心知识点（锚定官方）
- **OWASP《Password Storage Cheat Sheet》铁律**:密码绝不能明文、不能用可逆加密;必须用现代自适应哈希算法——**Argon2id(首选)**,其次 scrypt、bcrypt,或需 FIPS 合规用 PBKDF2。
- **唯一随机盐**:每个密码配一个随机盐,防御彩虹表与数据库预计算查找;Argon2id/bcrypt/PBKDF2 均要求调用方提供盐(多数库自动生成)。
- **慢哈希(工作因子)**:SHA-256 这类快速哈希不适合存密码——攻击者每秒能试海量猜测;Argon2id 推荐最低 19 MiB 内存、2 次迭代、1 并行度,bcrypt 工作因子 ≥10,让暴力破解又慢又贵。
- **参数基准**:OWASP 给出 PBKDF2(HMAC-SHA-256)迭代 ≥600,000,作为 FIPS 场景基线。

## 为什么重要
凭据库是攻击者的头号目标。一旦泄露,弱哈希(明文/MD5/ 无盐 SHA)能在数小时内被彩虹表或 GPU 集群破解;而 Argon2id + 独立盐,即便单条泄露也极难还原明文,把损失锁在「这一批」而非「全部用户」。

## 常见坑
- 用 MD5/SHA1 直接哈希密码还不加盐——教科书级错误。
- 把密码「加密」存储,以为更安全,实则密钥泄露即全裸。
- 所有用户共用一个盐,盐失去意义,彩虹表仍可复用。
- 工作因子设太低,哈希快到攻击者能并行爆破。

## 动手自测
1. 用 `bcrypt` 库对同一个明文密码分别加两次盐,比较两次密文是否相同,并尝试验证是否都通过。
2. 在本地用 hashcat 对一段 MD5(无盐)和一个 bcrypt 哈希各跑一会儿,直观感受破解速度差异。
3. 写出一个「注册时存哈希、登录时验证」的最小后端流程,注意盐和哈希结果都要入库。

## 面试视角
「密码怎么存」是安全必考题。标准答案:Argon2id/bcrypt + 每用户随机盐 + 高工作因子,绝不明文/ 可逆加密/ 无盐快速哈希。能说出慢哈希抗 GPU、盐抗彩虹表,基本稳。

## 6. 加密基础:对称、非对称与哈希

> 引导：厘清哈希/对称/非对称三者的用途边界与组合(HTTPS 混合加密),并强调密钥管理才是核心。

## 心智模型
加密三兄弟常被混:哈希(单向摘要,验真不还原)、对称加密(一把钥匙开解锁,快)、非对称加密(公钥加密私钥解,慢但能解决「怎么安全送钥匙」)。HTTPS 正是用非对称交换出一把对称会话密钥,之后用对称高速通信——各取所长。

## 核心知识点（锚定官方）
- **哈希(无密钥,单向)**:SHA-256 等,用于完整性校验、口令存储(见上节)、数字签名中对摘要签名。
- **对称加密(AES)**:同一密钥加解密,GCM 等带认证的模式(AEAD)同时保证机密与完整;适合大量数据。
- **非对称加密(RSA/ECC)**:公钥加密、私钥解密(机密性),或私钥签名、公钥验签(不可抵赖/ 完整性)。TLS 握手用非对称协商出对称密钥。
- **密钥管理是核心**:算法再强,密钥泄露全归零。密钥应存 KMS/ 环境变量,绝不硬编码、不进代码仓库。

## 为什么重要
数据在「传输中」(TLS)与「静态存储」(磁盘加密)都需要保护。分不清哈希与加密、把密钥写死在源码里,都会把精心选的算法变成摆设。合规(等保/GDPR)也明确要求传输与存储加密。

## 常见坑
- 用 base64 当「加密」——它只是编码,谁都能解。
- 自己发明加密算法或模式(如 ECB 分组),ECB 会让相同明文块得到相同密文,泄露结构。
- 硬编码密钥进 GitHub,被扫描机器人秒抓。
- 用 RSA 直接加密大文件(极慢且受限),应只加密对称密钥。

## 动手自测
1. 用 OpenSSL 分别对一段文本做 AES-256-GCM 加密与 SHA-256 哈希,对比两者产物与是否能还原。
2. 找一段用了 ECB 模式的加密图,观察明文规律如何「透」到密文(经典 Linux 企鹅图)。
3. 检查你项目里所有密钥配置,是否存在硬编码进仓库的情况,列出整改方式。

## 面试视角
常见辨析题:哈希 vs 加密、对称 vs 非对称、为什么 HTTPS 用混合加密。讲清「非对称协商对称密钥」的动机与密钥管理的重要性,就能体现工程素养。

## 7. SQL 注入与防护

> 引导：锚定 OWASP 注入防护备忘单,确立参数化查询为首要防御,转义为脆弱兜底,辅以白名单与最小权限。

## 心智模型
SQL 注入像有人在你写的「问句模板」里偷偷塞了半句命令,数据库分不清哪句是你的、哪句是他的,照单全收。根治办法只有一个:把「句子结构」和「填空内容」彻底分开——这就是参数化查询。

## 核心知识点（锚定官方）
- **OWASP《SQL Injection Prevention Cheat Sheet》首要防御**:对所有数据库访问使用**参数化查询 / 预处理语句(Prepared Statements with bind variables)**,先定义全部 SQL 代码、再传参数,数据库始终区分代码与数据,即便输入含 SQL 命令也无法改变查询意图。
- **转义不可信输入是第四选项且「强烈不推荐(STRONGLY DISCOURAGED)」**:脆弱、无法保证防住所有注入,不能作为主防线。
- **白名单输入验证**:当表名/ 列名/ 排序方向(ASC/DESC)等无法用绑定变量时,把用户值映射到代码里的固定字符串(allow-list);输入验证也是所有情况的辅助防线。
- **最小权限(Least Privilege)**:DB 账户只给必需权限,绝不分配 DBA/ADMIN,不同应用用不同 DB 用户,可借视图细化到字段级。

## 为什么重要
SQL 注入长期位居 OWASP Top 10 的 Injection 类(A03,2021),可导致拖库、绕过认证、甚至命令执行。它是「字符串拼接 + 用户参数」这一习惯动作的直接产物,初看只是小漏洞,实则是数据资产的头号威胁。

## 常见坑
- 用字符串拼接拼 SQL(`"SELECT * FROM u WHERE name='"+name+"'"`),name 传入 `' OR '1'='1` 直接命中全表。
- 以为「转义一下」就安全,OWASP 明确转义脆弱不可靠。
- 应用用 root/DBA 账号连库,注入一旦成功就是完整控制。
- 误信 ORM 自动防注入而写 HQL/JPQL 拼接,同样中招(ORM 也需参数化)。

## 动手自测
1. 用 Java `PreparedStatement` 与 `?` 占位符写查询,传入 `tom' OR '1'='1`,观察数据库是「查找该字面用户名」还是「返回全表」。
2. 在旧代码里 grep 出所有 `+` 拼接 SQL 的位置,逐一改成绑定变量。
3. 给一个必须用动态表名的报表查询,设计 allow-list 映射(如 `case "sales": "t_sales"`),杜绝用户直接指定表名。

## 面试视角
注入是安全题常客。标准答:参数化查询为主、白名单为辅、最小权限兜底,绝不靠转义;能结合「代码与数据分离」的本质讲,比背清单更得分。也可延伸到 NoSQL 注入与 ORM 的正确用法。

## 8. XSS 与 CSRF

> 引导：区分骗浏览器(XSS)与骗服务器(CSRF)两类攻击,掌握编码/CSP/HttpOnly 与 SameSite/Token 的对应防护。

## 心智模型
XSS 是「把恶意脚本塞进别人的浏览器替你执行」,CSRF 是「借用户的登录态,以他的身份偷偷发请求」。一个骗浏览器,一个骗服务器。二者都靠「用户已经登录」这个前提,所以防御要从浏览器与服务器两端同时下手。

## 核心知识点（锚定官方）
- **XSS(跨站脚本)**:OWASP 归类为注入的一种。存储型(恶意脚本存库后渲染)、反射型(参数回显)、DOM 型(前端 JS 操作 DOM 触发)。防护靠**输出编码**(HTML/JS/URL 上下文分别编码)、`Content-Security-Policy`(CSP,限制可执行的脚本源)、`HttpOnly` Cookie 防脚本读 token。
- **CSRF(跨站请求伪造)**:攻击者诱导已登录用户访问恶意页,自动发起跨站请求(如转账)。防护靠 `SameSite` Cookie(Strict/Lax 阻断跨站携带)、**CSRF Token**(服务端下发、请求时校验)、关键操作要求二次确认。
- **OWASP Top 10 关联**:A03 Injection 涵盖 XSS;A01 Broken Access Control 常是 CSRF 的后果;身份与认证失效(A07)也与之相关。

## 为什么重要
XSS 能偷 token、钓鱼、蠕虫传播;CSRF 能在用户不知情下完成任意状态变更。二者都直接建立在「信任已登录用户」之上,前端再怎么隐藏按钮都没用——后端必须校验来源与意图。

## 常见坑
- 富文本直接 `innerHTML` 渲染用户内容,未做白名单过滤与编码。
- 只在前端做输入校验,后端不校验,攻击者可绕过前端直接发请求。
- 全局关掉 `SameSite` 又不加 CSRF Token,给了伪造请求可乘之机。
- 误以为 HTTPS 能防 CSRF/ XSS——加密和这两个攻击维度无关。

## 动手自测
1. 在一个评论框输入 `<script>alert(document.cookie)</script>`,看存储后其他用户页面是否弹窗(应有 CSP + 输出编码使其失效)。
2. 关闭 `SameSite` 后,用一个第三方站点自动提交表单,观察目标站点是否执行了越权操作(验证需加 CSRF Token)。
3. 给你的项目写一条 CSP 策略,只允许同源脚本与指定 CDN,测试内联脚本是否被拦。

## 面试视角
XSS 与 CSRF 几乎必问。讲清二者区别(骗浏览器 vs 骗服务器)、各自防护(编码/CSP/HttpOnly vs SameSite/Token),并点出「HTTPS 不防这俩」,能快速拉开差距。

## 9. 权限模型:RBAC 与 ABAC

> 引导：对比角色模型与属性模型,落到最小权限与职责分离,建立可扩展、可审计的授权体系。

## 心智模型
权限模型回答「谁能对什么做什么」。RBAC 像公司门禁卡——按「角色」批量授权(管理员/ 员工/ 访客);ABAC 像智能门禁——每次刷卡都现算(时间、地点、职级、资源敏感度综合判断)。前者简单好管,后者细到字段级但复杂。

## 核心知识点（锚定官方）
- **RBAC(基于角色)**:用户→角色→权限的三元组。NIST RBAC 模型定义了角色层级、约束(如职责分离 SoD)。适合组织边界清晰的系统,授权变更只需调角色。
- **ABAC(基于属性)**:用主体/ 资源/ 环境/ 操作的属性组合成策略(如「职级≥P6 且 工作时间 且 资源密级≤内部」),策略引擎(如 XACML、OPA)实时决策,粒度到字段/ 行级。
- **最小权限原则(Least Privilege)**:每个主体只拿完成工作所需的最小权限,是 RBAC/ABAC 共同的设计基线,也是 OWASP、NIST 反复强调的纵深防御一环。
- **职责分离(SoD)**:互斥角色不可同属一人(如「发起付款」与「审批付款」),防止单人舞弊。

## 为什么重要
权限模型是「授权」的工程落点。模型选错:用硬编码 `if(role=='admin')` 会随业务爆炸;忽视最小权限会让一个越权漏洞放大成全身瘫痪。RBAC/ABAC 的取舍直接决定系统能否安全、可审计地扩张。

## 常见坑
- 用字符串硬编码角色判断散落各处,改一次权限要动几十个 `if`。
- 给默认角色塞太多权限(「超级管理员」泛滥),违背最小权限。
- 忘记 SoD,同一账号既能发起又能审批,埋下舞弊风险。
- 把权限判断只放前端,后端不校验(见第 1 节越权坑)。

## 动手自测
1. 把你系统的权限需求列成「用户-角色-资源-操作」表,看是否落在 RBAC 能覆盖的范围;哪些必须 ABAC?
2. 找出代码里所有 `if(user.role===...)` 硬编码,设计一张角色-权限映射表替代。
3. 设计一个「转账」功能的 SoD 规则,确保发起人与审批人不能是同一人。

## 面试视角
权限设计题常考 RBAC vs ABAC、最小权限、SoD。结合你实际项目讲「从硬编码角色迁移到 RBAC 表」的经历,比纯概念更有说服力;能提 OPA/ 策略即代码是加分项。

## 10. 纵深防御与安全响应头

> 引导：用纵深防御框架串联各层防护,掌握 CSP/HSTS 等高杠杆安全头与 OWASP Top 10 自查清单。

## 心智模型
把安全当成「最后一道门」必输,要当成「层层设防的城堡」:城墙(网络)、吊桥(网关/WAF)、卫兵(认证授权)、金库(加密存储)、监控(日志审计)各管一段。任何一层被突破,后面还有缓冲。这就是「纵深防御」,也是 OWASP、NIST 共同倡导的底层思维。

## 核心知识点（锚定官方）
- **安全响应头**:`Content-Security-Policy`(限制脚本源,挡 XSS)、`Strict-Transport-Security`(HSTS,强制 HTTPS)、`X-Content-Type-Options: nosniff`(防 MIME 嗅探)、`X-Frame-Options`/`Content-Security-Policy: frame-ancestors`(防点击劫持)。OWASP 有《HTTP Headers Cheat Sheet》系统梳理。
- **纵深防御(Defense in depth)**:多层异构控制,任一单点失效不导致整体失守;网络层(WAF/ 防火墙)、应用层(认证/ 授权/ 输入校验)、数据层(加密/ 最小权限)协同。
- **OWASP Top 10(2021)**:A01 失效的访问控制、A02 加密机制失效、A03 注入、A07 身份与认证失效等——是安全自查的优先级清单。
- **日志与审计**:记录认证成功/ 失败、授权拒绝、敏感操作,且日志本身不可篡改,是事后溯源与合规的基础。

## 为什么重要
没有绝对安全的单点。一次 0day、一个配置失误都可能突破某层;纵深防御让「突破一层」不至于「全线崩溃」。安全响应头是零成本的高杠杆加固,应默认开启。

## 常见坑
- 只在登录页加 HTTPS,其他页面走 HTTP,被中间人降级劫持。
- 开了 CSP 却 `default-src 'unsafe-inline'`,等于没开。
- 日志里记了明文密码/ 令牌,日志本身成了泄露源。
- 以为「上了 WAF 就安全」,忽视应用层与数据层防护。

## 动手自测
1. 用 securityheaders.com 或本地扫描,给你项目出一份响应头评分,逐条补齐缺失头。
2. 列出你系统的安全分层(网络/ 应用/ 数据),标出哪层是单点、一旦失效无兜底,设计补强。
3. 检查日志配置,确认敏感字段(密码/ token)未被明文写入。

## 面试视角
综合题常问「你们怎么保障安全」。用纵深防御框架组织回答:传输(HSTS/TLS)、应用(认证授权/ 输入校验/OWASP Top 10 自查)、数据(加密/ 最小权限)、可观测(日志审计),比罗列工具更显体系化。
