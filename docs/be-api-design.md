# be-api-s1 | REST 成熟度与资源建模
> 好的 REST 不是"用 JSON 走 HTTP"，而是用 HTTP 表达资源与操作。

## 心智模型
REST 资源建模像**图书馆编目**：每本书（资源）有唯一索书号（URL），你用标准动作（HTTP 方法）对它"借阅/归还/续借"，而不是为每种操作发明一个新动词接口。URI 是名词、方法是动词。

## 核心知识点（锚定官方）
- **Richardson 成熟度模型**：Level 0（单端点 RPC）→ 1（资源 URI）→ 2（用 HTTP 方法/状态码）→ 3（HATEOAS 超媒体）。生产通常目标 Level 2。
- **资源 vs 子资源**：`/users/{id}/orders` 表达从属；用名词复数、避免动词（`/getUser` 反模式）。
- **HTTP 方法语义（RFC 9110）**：GET 安全幂等、POST 建资源、PUT 全量替换、PATCH 部分更新、DELETE 删。

## 为什么重要
API 是后端核心交付物，建模质量直接决定前端易用性、可缓存性与演进成本。清晰的资源模型能减少"接口爆炸"和歧义。

## 常见坑
- 把动词塞进 URI（`/createUser`、`/updateOrderStatus`）破坏资源化。
- 用 POST 做本该 GET 的查询，丧失缓存与安全语义。
- 用 PUT 当 PATCH，误覆盖未传字段。

## 动手自测
1. 把一个"用户改密码/冻结账号"的 RPC 式接口重构成资源化 REST（含正确方法与状态码）。
2. 用 curl 验证 GET 可重复（幂等）、POST 重复创建两条。

## 面试视角
"REST 成熟度？资源建模原则？PUT 和 PATCH 区别？"——讲清资源化、HTTP 语义、幂等。

# be-api-s2 | HTTP 语义与状态码
> 状态码是 API 的"表情"，用错会让调用方误判。

## 心智模型
HTTP 状态码像**快递员的回执代码**：2xx 妥投、3xx 改地址、4xx 是你填错单（客户端问题）、5xx 是快递公司炸了（服务端问题）。乱用代码等于回执写错，收件人无法判断真状况。

## 核心知识点（锚定官方）
- **2xx**：200 成功、201 已创建（POST 建资源）、204 无内容（DELETE 成功）。
- **4xx**：400 请求错、401 未认证、403 无权限、404 资源不在、409 冲突（如重复创建）、422 语义校验失败。
- **5xx**：500 未捕获、502/504 网关/超时、503 不可用（限流/维护）。

## 为什么重要
正确的状态码让网关、重试、前端错误处理自动化。比如 429（Too Many Requests）配合 `Retry-After` 才能让客户端优雅限流重试。

## 常见坑
- 所有错误都返回 200 + `{success:false}`，破坏 HTTP 语义与中间件判断。
- 用 404 表示"无权限"（应 403），泄露资源是否存在。
- 500 把堆栈细节返回给客户端（安全风险）。

## 动手自测
1. 设计一套错误码：重复注册返回 409、未登录 401、越权 403、参数错 422。
2. 验证网关对 5xx 自动重试、对 4xx 不重试的行为差异。

## 面试视角
"401 和 403 区别？何时 409/422？为什么别总返回 200+success？"——讲清客户端/服务端、语义化错误。

# be-api-s3 | API 版本化策略
> 接口上线就有人依赖，改了不能让老调用方崩。

## 心智模型
版本化像**合同的不同修订版**：你出了 v2 新条款，但 v1 老客户手里的合同在到期前依然有效。API 版本让"升级"和"不破坏老用户"可以并行。

## 核心知识点（锚定官方）
- **URL 版本**：`/v1/users`、`/v2/users`——简单直观，但污染资源路径。
- **Header 版本**：`Accept: application/vnd.myapi.v2+json` 或自定义 header——资源 URI 干净，但调试不直观。
- **演进式（无版本）**：只做向后兼容的加字段，旧客户端忽略新字段（JSON 天然友好）。

## 为什么重要
破坏式变更是"半夜被叫醒"的主因。选对版本策略能平滑演进，给老用户迁移窗口，同时推进新能力。

## 常见坑
- 在 URL 里塞 `/v1` 又同时改了 v1 行为，等于没版本。
- 版本无限分裂（v1~v9 共存），维护成本爆炸，应设弃用与下线流程。
- 忽略"默认版本"策略，新人不知调哪个。

## 动手自测
1. 同时提供 `/v1/users` 与 `/v2/users`（v2 多返回 `avatar`），验证老客户端不受影响。
2. 给 v1 加 `Deprecation` 响应头，规划 6 个月后下线。

## 面试视角
"URL 版本 vs Header 版本？演进式版本怎么做？如何弃用旧版？"——讲清兼容、迁移窗口、弃用流程。

# be-api-s4 | OpenAPI 与文档即契约
> API 文档不该是人肉维护的 Word，应是机器可读的契约。

## 心智模型
OpenAPI 像**接口的标准化图纸**：你用 YAML/JSON 描述"有哪些路径、参数、返回啥"，机器据此自动生成在线文档、客户端 SDK、甚至服务端桩代码。文档不再是会过期的附属品，而是单一事实源。

## 核心知识点（锚定官方）
- **OpenAPI Specification（openapis.org）**：`paths/parameters/requestBody/responses/components` 描述接口；`swagger-ui` 渲染交互文档。
- **代码生成**：`openapi-generator` 生成客户端/服务端骨架；`oapi-codegen`（Go）等。
- **契约校验**：用 Spectral 做规范 lint，CI 里卡风格与必填字段。

## 为什么重要
文档滞后、前后端对字段理解不一致是协作黑洞。OpenAPI 让"文档=契约=测试依据"统一，显著提升联调效率。

## 常见坑
- 手写文档不与代码同步，三个月后就失真。
- 只描述 happy path，缺错误响应与鉴权说明。
- 用生成器但把生成代码改了又手改，下次生成覆盖冲突。

## 动手自测
1. 为一个现有接口写 OpenAPI 描述，用 swagger-ui 渲染可交互文档。
2. 用 Spectral 对其做 lint，修复缺失的 4xx 描述。

## 面试视角
"OpenAPI 解决什么？文档即契约怎么落地？如何防文档失真？"——讲清单一事实源、自动生成、契约校验。

# be-api-s5 | GraphQL 适用与权衡
> 当客户端要"自己挑字段、一次拿全"，GraphQL 比 REST 省往返。

## 心智模型
GraphQL 像**自助餐而不是套餐**：REST 是后端定好"一份套餐（固定字段）"，GraphQL 让客户端用查询自己选"要哪几样、要不要嵌套的配菜"，一次请求拿全，不多不少。

## 核心知识点（锚定官方）
- **Schema + Query/Mutation（graphql.org）**：强类型 schema 定义可查字段；`query` 读、`mutation` 写。
- **Resolver**：每个字段对应一个解析函数，天然聚合多源数据。
- **代价**：N+1 查询（用 DataLoader 批处理）、缓存比 REST 难（需 APQ/Response Cache）、查询复杂度需限流。

## 为什么重要
聚合多服务的 BFF、字段需求多变的移动端，GraphQL 能大幅减少往返与过度获取。理解权衡才能判断"该不该上"。

## 常见坑
- 不做查询复杂度/深度限制，恶意深查询打垮服务。
- N+1 问题未用 DataLoader，一个列表查询触发上百次 DB。
- 用 GraphQL 当 REST 的纯替换，却丢了 HTTP 缓存/CDN 优势。

## 动手自测
1. 用 GraphQL 一次查出"用户+其最近3订单+订单商品"，对比 REST 需几次往返。
2. 加查询深度限制中间件，验证深递归查询被拒。

## 面试视角
"GraphQL 和 REST 取舍？N+1 怎么解？为什么需要限流？"——讲清聚合优势、DataLoader、复杂度控制。

# be-api-s6 | gRPC 与 Protobuf
> 内部服务间高性能通信，gRPC 用 HTTP/2 + Protobuf 取代 JSON。

## 心智模型
使用 gRPC 像**两台机器说同一种紧凑二进制方言**：用 Protobuf 定义"接口与消息格式"（.proto），代码自动生成，数据序列化成体积小、解析快的二进制，跑在 HTTP/2 多路复用上，比 JSON/REST 快且省带宽。

## 核心知识点（锚定官方）
- **Protobuf（protobuf.dev）**：IDL 定义消息，强类型、向后兼容（只加字段、不改/删已用编号）。
- **gRPC（grpc.io）**：四种方法——Unary、Server/Client Streaming、Bidirectional；默认 Protobuf 编码。
- **适用**：内部微服务、低延迟、多语言 SDK 生成；浏览器需 gRPC-Web 网关。

## 为什么重要
服务网格内服务间调用追求低延迟与强契约，gRPC 是云原生事实标准（K8s/Envoy 原生友好）。懂它能在"何时用 REST、何时用 gRPC"上做对选择。

## 常见坑
- 改 Protobuf 已用字段编号导致不兼容（必须只增不改删）。
- 在人-机（浏览器直连）场景硬上 gRPC，缺少生态与调试便利。
- 忽略 HTTP/2 连接管理，高频短连接失去多路复用优势。

## 动手自测
1. 定义 proto 并生成 Java/前端 stub，写一个简单的 Unary 调用。
2. 给消息新增字段但不改旧编号，验证旧客户端仍可读。

## 面试视角
"gRPC 适用场景？Protobuf 兼容性规则？和 REST 比优劣？"——讲清内部高性能、编号兼容、场景取舍。

# be-api-s7 | 分页/过滤/排序与幂等
> 列表接口和写接口的健壮性，决定系统能不能扛规模。

## 心智模型
分页/过滤/排序像**图书馆的检索台**：你告诉它"第几页、按什么筛、怎么排"，它返回刚好一屏；幂等像**重复提交同一张转账单**，系统只真正执行一次，不会因为点了两次就转两笔。

## 核心知识点（锚定官方）
- **游标分页 vs offset 分页**：offset（`?page=2&size=20`）简单但深翻慢、易漏数据；cursor（`?after=<id>`）基于有序键，稳定高效。
- **幂等键**：写接口带 `Idempotency-Key`，服务端去重，防重试双写。
- **过滤/排序**：用统一 query 约定（`?status=open&sort=-createdAt`）。

## 为什么重要
列表是最高频接口，深分页和乱序会让 DB 雪崩；非幂等写接口在超时重试时会制造重复订单/重复扣款，是资损高危点。

## 常见坑
- 深翻 offset 导致 `LIMIT 100000,20` 全表扫描。
- 重试 POST 创建导致重复资源（无幂等键）。
- 排序字段无索引，查询变慢。

## 动手自测
1. 把 offset 分页改成游标分页，验证大数据集深翻性能。
2. 给创建订单接口加幂等键，连续两次同键请求只生成一单。

## 面试视角
"游标和 offset 分页区别？为什么写接口要幂等？幂等键怎么实现？"——讲清稳定性、去重、资损防护。

# be-api-s8 | API 层认证与授权
> 谁能用、能用什么，必须在 API 边界就卡死。

## 心智模型
API 网关/接口层像**大楼门禁**：先刷工牌确认你是谁（认证 authentication），再看你的权限卡决定能进哪层（授权 authorization）。这两项必须在"进门处"统一做，不能每个房间自己判断。

## 核心知识点（锚定官方）
- **认证**：JWT（RFC 7519）/OAuth2（RFC 6749）Bearer Token；网关校验签名与过期。
- **授权**：RBAC/ABAC 在资源层判定；API 层做粗粒度（是否登录、是否有 scope）。
- **最小暴露**：公开/内部接口分离，内部接口不暴露公网。

## 为什么重要
越权访问（见 be-sec）多因认证授权在 API 边界缺失或错位。统一的网关层鉴权是安全基线。

## 常见坑
- 把授权逻辑散落各接口，漏一处就越权。
- JWT 不校验 `aud`/`iss` 或被弱密钥签名，被伪造。
- 内部接口误暴露公网且无鉴权。

## 动手自测
1. 在网关统一校验 Bearer Token，未带返回 401，越权返回 403。
2. 用错误密钥签的 JWT 调接口，验证被拒。

## 面试视角
"认证与授权区别？API 层该做多细的授权？JWT 校验要点？"——讲清身份/权限、边界统一、令牌校验。

# be-api-s9 | API 演进与兼容性
> 接口是承诺，演进要"加新不改旧、弃用有流程"。

## 心智模型
API 演进像**城市基建改造**：你可以新建一条更宽的路（加字段/新版本），但不能突然把老路挖断让还在跑的车掉坑（破坏兼容）。旧路要退役，得先立"即将封闭"的牌子（Deprecation），给足够过渡期再填。

## 核心知识点（锚定官方）
- **向后兼容原则（Google API Design Guide）**：只加可选字段、不改语义、不改/删字段编号（呼应 Protobuf）；旧客户端忽略未知字段。
- **弃用流程**：`Deprecation` 头 + 文档 +  sunset 日期，监控旧版调用量归零再下线。
- **破坏式变更**：改 URL、改字段名、改类型、改状态码——必须走新版本。

## 为什么重要
API 一旦有人调用就成了"公开契约"。缺乏演进纪律会让每次改动都变成事故，或让团队因怕破坏而不敢优化（技术债堆积）。

## 常见坑
- 直接改线上字段名，老 App 全部解析失败。
- 宣布弃用却无限期不清，版本越积越多。
- 把"内部临时接口"当稳定接口对外，后期无法改动。

## 动手自测
1. 给接口加一个可选 `tags` 字段，验证老客户端（不读该字段）无感。
2. 设计弃用时间线：Deprecation 头 + 90 天监控 + 下线。

## 面试视角
"什么是向后兼容？破坏式变更有哪些？弃用流程怎么设计？"——讲清加新不改旧、监控下线、契约精神。
